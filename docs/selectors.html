Selectors

Selectors are the permitted reads of the state. They are the contract's methods, used as they are by components, the store and tests. You write them with the state as the first parameter, and Super supplies it at call time: you write count(s, id) in the contract, then selectors.count(id) everywhere else.

Declaring selectors

  • Each selector receives the state as its first parameter. Annotate it (s: CounterState): TypeScript does not infer a method's parameters.
  • It can take other parameters after the state: count(s, id: string) is used as selectors.count('coffees').
  • It can ignore the state: catalog returns static data. This is useful so that components have nothing to ask for other than the contract.
  • It must be pure: no side effects, no network calls, only a read.
  • pending is reserved: Super adds it to the selectors, to tell whether a command is pending (selectors.pending('load')). A pending method in the contract does not compile (error at the store's declaration). A selector only reads the state; pending commands are not part of it.

A selector without parameters

A selector only takes a parameter if the answer depends on it. canDecrement needs the id (you need to know whether this counter is above 0). loadErrorMessage does not: the answer only depends on the global state. On the component side, the difference shows: a selector without parameters is passed as is to @selector loadErrorMessage = this.counter.selectors.loadErrorMessage;, a selector with parameters is called inside a function (see In a component).

Why selectors

  • A single definition. "A missing counter is worth 0" is written once. The store, components and tests apply the same rule; changing it in the contract changes it everywhere.
  • A closed door. A component never sees the raw state: this.counter has no state(), and this.counter.selectors.counts does not compile, since counts is not a selector. The view cannot reinvent a reading rule on its own.
  • Less noise. The state is supplied by Super: no s to carry around.

In a component

An @selector reads a selector's value as is; the condition or the computation happens in render, or in a new selector in the contract. See Reading a store for the re-render rules.

In the store

Each call rereads the current state: right after a this.set, this.selectors.count(id) already returns the new value.

In a test

Why on the handle, and not on the contract? A contract has no state: it describes a store, it is not one. There can be several stores for the same contract. Selectors are therefore read on a specific store: its handle (store.selectors), its view in a component (this.counter.selectors), or this.selectors in the store itself. Each one supplies that store's state, and its cache.

What to put in a selector

  • Yes: any read that a component or the store does more than once, or that contains a rule ("worth 0 if missing", "possible if nothing is pending").
  • Yes: the data that components need and cannot import from @core/ (catalogue, labels).
  • Yes: a value the screen displays after a condition or a computation, when that computation deserves a name. @selector only accepts a selector as is; one more selector keeps the component simple.
  • No: a selector that returns the whole state (all(s: CounterState) { return s; }). That reopens the door selectors close.
  • Yes: derivations (a cart's lines, total, filtered list). They belong in the contract rather than in components: they are shared, testable without a DOM, and Super stabilises their result (see below).

Deriving in a selector

A selector can filter, sort or build new objects without any particular precaution. Each store keeps a cache of its selectors, and Super avoids needless recomputations and re-renders in two steps.

  • Recompute or not: Super records the top-level fields of the state that the selector reads. On the next state change, if none of these fields has changed reference, the previous result is returned without recomputing.
  • Keep the reference: after a recomputation, the result is deeply compared with the previous one. If it is equal, the old reference is returned. Otherwise, the unchanged parts (a line that has not moved) keep theirs.

Example: a messaging app whose state contains the messages and the reply being typed.

visible reads messages and folder. A keystroke in draft creates a new state, but triggers no filter, no sort and no re-render. A received message triggers the recomputation; the list re-renders, and only the new message's line is new.

What you need to know:

  • Tracking stops at the top level: a selector that returns s.messages[3].subject is recomputed as soon as any message changes. The recomputation has no consequence, the comparison of the result avoids the re-render.
  • A selector that walks the whole state (Object.keys(s), { ...s }) depends on everything: it is recomputed on every change.
  • The comparison only descends into arrays and plain objects: a Date, a Map or a class instance is compared by reference.
  • A selector only reads its state and its arguments: what it would read elsewhere (a module variable, Date.now()) is not tracked.

A contract without selectors

Selectors are optional, but they are the only reads a component has. Without them, a component can send commands to the store and listen to its events, nothing more: it never sees the raw state. The full handle, for its part, keeps state() for tests, the composition root and the other stores. The router follows the same rule: components read the active route through this.router.current (name(), path(), params, query), never its raw state (see Router).
