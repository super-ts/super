Guarantees

Most misuses of Super are caught before run time: by TypeScript, or by the Vite plugin. This page lists what is checked, where, and what is not.

Except for the section on templates, each excerpt below comes from the repository's type tests (packages/*/src/*.test-d.ts): each @ts-expect-error there makes npm run typecheck fail if the expected error disappears. The excerpts use their test contract basket: commands add({ sku }), clear() and save({ id }) (which declares Outcome<{ count: number }, 'empty' | 'offline'>), events emptied and saved: { id }, selectors quantity(sku), count(), entries().

Contracts and stores

  • A command declared with a direct response, or with several parameters.
  • A super({ contract }) that names an unknown contract, or a non-conforming initial state.
  • With implements Commands<Self>: a command without a method, a method whose parameters differ from the contract's, a method that returns something other than the declared result (or forgets it), a public method outside the contract.
  • An unknown event, a payload wrongly typed or forgotten; a failure reason unknown to the contract; an unknown command in this.send.
  • Missing or wrongly typed dependencies at creation.

Templates in .super files

The template of a .super component is checked by npm run typecheck (super-tsc), and each error is reported at its position in the .super. The excerpt comes from the test project in packages/lang: each line marked ERROR must be reported, and no other (packages/lang/src/check.test.ts); there are 16 of them. Greeting there is a component with props { name: string }, which emits closed; Panel declares @prop heading: string;, @prop content: Children; and @prop footer?: Children;.

  • A tag without a hyphen that is not a known HTML tag.
  • A possibly null value read without a test; the narrowing of an if applies to the elements it contains.
  • A loop key (key) that does not exist on the iterated item.
  • An object displayed with {…} (no more [object Object]).
  • An on: listener for an event the tag does not have, and the type of the received event (e.currentTarget is the HTMLInputElement).
  • A ref={…} reference set on an element of a different type from its own.
  • A non-exhaustive switch, with default: {assertNever(x)}.
  • On a child component: an unknown prop, a wrongly typed prop, an on: for an event missing from its emits.
  • Children for a component that does not declare content, required children that are missing, a <:name> slot that is not a prop of the component.
  • Text that starts like a statement without being one, with the suggested fix: {'for (more info) see below'}.
  • A prop named after a property of HTML elements (@prop title, id, hidden…): "'title' is already a property of HTML elements: choose another name".

The TypeScript message is reported as is ("'nam' does not exist in type 'Props'. Did you mean to write 'name'?"). The parser also rejects, with the message and often the fix (packages/lang/src/parser.test.ts, packages/lang/src/compile.test.ts):

  • lit syntax: @click, ?disabled, .value ("lit syntax: write on:click={…}");
  • < and } in text, with the fix {'<'}, {'}'};
  • a closing tag that does not match ("</i> closes <b>");
  • return x; in a method that emits elements (return; remains allowed, as does return x; in a nested function);
  • an element outside a class method;
  • a block whose } is missing before the parent's closing tag;
  • a <:name> slot outside a component, with attributes, filled twice, or named content.

Component declarations

The @tag, @title, @prop and @emit declarations are read by the parser, which rejects (parser.test.ts, "parse: component declarations"):

  • a component without @tag ("A component declares its tag: `@tag = 'my-component';`"), except an abstract class;
  • static tag = '…'; in a .super ("In a `.super` file, the tag is declared with `@tag = '…';`");
  • a tag that is not a literal string, in lower case, with a hyphen;
  • a hand-written SuperElement<…> generic ("In a `.super` file, props and events are declared in the class: `@prop name: Type;` and `@emit name: Type;`");
  • a duplicate declaration ("`@tag` declared twice", "`@prop a` declared twice");
  • a prop without a type (@prop label;), an optional prop with a default value (@prop size?: number = 2;: "remove the ?"), an event with a value;
  • a declaration outside a component ("`@prop` is only written in a component (`extends SuperElement`)").

The component's types are derived from them (virtual.test.ts): @prop question: string; becomes a required prop, @prop tone: … = 'neutral'; and @prop size?: number; optional props, @emit answered: { confirmed: boolean }; an event. These are what the tags that use the component are checked against (unknown prop, wrongly typed prop, unknown on:, above).

Setup declarations (@contract, @selector, @state, @form, @ref, @on) are read too, and the parser rejects (parser.test.ts, "parse: setup declarations and listeners"):

  • a contract declared twice, even under another field name ("The contract `cart` is already declared by `@contract cart`");
  • @contract router; ("The router is read through `this.router`, without `@contract`");
  • a contract that is not a literal string (@contract cart = name;);
  • a type on @selector ("No type on `@selector`: it comes from the value");
  • a @ref without a type ("A ref declares the type of its element: `@ref input: HTMLInputElement;`");
  • a badly written @on (@on('cart'): "`@on` is written `@on('contract', 'event')`, above a method");
  • the old form in a component (cart = this.contract('cart');, this.selector(…), this.state(…), this.ref<T>()), with the rewritten line as the fix (@contract cart;, @state local = { open: false };…); outside a component, the same line remains ordinary TypeScript;
  • a listener set in the constructor ("In a `.super` file, a listener is declared on a method: `@on('cart', 'event') onEvent(payload) { … }`").

The virtual TypeScript derives from them the fields that used to be written by hand (virtual.test.ts): @contract cart; becomes readonly cart = this.contract('cart');, @selector, @state and @ref become the fields this.selector(…), this.state(…), this.ref<T>(), and @on('profile', 'save:done') onSaved(…) a listener this.contract('profile').on('save:done', …): the method's parameter therefore has the type of the event's payload, checked as in a hand-written listener. @on('router', 'navigated') becomes this.router.on('navigated', …).

Page title

@title = …; and this.page.title = … are checked at run time (packages/dom/src/page.test.ts):

  • a title set during render throws "`this.page.title` cannot be set during render";
  • this.page.title cannot be read: "`this.page.title` is set, it cannot be read";
  • the stack is tested: the last mounted component that sets a title wins, the one below follows its data without being displayed and comes back on unmount; a title written as a function follows the values it reads, like render.

The compiled code keeps the source's line numbers, and its source map maps the final JS back to the line and column of the .super (compile.test.ts). See Templates and Tooling.

Architecture (Vite plugin)

These rules are not type errors: the plugin refuses to load the module, in dev, at build time and in tests. For a .super, they apply to its compiled code. Test files (*.test.ts) are not subject to them.

  • A module that imports SuperContract or SuperStore outside src/@core/.
  • A module that imports SuperElement outside src/@components/.
  • A component that imports anything other than a type from @core/ (a contract, a store, a constant, or import * as): it talks to stores through @contract name; (this.contract('name') in a .ts).
  • A module in @core/ that imports a value from @super-ts/dom.

The plugin also reads the contracts and the router to generate src/@core/contracts.d.ts. It stops with an error on:

  • a contract (export class X extends SuperContract) that does not name itself through super({ name: '…' });
  • two contracts with the same name;
  • a contract named 'router' when the app declares a router;
  • two export const … = defineRouter(…) in the src.

What is not checked

  • A store without implements Commands<Self>: no missing command, parameters, result or extra method is detected. A command without a method is then only reported on send ("unknown command").
  • this.fail accepts the reasons of all the contract's commands, not only those of the current command.
  • A declared event that the store never emits.
  • A component does not catch the error from its own constructor: only an ancestor's renderError receives it.
  • Only one router is typed: the one the plugin finds in the src.
  • A value from the URL: it comes from outside. A value that does not match the description is read as absent (query) or undefined (param), and isValid() reports it; it is up to the screen or the guard to decide.
  • The link between a screen and its route comes from .screens(…), read by the Vite plugin: a screen it cannot find (a class without a readable @tag, or without static tag in a .ts, an import it cannot resolve) sees every route. The route a .ts component declares by hand (SuperElement<{ route: 'counter' }>) is not compared with .screens(…).
  • An incomplete oneOf list: for sort: 'label' | 'value', { oneOf: ['label'] } compiles. An extra value is rejected, but a forgotten value is not: it will never be read as valid from the URL. Since the type is given separately (query<T>), TypeScript cannot check that the list covers the whole union.
  • A component written by its tag (<counter-screen> in a template) instead of its class (<CounterScreen />): a tag with a hyphen is an arbitrary custom element, neither its attributes nor its events are checked, and this is not supported.
  • An import * as of @super-ts/dom or @super-ts/core outside the imposed folders: the placement rule only sees named imports.
