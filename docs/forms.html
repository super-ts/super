Forms

@form binds fields to typed values, applies your rules, checks with the server while the user types when needed, and submits through a store command. "Pending" and server errors come from that command's lifecycle.

A first form

  • @form signup = { … }; is declared once in the class body, like the other setup declarations. The field types come from the value: no annotation on @form. In a component written in .ts, the equivalent is signup = this.form({ … }), which throws if called during render.
  • The form is ready from construction: render can read its values and errors on the first render. It connects to the store when the component mounts, and disconnects when it unmounts.
  • signup.bind() and signup.field('email') are element directives: they are written in braces inside the tag, <form {signup.bind()}> for the form, <input {signup.field('email')} /> for a field (see Attributes).
  • disabled={signup.submitting()} sets the attribute while the submission is pending, and removes it afterwards.
  • @contract account; gives a view of the store without reading anything from it: the form has its own values. It only needs the store to send register and follow its outcome. submit.to must be a view declared by @contract, before the form in the class: declarations are initialised in order.

Why a declaration and not a <Form> component

A form is component state: its values, errors, checks and submission are read all over the template (this.edit.field('name'), this.edit.values(), the "Saving…" button). The tag already exists: it is the native <form>, bound with <form {this.edit.bind()}>. A <Form> component would hide that state behind its props and lose the field typing. <Table> is a different case: it is a display component.

Binding fields: field

field(name) goes on an <input>, a <select> or a <textarea>. It writes the value into the field, listens to input, and records the first time the user leaves the field. It picks the right property by itself according to the element type.

In the snippets below, initial comes from the @form edit = { … }; declaration, and the tags from the body of render(), where const { edit } = this; gives the form.

Text fields

The value follows every keystroke; the field is marked "touched" when the user leaves it.

Numbers and sliders

A cleared number field gives null: declare null as number | null for an optional number. The min, max and step attributes guide input, but do not replace a rule: the form turns off the browser's native validation in favour of your rules.

Dates, times and colours

These fields give strings, in the browser's format. Convert them in submit.toInput if the command expects another format.

Drop-down lists

The options can come from an array, rendered by a keyed for loop: the selection is restored once the options are in place.

Radio buttons

Each button gets its value as the second argument; the form checks the matching one. The value is typed by the union: field('plan', 'gold') does not compile. No need for a name or value attribute.

Checkboxes

Without a second argument, the box is true or false. With one, it adds or removes its value from the array.

Files

A browser does not allow pre-filling a file field: the initial value is necessarily empty, and reset() clears the field.

Values without a field

A value does not need a visible field: an identifier, or a value computed or picked by a custom component, is read with values() and changed with set(name, value).

Props can be read when the form is built, but initial is read only once: a value that comes from the props and can change (the identifier of the record being edited) does not belong there. Add it in submit.toInput, called on submission: toInput: (values) => ({ ...values, id: this.recordId }), with @prop recordId: string; (a prop cannot be called id, a native property of HTML elements).

The form tag: bind

<form {edit.bind()}> submits the form when a button is clicked or Enter is pressed, without reloading the page. It turns off the browser's native validation (error bubbles), replaced by your rules and your messages. Without a <form>, call edit.submit() yourself.

When errors are shown

  • A rule or validate: after the user first leaves the field (by leaving it, or by changing a box, a list, a file), or after a submission attempt. Typing an incomplete address shows nothing while the user is in the field.
  • A server error (failures.fields): immediately, and until the user edits that field.
  • A rejected async check: as soon as it responds.

error('email') returns a single message, in this order of priority: server, field rule, validate, async check.

Submission

Submission is a store command. submit says which one, and toInput converts the form values into the command's input: remove what only serves the screen (a password confirmation), convert (an empty date to null), group. When the values already have the right shape, toInput: (values) => values is enough. This same input is what you find in save:done and save:failed.

What happens on submission:

  1. All fields are marked "touched": rule errors appear.
  2. If an error remains (rule, validate or rejected check), nothing is sent, and the first field in error is centred on screen and receives focus.
  3. If an async check is pending, the submission waits for it, then resumes by itself.
  4. Otherwise, the command is sent with toInput(values). submitting() is true until its outcome.
  5. On failure, the error is shown according to failures. On success, the form clears its errors and keeps its values.

Going to the first error

When a submission is blocked, the form centres the first field in error on screen, in page order, and gives it focus. Same when the server returns an error attached to a field (failures.fields). On a long form, the user immediately sees what to fix, can do it with the keyboard, and a screen reader announces the field.

  • For a group of radios or checkboxes, the first box of the group receives focus.
  • An error attached to the whole form (failures.form) moves nothing: it has no field.
  • Only fields bound with field(…) are found: a value without a visible field moves nothing.

Server errors: failures

Each failure reason declared by the command is attached to a field, or to the whole form:

KeyWhere the message is shownWhen it disappears
fieldsUnder the field, with error('email'). A reason can target several fields.When the user edits that field.
formFor the whole form, with formError().On the next submission.
  • Each declared reason appears exactly once, in fields or in form. A forgotten reason, a duplicate, one unknown to the contract, or an unknown field in fields does not compile.
  • form.error is optional. It is the message for an unexpected exception (a bug, an unreadable response). Without it, formError() shows "An unexpected error occurred.", so the user is never left without feedback. The exception also goes to onError.
  • A command with no declared failure reason does not need failures.

Async checks: checks

A check while the user types ("is this address free?") is a command of the submission store. The form triggers it and reads its outcome:

  • Only if the field's rules pass: no point asking the server about "abc".
  • After a pause in typing of delay milliseconds (300 by default): a single request for an address typed in one go.
  • Stale responses are ignored: if the field has changed since, the response for the old value does not count.
  • checking('email') is true during the pause and during the request.
  • Submission waits for pending checks to finish.
  • A check that fails (network down) does not block: the server remains the judge on submission, and the reason then comes back through failures.
  • Checks go through the same store as the submission: that is what lets the compiler type toInput and accept according to the chosen command.

Dynamic lists

For a number of rows that changes while the user types (phone numbers, addresses, invoice lines), declare an array of objects:

MemberRole
list('phones')The list, to declare in a field, after the form (phones = this.edit.list('phones')).
items()The rows, each with key, index, value, field(name) and error(name).
add(row)Adds a complete row, typed by the list.
remove(row | index)Removes a row.

Use item.key as the loop key (for (const item of phones.items(); key item.key)). It does not change when another row is removed: input and errors stay on the right row. The index, on the other hand, shifts.

What the compiler checks

  • field targets an existing field that is not a list; a radio's value belongs to the declared union.
  • Each rule receives the right type: age receives number | null, newsletter a boolean.
  • submit.toInput does produce the command's input.
  • failures splits exactly the command's reasons between fields and form, and fields only targets existing fields.
  • A check targets a store command, and toInput and accept are typed by it.
  • list(…).add(…) requires a complete row.

Limitations

  • Nested objects are only supported as lists of rows. For a sub-object (an address), flatten its fields (street, city), then rebuild the object in submit.toInput.
  • Server errors (failures.fields) target top-level fields, not a row of a list.
  • Async checks go through the submission store.
  • A file field cannot be pre-filled.
