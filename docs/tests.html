Tester

Chaque brique se teste à son niveau : le store sans DOM, l'adapter seul, le composant avec un faux store, l'app entière avec un router en mémoire. Et les garanties de typage ont leurs propres tests.

La configuration

Les tests tournent sous Vitest avec happy-dom, un DOM simulé. Ils vivent à côté du code qu'ils testent (@core/counter/store.test.ts à côté de @core/counter/store.ts, @components/counter/index.test.ts à côté de l'écran, index.super).

Un test reste un fichier .ts, même pour un composant écrit en .super. Vitest reprend les plugins de vite.config.ts : le plugin Super y compile les .super comme en dev, et import { CounterControls } from './counter-controls' trouve counter-controls.super.

Node 25 et plus Node expose un localStorage natif qui masque celui de happy-dom (« localStorage.clear is not a function »). L'option execArgv: ['--no-experimental-webstorage'] le désactive dans les workers de test.

Tester un store

Un store se teste sans DOM, avec un adapter en mémoire. XStore.create(deps) renvoie le handle, comme dans main.ts ; await send(…) attend la fin de la commande, puis on vérifie l'état, les sélecteurs et les événements.

  • store.selectors.x(…) lit l'état courant par les sélecteurs du contrat ; store.state() donne l'état brut, figé.
  • store.pending(…) dit si une commande est en cours : toutes (pending()), une commande (pending('load')), ou une commande pour un body (pending('increment', { id: 'cafes' })).
  • record(store, événement) enregistre les payloads, y compris ceux du cycle de vie ('increment:done') : calls (tous), last (le dernier), stop() (arrête l'écoute).

Tester un adapter

L'adapter localStorage se teste contre le localStorage de happy-dom, ou contre n'importe quel objet compatible grâce à son option storage. Rien de Super ici : c'est du user-land.

Tester un composant seul

Un composant de présentation, sans store, se monte avec ses props ; ses événements s'écoutent par on, typé par ses emits. Le composant est un .super, le test un .ts qui l'importe sans extension.

mount

mount(Classe, options) prend la classe exportée par le .super (pas un élément déjà créé), le monte dans document.body sous une application de test, attend le premier rendu et retourne :

OptionRôle
propsLes props du composant, typées par sa classe.
storesLes stores à fournir (vrais ou faux), trouvés par le nom de leur contrat comme avec createApp.
routerUn router, en général createRouter(Router, { mode: 'memory', initialPath }). Un écran monté seul y lit sa route : initialPath: '/counters/cafes' lui donne id === 'cafes'.
onDes écouteurs pour les événements du composant, typés par ses emits.
onErrorReçoit les erreurs des composants montés, comme createApp({ onError }). Voir Tester les erreurs.
RetourRôle
containerLe conteneur, à passer à within() de testing-library.
elementL'instance montée, typée par sa classe.

flush

Les notifications de store et les rendus sont regroupés à la fin de la tâche. Après une action qui change un store sans passer par testing-library (un emit de faux store, un send sur un vrai), await flush() laisse passer les rendus en attente. Les findBy* de testing-library attendent d'eux-mêmes.

Tester un écran avec un faux store

fakeStore('nom', { state, commands? }) crée un store pour le contrat de ce nom, sans implémentation. L'écran le trouve comme il trouverait le vrai, par @contract counter : c'est ce que permet la règle « un composant ne connaît que le contrat ». L'état donné est typé par le contrat, et les sélecteurs du contrat le lisent normalement.

Membre du faux storeRôle
sentLes commandes reçues, dans l'ordre : { name, args }.
setState(patch)Change l'état, comme le ferait le store.
emit(nom, payload)Émet un événement du contrat, ou l'issue d'une commande ('decrement:failed'), comme le feraient le store et Super.
selectors, state(), on…Le reste du handle d'un store, comme un vrai.
commands (option)Des implémentations pour certaines commandes. Les autres sont enregistrées et se terminent sans publier d'issue : c'est au test d'émettre :done ou :failed, avec des valeurs conformes au contrat.

FakeCommands<'counter'> type ces implémentations par le nom du contrat. Chacune reçoit le body, puis { fail }, et retourne le résultat déclaré par l'Outcome : Super publie alors l'issue comme pour un vrai store.

Tester l'application entière

L'app s'assemble comme dans main.ts : vrais stores, adapters sans latence, router en mémoire. mount reçoit la coquille, AppShell, qui affiche l'écran de la route.

Tests de types : les fichiers *.test-d.ts

Une partie de ce que promet Super, ce sont des erreurs de compilation : une route inconnue, un paramètre manquant, un écran aux mauvaises props. Un test Vitest ne peut pas constater qu'une ligne est refusée par le compilateur. Les fichiers *.test-d.ts servent à ça.

  • Le « d » vient de .d.ts : ces fichiers testent le typage, pas le comportement. C'est la convention de Vitest.
  • Ils ne sont jamais exécutés. C'est npm run typecheck (super-tsc, qui lance tsc) qui les compile.
  • Chaque // @ts-expect-error affirme « cette ligne doit être refusée ». Si un changement la rend acceptable, la compilation échoue (« Unused '@ts-expect-error' directive »).
  • npm run check lance le typecheck puis les tests : ces fichiers sont vérifiés à chaque passage.

Le template d'un .super n'a pas besoin de tests de types : npm run typecheck le vérifie directement (props d'un enfant, attributs, événements, interpolations). Les types qu'un test voit d'un composant .super (ses props pour mount, ses emits pour on) viennent du TS virtuel, par la déclaration que super-tsc écrit dans .super/types/ (voir Outillage).
