Démarrer

Installer le dépôt, lancer l'exemple, puis écrire une fonctionnalité complète de bout en bout.

Installer

Super n'est pas encore publié sur npm. On travaille dans le dépôt, qui contient les paquets et une app d'exemple.

Les paquets @super-ts/core, @super-ts/dom, @super-ts/testing, @super-ts/ui et @super-ts/vite sont résolus par des alias déclarés dans les tsconfig.json et vite.config.ts. Dans l'app, les dossiers Super s'importent eux aussi par alias, depuis n'importe quel fichier : '@core/counter/contract', '@components/app-shell' (voir Architecture).

Les composants s'écrivent dans des fichiers .super : le plugin Vite les compile, et npm run typecheck les vérifie. Pour avoir les erreurs et la complétion dans ton éditeur, branche le serveur de langage des .super (voir Outillage).

L'app d'exemple

examples/demo est une seule app, qui regroupe les exemples de Super. npm run dev la lance sur http://localhost:5173 ; sa page d'accueil mène à chaque exemple :

  • Compteurs (/counters) : une liste de compteurs, une page de détail par compteur avec des boutons + et −, une persistance dans le localStorage.
  • Formulaire de profil (/profile) : tous les types de champs, des règles, une vérification asynchrone, une liste dynamique, et un serveur simulé (latence, adresse prise, panne réseau).
  • Boutique (/shop) : un store qui dépend d'un autre, un événement écrit à la main, un dialogue de confirmation, un guard.
  • Erreurs (/errors) : chaque niveau de gestion des erreurs, provoqué pour de vrai, avec le journal de onError.
  • Widget (/widget) : une seconde application dans la page, un mounted avec nettoyage par signal, un raccourci clavier.
  • Kit (/kit) : un sommaire et une page par famille de composants de @super-ts/ui, branchés sur les stores de la démo, dont une table branchée sur une vraie API et une page de thème.

Presque tous les extraits de cette doc en viennent : quand un extrait est tiré de l'exemple, un lien mène au fichier complet. La page Exemples détaille ce que montre chaque fichier.

Ta première fonctionnalité : un bouton de thème

On va ajouter un bouton qui bascule entre mode clair et mode sombre. C'est volontairement simple, mais ça passe par toutes les étapes : contrat, store, composant, branchement et test.

Étape 1 : le contrat

Le contrat décrit ce que le store sait faire, sans dire comment. C'est une classe, dans son propre dossier sous src/@core/, qui se nomme dans son constructeur : c'est par ce nom qu'on la demandera.

Le plugin Vite repère le contrat et l'inscrit dans src/@core/contracts.d.ts, un fichier généré (à committer, jamais à écrire à la main). C'est ce qui fait connaître 'theme' au compilateur partout dans l'app. Voir Contrats et Sélecteurs.

Étape 2 : le store

Le store implémente le contrat : un état de départ, et une méthode par commande.

implements Commands<ThemeStore> fait vérifier les méthodes par le compilateur : une commande oubliée, un paramètre différent du contrat ou une méthode publique hors contrat ne compilent pas. Ce constructeur ne prend rien : le store se crée avec ThemeStore.create(). Voir Stores.

Étape 3 : le composant

Le composant demande le store par le nom de son contrat, lit un sélecteur et envoie la commande au clic. Il est réutilisable : il va dans src/@components/shared/, dans un fichier .super.

render() ne renvoie rien : le bouton est écrit comme une instruction, on:click pose l'écouteur et {…} affiche une valeur (voir Templates). Le composant n'importe rien de src/@core/ : @contract theme; suffit, et le compilateur connaît les sélecteurs et les commandes du contrat. Voir Composants et Lire un store.

Étape 4 : le branchement

La racine de composition, main.ts, crée les stores et les fournit à l'app. Le composant peut alors être utilisé n'importe où sous la racine, par exemple dans l'en-tête de la coquille : <ThemeToggle />, après import { ThemeToggle } from '@components/shared/theme-toggle'.

L'app retrouve chaque store par le nom de son contrat : un composant qui demande 'theme' reçoit celui-ci. Voir Brancher l'application.

Étape 5 : le test

Le test reste un .ts : il importe le composant .super sans extension et le monte avec mount. Un test peut importer un store : le plugin ne vérifie pas les fichiers *.test.ts. Pour tester le composant seul, remplace le vrai store par fakeStore('theme', { state: { mode: 'dark' } }). Voir Tester.

Et ensuite

  • Persister le thème : ajoute un port ThemeStorage et un adapter localStorage (voir Ports et adapters).
  • Comprendre le trajet complet d'une action : Commandes et événements.
  • Ajouter des pages : Router.
