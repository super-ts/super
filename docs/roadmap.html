Roadmap and open questions

What Super lacks for a real app, the follow-ups put aside, and the questions still under discussion. None of this is decided: it is the list the next piece of work will start from. What Super does not do well today is in Limitations.

The most needed work

In order of importance: these are the most visible gaps compared with other frameworks.

1. Lazy loading of screens, and loaders

Today, the whole app goes into a single bundle: the router imports all its screens, none is loaded on demand. An app that grows pays for it on every first load.

  • Screens loaded on navigation: counter: () => import('@components/counter') in .screens(…), with a loading state and a loading error caught like a screen error.
  • Loaders: a screen declares the data to load before it is displayed (a store command), so as not to show an empty screen and then fill it.
  • Preloading: a screen's code and data loaded on hover or focus of a link leading to it.

2. A server data layer on top of commands

A store's commands talk to the server through its ports, and their outcome comes back through name:done and name:failed. Everything else is written by hand in each store, even though the needs are always the same (this is what TanStack Query does):

  • deduplicating two identical loads started at the same time;
  • serving the already known value and revalidating it in the background;
  • retrying a load that fails;
  • invalidating what a write makes stale;
  • applying a write right away (optimistic update), and rolling back if it fails;
  • choosing what to do with two concurrent commands (keep the latest, queue them).

3. A command log for development

Each command already goes through an EventTarget, with its outcome. A development panel could list them: the command, what it received, its duration, its result or failure reason, and the store's state before and after. It is little code for a lot of debugging help, and a first building block for devtools.

Follow-ups set aside

Router

  • A shortcut to change a single query key (today, navigate with ...query).
  • Params and a query described by a Zod or Valibot schema (Standard Schema), instead of Super's descriptions.
  • Redirecting to the '*' screen when a param is invalid ({ invalid: 'not-found' } per param).
  • Restoring scroll and placing focus after a navigation.
  • The rest of the <head> per screen (<meta>, description): the title already exists, through @title.
  • A value forgotten in oneOf is not flagged at compile time.

UI kit

  • A few texts cannot be changed through a prop yet: "Checking…", "Loading…" in Table and Combobox, the pagination, "Details".
  • Sorting a table on several columns.
  • The native popover API when the browser has it, with the current fallback otherwise.
  • fieldOf only works in the render of the component that declares the form.

Publication

  • Publish the @super-ts/* packages on npm, once the API is stable: today, they are resolved by alias from packages/*/src.
  • Publish the Tree-sitter grammar and the Zed extension. This needs a public repository for each, a licence, English texts, a language server published on npm (as a single file) that the extension installs, and a request to add it to Zed's extension registry.

Open questions

  1. Dependencies between contracts. Declaring that a store listens to another store, to make the graph readable and detect cycles.
  2. Global overlays (toast, confirmation requested from any screen): stay in user-land with a dedicated store driving a component mounted in the shell, or become a Super concept.
  3. Leave guard. Preventing leaving a screen (unsaved changes), carried by the screen rather than by the route.
