Limites

Super est un draft. Voici ce qu'il fait mal ou vérifie mal aujourd'hui. Ce qu'il ne fait pas encore est dans Chantiers et questions ouvertes.

Limites connues

Typage

  • Les paramètres d'une méthode de store s'annotent à la main : TypeScript n'infère pas les paramètres d'une méthode de classe. implements Commands<…> vérifie seulement qu'ils sont égaux à ceux du contrat.
  • this.fail accepte toutes les raisons déclarées par le contrat, pas seulement celles de la commande en cours.

Plugin d'architecture

  • Il lit le code comme du texte : il voit les imports nommés (y compris renommés), pas un import * as dom from '@super-ts/dom' hors des dossiers imposés.
  • Il reconnaît un contrat à sa déclaration export class X extends SuperContract, suivie de super({ name: '…' }) avec un nom écrit en toutes lettres.
  • Rien n'empêche un composant d'importer un store exporté par un module user-land.

Composants

  • Un composant ne rattrape pas l'erreur de son propre constructeur : seul le renderError d'un ancêtre le peut.
  • @selector n'accepte que la valeur d'un sélecteur, telle quelle : une condition ou un calcul va dans render, ou dans un nouveau sélecteur du contrat.
  • Une prop ou un champ ne peut pas porter le nom d'une propriété des éléments HTML (id, title, hidden, slot…) : c'est une erreur de type. Un paramètre de route id se lit donc dans un champ nommé autrement (counterId = this.router.current.params.id;), et une prop title devient heading. C'est aussi pour ça que le contenu écrit entre les balises remplit une prop content et non children, propriété native des éléments.
  • page est un nom réservé dans un composant : c'est this.page, qui porte le titre de la page.
  • Un titre suivi (@title = () => …) n'est recalculé qu'au rendu du composant qui le pose. Ce qu'il lit est suivi comme les lectures de render : une valeur lue par le titre seul re-rend donc tout le composant quand elle change, et une valeur que Super ne suit pas (un champ ordinaire, l'heure) ne le met à jour qu'au prochain rendu.
  • Un composant enfant s'écrit par sa classe (<CounterScreen />) : une balise <counter-screen> écrite par son tag n'est pas supportée.
  • Le remplacement à chaud recharge la page quand un composant change de champs, ou a des membres #privés, méthodes comprises (voir Remplacement à chaud).

Fichiers .super

La syntaxe est en version 0 (packages/lang/SPEC.md). Ses limites assumées :

  • Pas de directive sur un composant ({form.field('x')} dans sa balise) : un composant reçoit des props, des on:, des enfants et des emplacements nommés.
  • Sur une balise native, on: n'accepte que les événements de cette balise : écouter sur un <div> un événement personnalisé remonté d'un enfant n'est pas permis.
  • Une signature d'appel générique dans un type littéral ({ <T>(x: T): T }) est prise pour un élément : sors-la dans un type ou une interface d'un fichier .ts.
  • @prop, @emit et les déclarations de préparation (@contract, @selector, @state, @form, @ref, @on) sont du TS valide (des champs et des méthodes décorés), mais @tag = … et @title = … ne le sont pas : seuls nos outils les connaissent (le formateur des .super, la grammaire Tree-sitter, le serveur de langage). Un éditeur sans eux les affiche en erreur.
  • Le nom d'événement de @on est une chaîne écrite telle quelle : pas de gabarit (@on('counter', `${change}:done`)) ni de boucle sur une liste d'événements. Écouter plusieurs événements demande une méthode par événement, qui peuvent appeler une même méthode privée (l'écran du compteur a onIncremented, onDecremented, onReset… qui appellent #done).
  • Pas de type sur @contract, @selector, @state ni @form : il vient de la valeur. Pour l'élargir, on écrit as dans la valeur (@state local = { message: null as string | null };). @ref est l'inverse : un type, sans valeur.
  • L'ancienne forme (cart = this.contract('cart');, this.selector(…), this.state(…), this.form(…), this.ref<T>(), .on(…) dans le constructeur) est refusée dans un .super. Un composant écrit en .ts garde ces méthodes, qui restent la seule écriture possible hors des .super.

Et côté outillage (voir Outillage) :

  • Biome ne lit pas les .super : leur TS est formaté par Biome à travers le formateur des .super, mais l'ordre de leurs imports n'est pas contrôlé.
  • Dans Zed, l'extension des .super (editors/zed) s'installe en extension de développement, et sa grammaire (editors/tree-sitter-super) est compilée depuis un dépôt git local, désigné par un chemin absolu dans extension.toml tant que la grammaire n'est pas publiée.
  • Le serveur de langage tourne sur TypeScript 6, parce que Volar ne supporte pas encore TypeScript 7. La vérification en ligne de commande (npm run typecheck), elle, utilise le TypeScript 7 du dépôt.

Rendu

  • Le suivi des sélecteurs s'arrête au premier niveau de l'état : un sélecteur qui lit une liste est recalculé dès qu'un élément change. Un sélecteur qui construit de gros objets par élément paie alors un parcours complet de son résultat.
  • Le cache des sélecteurs garde un résultat par jeu d'arguments primitifs (un sku, un id) pendant toute la vie du store.
  • Le gel de l'état ne descend que dans les tableaux et les objets simples : le contenu d'une Map, d'un Set ou d'une instance reste modifiable, et une telle mutation échappe au suivi.
  • Les erreurs du code que Super ne voit pas passer (setTimeout, écouteur posé à la main sur window) partent seulement dans la console.

Router

  • Les guards sont synchrones, et il n'y a pas de guard de sortie (« modifications non enregistrées »).
  • Pas de chemin de base (application servie sous /app/).
  • Les types décrits se limitent à String, Number, Boolean, { oneOf } et leurs listes : pas de date, d'objet, ni de conversion sur mesure.
  • Une liste { oneOf } qui oublie une valeur de l'union compile : seule une valeur en trop est refusée. La valeur oubliée n'est jamais valide dans l'URL.
  • Pas de raccourci pour changer une seule clé de query : une navigation redonne toute la query ({ ...valeursActuelles, sort: 'value' }).
  • Un seul router typé par app : le plugin refuse deux déclarations defineRouter.

Kit d'interface

  • Pas de composant de mise en page (Stack, Grid, Card) : l'agencement reste le CSS de l'app.
  • fieldOf s'écrit dans le rendu du composant qui possède le formulaire : un champ du kit placé dans un sous-composant ne suivrait plus le formulaire.
  • Les éléments flottants (menu, popover, info-bulle, liste du combobox) n'utilisent pas l'API popover du navigateur : un ancêtre en overflow: hidden peut les couper.
  • Quelques textes en français n'ont pas encore de prop pour les changer (« Vérification… », la pagination de la table). Voir Limites du kit.

Distribution

  • Les paquets ne sont pas publiés : ils sont résolus par alias depuis packages/*/src.

Ce qui manque encore, les suites mises de côté et les questions en discussion sont dans Chantiers et questions ouvertes.
