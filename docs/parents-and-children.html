Parents and children

Props go down, events go up. A parent never drives a child by calling its methods: it passes it props, and the child answers with events.

Using a child component

In a template, a child is placed as a tag, named after its class: a tag that starts with a capital letter is a component, imported like any class (import { CounterControls } from './counter-controls').

  • The attributes are the props. The compiler checks them against the child's @props: a missing required prop, an extra prop or a wrongly typed value is an error. A fixed value is written in quotes (question="Empty the cart?", a string), a computed value in braces.
  • on:name wires a child event to a parent function. The name and the payload are checked against the child's @emits.
  • The tag is the equivalent of CounterControls.create({ count, … }, { on: { increment, … } }), the call used outside a template (see Creating an element outside a template).
  • The child element is created once per position, then its props are updated on each parent render. It keeps its local state. If it receives equal props (compared key by key), it does not re-render.
  • A component can also receive elements between its tags, if it declares them (see Composing: children).

Declaring props

A prop is declared in the class body with @prop, with its type, and is read through this.name. The tag, the props and the events are written in the same place, without a generic (the details of each declaration are in Components: declarations):

A prop takes one of these three forms:

  • A required prop missing from the parent's tag is a compile error.
  • An optional prop (?) is undefined when the parent does not pass it. ? and a default value do not go together: it is an error.
  • The default value makes the prop optional; it is computed once per instance (a default [] is not shared between two elements).
  • A component whose props are all optional is placed without attributes (<RouterOutlet />).
  • this.counterId is read-only, and always up to date: a prop change re-renders the child. this.props still exists (all the props, read-only), but you write this.name.
  • Props are readable from construction (to initialise a @state, for example). A copy made at that moment does not follow later changes: read this.name in render or in a @selector function for an always up-to-date value.

Names already taken by HTML elements

A component is an HTML element: this.id, this.title, this.hidden or this.slot already exist. A prop therefore cannot have one of these names, and the compiler says so:

An id route parameter is likewise read into a field with another name: counterId = this.router.current.params.id;. The name page is reserved too (it is this.page). For the same reason, the content written between the tags fills a content prop (children is native), see Composing: children.

emit in the child, on in the parent

Each side uses its own vocabulary. on: is the prefix used on the parent side to listen; the child never sees it.

Child side (CounterControls)Parent side (CounterScreen)
Declare@emit increment: void; and @emit decrement: void;, in the class bodynothing
Actthis.emit('increment'): "I announce that someone clicked"on:increment={…}: "when you announce that, I do this"

The child speaks, the parent listens. The child does not know who listens to it, or even whether anyone does. It is the same principle as an HTML <button>: it emits click, and it is the page that writes on:click={…}, with the same prefix. Elsewhere, it is $emit / @increment in Vue, dispatch / on:increment in Svelte.

Declaring a component's events

@emit name: T; declares an event and the type of what it carries (void if it carries nothing). It has no value: @emit closed: void = … is an error. A void event is emitted without an argument. The compiler rejects an unknown name, a wrongly typed payload, or a forgotten payload.

The full journey of a click on "+"

  1. CounterControls emits increment.
  2. CounterScreen receives the event and calls this.run('increment').
  3. run sends this.counter.send('increment', { id: 'coffees' }) to the store.
  4. The store saves and updates its state; Super publishes increment:done.
  5. The screen re-renders; the new value flows back down into CounterControls through the count prop.

CounterControls knows neither the store, nor the id, nor the command: it stays reusable. It is the screen that decides what "increment" means.

A dialog: the parent renders it, it answers with an event

In the Shop example: shared/confirm-dialog.super, shop/index.super. "Empty the cart?" is rendered by the parent and answers with an event.

Even a confirmation dialog follows this rule. The parent opens it by rendering it, with its question as a prop; the dialog emits the answer. Mounted, it is open: no nullable prop that would mean "closed". Nobody waits for anything, there is no await.

  1. Click on "Empty the cart": the parent puts dialog: 'confirm-clear' in its local state.
  2. The parent re-renders; the condition is true, the dialog is mounted with its question and shows.
  3. Click on "Confirm": the dialog emits answered { confirmed: true }.
  4. onClearAnswered sets dialog back to null (the dialog is unmounted) and sends the command.

Opening and closing a dialog means changing a value in the parent's state. With several dialogs, keep a single field (dialog: 'confirm-clear' | 'confirm-delete' | null) and one condition per dialog: each has its question and its handler, and two modals cannot be open at the same time. The same pattern works for a drawer or a menu.

A handler passed to a child: an arrow field

onClearAnswered is a field holding an arrow function, not a method. An arrow function keeps the component's this; a method passed as is (on:answered={this.onAnswered} with onAnswered() { … }) would lose it, and this.local would be undefined at call time. Same rule for an action passed to on:click without a wrapping function.

Lists

For a list of children, use a for loop with a key, written after key: a moved element keeps its DOM and its local state. Without a key, rendering follows the position (see Lists).

Composing: children

A card, a modal, tabs: layout components whose content comes from the parent. The component declares what it accepts through props of type Children, and places them where it wants:

  • content receives the content written between the tags. It is a prop like any other: @prop content: Children;, read through this.content. It is not called children because this.children is the native property of HTML elements (the list of their child elements).
  • A named slot is another prop of type Children, here actions, read through this.actions. When optional, it is written with ? (@prop footer?: Children;); a component declares as many as it wants.

The parent fills content with the elements written between the tags, and actions with a named slot, or with a method:

  • The children belong to the parent: the click on "Reset to zero" calls a parent method, and this.count is read by the parent. The children follow its render; the card keeps them when it re-renders on its own.
  • The compiler checks the contract: children for a component that does not declare content, missing required children, a slot that is not a prop of the component are errors.
  • The full syntax is in Templates: children and named slots. The Composition example in the demo app shows both ways side by side.

What does not exist, on purpose

  • No reference to a child to call its methods: a child exposes no API. In a template, <CounterControls … /> mounts the child, it does not give you an instance to keep.
  • No callback prop to pass information up: nothing technically prevents it, but you use an event, declared with @emit and typed. The child stays decoupled, and the test can listen to the event with mount(…, { on }).
  • No access from a child to its parent's stores through props: a child that needs a store declares @contract name; itself.
  • No hand-written tag: <counter-controls> in raw HTML is not supported. A child always goes through its class, <CounterControls … /> (or create outside a template).
