Composants : une classe et son render

Un composant est un custom element typé, écrit comme une classe qui étend SuperElement. Ses déclarations et ses champs préparent l'instance une fois ; render() affiche à chaque rendu.

Définir un composant

Un composant vit dans un fichier .super sous src/@components/, par exemple src/@components/shop/index.super. C'est un module TypeScript ordinaire, à une différence près : dans ses méthodes, le HTML s'écrit directement, en éléments placés comme des instructions (voir Templates). Un import sans extension le trouve : @components/shop désigne shop/index.super.

Une classe de composant se compose de quatre éléments :

ÉlémentRôle
extends SuperElementLa classe de base, sans générique dans un .super : le compilateur tire les types du composant de ses déclarations.
Les déclarations@tag (le nom du custom element, obligatoire, avec un tiret), puis selon les besoins @prop pour les props reçues, @emit pour les événements émis vers le parent, @title pour le titre de la page. Voir Déclarations du composant. Un écran ne reçoit pas de props du router : il lit sa route par this.router.current, typé d'après sa route sans rien déclarer (voir L'écran et sa route).
La préparationLes contrats (@contract), les valeurs lues (@selector), l'état local (@state), le formulaire (@form), les références (@ref), les écouteurs (@on sur une méthode), et les actions en champs. Voir Préparer.
render()Le HTML du composant, obligatoire, écrit en éléments dans le corps de la méthode, sans return. Une méthode facultative renderError(error) le remplace si le composant ou un descendant plante (voir Gérer les erreurs).

Le composant n'importe rien de @core/, sauf des types : il parle aux stores par @contract nom; (et au router par this.router), et le plugin Vite le vérifie.

Déclarations du composant

Ce qui décrit le composant vu de l'extérieur s'écrit en tête du corps de sa classe : son tag, ses props, ses événements, et le titre de la page tant qu'il est monté. Pas de générique sur SuperElement, pas de type Props au-dessus de la classe : le compilateur tire les types du composant de ces lignes, et les vérifie à chaque balise qui l'utilise. Ce que le composant prépare une fois (contrats, lectures, état, formulaire, références, écouteurs) se déclare de la même façon : voir Préparer.

DéclarationSens
@tag = 'x-y';Le nom du custom element. Obligatoire (sauf classe abstract), une chaîne en minuscules avec un tiret. Unique dans l'app : un second composant avec le même tag lève une erreur à son premier create.
@prop nom: T;Une prop obligatoire, lue par this.nom.
@prop nom?: T;Une prop facultative (T | undefined).
@prop nom: T = valeur;Une prop facultative avec une valeur par défaut, calculée une fois par instance.
@emit nom: T;Un événement, émis par this.emit('nom', payload) (void s'il ne transporte rien).
@title = …;Le titre de la page tant que le composant est monté : une chaîne, ou une fonction suivie. Voir Le titre de la page.

Les props

Une prop se lit par son nom, this.question, partout dans la classe et dès les champs. La lecture donne toujours la valeur courante, et un changement de prop re-rend le composant. this.props existe toujours (toutes les props, en lecture seule), mais on écrit this.nom. Le détail des trois formes est dans Parents et enfants.

  • Le contenu écrit entre les balises remplit la prop content. Elle se déclare comme les autres (@prop content: Children;) et se lit par this.content. Voir Composer : des enfants.
  • Les noms des propriétés natives sont refusés. Le composant est un élément du DOM : une prop ne peut pas s'appeler id, title, hidden, slot… L'erreur de type le dit : « « title » est déjà une propriété des éléments HTML : choisis un autre nom ». Dans la démo, title est devenu heading (KitPage, Card) et id est devenu counterId (CounterListItem). Un paramètre de route id se lit de même dans un champ nommé autrement : counterId = this.router.current.params.id;.
  • page est réservé : c'est this.page, qui porte le titre de la page.

Les événements

@emit nom: T; déclare un événement et ce qu'il transporte (void s'il ne transporte rien). Le composant l'émet par this.emit('nom', payload), le parent l'écoute par on:nom={…} sur la balise. Voir emit chez l'enfant, on chez le parent.

Ce que le compilateur refuse

  • Un tag manquant, écrit static tag = … (une correction rapide le réécrit en @tag), ou qui n'est pas une chaîne en minuscules avec un tiret.
  • Un générique écrit à la main : « Dans un .super, les props et les événements se déclarent dans la classe : @prop nom: Type; et @emit nom: Type; ».
  • Une déclaration en double, une prop sans type, un ? avec une valeur par défaut, un @emit avec une valeur, une déclaration hors d'un composant.

Un composant écrit dans un fichier .ts (RouterOutlet, les composants de @super-ts/ui, les tests du framework) n'a pas ces déclarations : il garde static tag et le générique, et lit ses props par this.props. Il prépare aussi par des méthodes (this.contract(…), this.selector(…), this.state(…), this.form(…), this.ref<T>(), .on(…) dans le constructeur).

Préparer : stores, lectures, état, formulaire, références, écouteurs

Ce que le composant prépare une fois, à sa construction, se déclare aussi dans le corps de sa classe : les contrats qu'il lit, ses valeurs lues, son état local, son formulaire, ses références et ses écouteurs. La plupart des composants n'ont donc plus de constructeur.

Dans un .superAvant, et toujours dans un .tsSe lit par
@contract cart;cart = this.contract('cart');this.cart.selectors.x(), this.cart.send(…)
@contract shop = 'catalog';shop = this.contract('catalog');idem, sous le nom this.shop
@selector lines = this.cart.selectors.lines;lines = this.selector(this.cart.selectors.lines);this.lines.value
@selector count = () => …;count = this.selector(() => …);this.count.value
@state local = { … };local = this.state({ … });this.local.get(), this.local.set(…)
@form edit = { … };edit = this.form({ … });this.edit.bind(), this.edit.field('name')…
@ref input: HTMLInputElement;input = this.ref<HTMLInputElement>();ref={this.input}, puis this.input.value
@on('profile', 'save:done') onSaved(p) { … }this.profile.on('save:done', (p) => …) dans le constructeurla méthode, appelée à chaque événement tant que le composant est monté

Seule la déclaration change : la lecture reste la même (this.lines.value, this.local.get(), this.edit.bind(), this.input.value, this.cart.send(…)).

  • Pas de type sur @contract, @selector, @state, @form : il vient de la valeur. Pour l'élargir, on écrit as dans la valeur (null as string | null). @ref, à l'inverse, déclare le type de son élément et n'a pas de valeur.
  • La valeur de @contract x = '…' est une chaîne écrite telle quelle, le nom du contrat : @contract log = 'error-log'; lit le contrat error-log sous le nom this.log.
  • L'ordre compte, comme pour des champs : un @selector ou un @form qui lit this.cart vient après @contract cart.

Les écouteurs : @on

Un écouteur se déclare sur une méthode : @on('contrat', 'événement') au-dessus d'elle, et la méthode est appelée à chaque événement tant que le composant est monté. Plus besoin de constructeur pour poser un écouteur.

  • @on n'exige pas de @contract : il ouvre lui-même l'accès au contrat. Un composant qui ne fait qu'écouter profile n'a pas besoin de @contract profile;.
  • Le paramètre de la méthode est typé par l'événement : pour save:done, { input, result } ; pour save:failed, { input, reason }. Pas besoin de l'annoter.
  • @on('router', 'navigated') écoute le router, comme this.router.on('navigated', …).
  • Le nom de l'événement est une chaîne écrite telle quelle, sans gabarit (`${change}:done`) : une méthode par événement. Dans la démo, CounterScreen déclare onIncremented, onDecremented, onReset, onIncrementFailed…, qui appellent toutes #done ou #failed (voir l'extrait en tête de page).

Pourquoi @form et pas un composant <Form>

Un formulaire est de l'état du composant : ses valeurs, ses erreurs, ses vérifications, sa soumission, lus partout dans le template (this.edit.field('name'), this.edit.values(), le bouton « Enregistrement… »). La balise, elle, existe déjà : c'est le <form> natif, relié par <form {this.edit.bind()}>. Un <Form> cacherait cet état et ferait perdre le typage des champs. <Table>, lui, est un composant parce qu'il ne fait qu'afficher.

Les erreurs de préparation

  • Un contrat déclaré deux fois : « Le contrat cart est déjà déclaré par @contract cart ».
  • @contract router : « Le router se lit par this.router, sans @contract ».
  • Un type sur @contract, @selector, @state ou @form : « Pas de type sur @selector : il vient de la valeur ».
  • Les anciennes formes, dans un .super : local = this.state({ … }) donne « Dans un .super, this.state(…) se déclare par @state : @state local = …; », avec une correction rapide qui réécrit la ligne (de même pour this.contract, this.selector, this.form et this.ref).
  • Un this.x.on(…) dans le constructeur : « Dans un .super, un écouteur se déclare sur une méthode : @on('x', 'événement') onEvent(payload) { … } ». Pas de correction automatique : la méthode est à écrire.

Hors d'un composant, rien ne change : un store qui écoute un autre store garde cart.on('add:done', …) dans son constructeur, main.ts garde cart.subscribe(…), et le handle d'un store, dans un test, garde counter.on('increment:done', …).

Dans l'éditeur

Un @ tapé dans le corps d'un composant propose tag, title, prop, emit, contract, selector, state, form, ref et on, avec un gabarit à compléter ; @t ne propose plus que tag et title, et un @tag ou un @title déjà écrit n'est plus proposé. Le survol de chaque déclaration affiche sa documentation. Après @contract , l'éditeur propose les contrats de l'app que le composant ne déclare pas encore. Dans @contract x = '…' et @on('…', '…'), l'éditeur complète les noms des contrats de l'app, puis ceux des événements du contrat choisi. @prop et @emit sont du TypeScript valide (des champs décorés) ; @tag = … et @title = … ne le sont pas, mais le formateur et la grammaire Tree-sitter de Zed les connaissent (voir Outillage).

La préparation est bloquée pendant le rendu. Dans un .super, elle ne s'écrit que par des déclarations, en dehors de render. Les méthodes qu'elles appellent (contract, state, selector, ref et form, écrites telles quelles dans un .ts) lèvent une erreur si elles sont appelées pendant render : on ne peut pas résoudre un store ou créer un état à chaque rendu. L'écouteur on d'un contrat est permis dans un gestionnaire ou dans mounted, mais lève une erreur pendant un rendu ; this.page.title de même (voir Le titre de la page). L'erreur passe par le renderError du composant, comme toute erreur de rendu.

Les props sont lisibles dès les déclarations et les champs : Super les dépose avant de construire l'instance. Une valeur copiée à ce moment-là (@state local = { draft: this.text };, les valeurs initiales d'un formulaire d'édition) ne suit pas les changements suivants : pour une valeur toujours à jour, lis la prop (this.text) dans render, dans la fonction d'un selector ou dans un écouteur, comme les méthodes @on de CounterScreen, qui appellent this.counterId() quand l'événement arrive et lisent donc la route du moment.

Où mettre quoi : préparation ou render ?

La question à se poser : est-ce que ça doit exister une seule fois pour l'instance, ou est-ce que ça se recalcule à partir des valeurs du moment ?

LigneOùPourquoi
@tag, @prop, @emitdéclarationCe que le composant est vu de l'extérieur : en tête de la classe, une fois pour toutes.
@title = () => …déclarationLe titre se pose une fois ; la fonction, elle, est recalculée après chaque rendu.
@contract counter;déclarationRésoudre un store est un branchement, fait une fois. Pendant un rendu, il lève une erreur.
@selector count = …;déclarationDéclare ce que le composant lit. La valeur, elle, est recalculée à chaque lecture de .value.
@state local = { message: null };déclarationL'état local doit survivre aux rendus. Recréé à chaque rendu, il repartirait de zéro.
@form edit = { … };, @ref input: HTMLInputElement;déclarationUn formulaire et une référence sont de l'état de l'instance : créés une fois, lus à chaque rendu.
@on('counter', 'increment:done') onIncremented(…) { … }méthode décoréeUn écouteur se pose une fois, et vit tant que le composant est monté. Pas de constructeur.
run = (command) => …champ fléchéUne action stable, créée une fois, avec this lié.
this.count.valuerenderLes valeurs changent : on les lit au moment du rendu.
if (label === null)renderUne décision d'affichage dépend de la valeur actuelle. La branche émet ses éléments, puis return; arrête le rendu : ce qui est déjà émis est gardé.
<main>…</main>renderLes éléments sont l'affichage lui-même.
#back() { <a …>…</a> }méthodeUn morceau de HTML réutilisé s'écrit dans une méthode qui émet ses éléments, appelée par {this.#back()} dans render.

En résumé : la préparation porte les verbes déclarer, s'abonner, écouter, préparer ; render porte les verbes lire, décider, afficher. render doit pouvoir être appelé dix fois de suite sans conséquence.

L'erreur classique : lire une valeur dans un champ

Un champ s'initialise à la création de l'instance : les props sont lisibles, mais le store n'est pas encore résolu, et une valeur lue à ce moment-là ne suivrait pas les changements.

Cas typiques : lancer une commande au montage, écouter un événement pour déclencher une action ailleurs (analytics, son, focus), poser un écouteur sur window. Un composant qui n'affiche rien garde un render vide : render() {} (voir Ne rien rendre).

Dans l'exemple Widget : timer-widget.super. Un intervalle démarré au montage, arrêté au démontage.

Cycle de vie

  1. Création : la balise du parent (ou create) dépose les props, puis construit l'instance (déclarations et champs, dans leur ordre, puis constructeur s'il y en a un), qui les lit déjà.
  2. Montage : l'élément entre dans le DOM. Super résout les contrats déclarés, branche les écouteurs @on, fait le premier render, pose son titre s'il en déclare un, puis appelle mounted.
  3. Rendus : à chaque changement de props, d'état local ou de valeur lue dans un store. Plusieurs changements dans la même tâche ne donnent qu'un rendu.
  4. Déplacement : un élément déplacé dans le DOM (par exemple par une boucle for avec key) n'est pas redémarré : il garde son état.
  5. Démontage : un vrai retrait du DOM avorte signal, désabonne le composant de ses stores (lectures et écouteurs @on), retire son titre, puis appelle unmounted. S'il est réinséré plus tard, la même instance se remonte : ses contrats sont résolus de nouveau, ses écouteurs @on rebranchés, son titre reposé, et mounted rappelé. Son état local est conservé.

Le titre de la page

Le titre de l'onglet (document.title) appartient aux composants montés : un composant le pose par @title, et le retire en se démontant. Personne n'écrit document.title à la main.

Un titre fixe ou suivi

Une chaîne donne un titre fixe, posé au montage et retiré au démontage : @title = 'Widget';. Une fonction donne un titre suivi : elle est recalculée après chaque rendu, avec les mêmes lectures que render. Le titre de la boutique change donc avec le panier :

Le calcul est libre (une condition, un formatage), contrairement à la fonction d'un @selector. Dans l'écran d'un compteur, @title = () => this.label.value ?? 'Compteur introuvable'; suit le nom du compteur : le renommer change aussi le titre de l'onglet.

this.page.title

@title est un raccourci : this.page.title = … fait la même chose en impératif, avec une chaîne ou une fonction. Ce qui change, c'est le moment où on l'écrit.

La pile des titres

Plusieurs composants montés peuvent poser un titre en même temps. Le dernier monté l'emporte ; ceux en dessous continuent de suivre leurs données sans s'afficher ; quand il se démonte, le titre précédent revient. N'importe quel composant peut poser un titre, pas seulement un écran : dans la démo, KitPage, la mise en page commune du kit, donne leur titre à toutes les pages du kit avec @title = () => this.heading;.

Le déroulé, pour la boutique et un dialogue de confirmation qui déclarerait @title = 'Confirmation';, avec le réglage de la démo (suffix: ' · Super', default: 'Super · exemples') :

À l'avant-dernière ligne, la boutique a suivi le panier vidé pendant que le dialogue était au-dessus : son titre est déjà à jour quand il revient.

Ce qui est interdit

  • Poser le titre pendant render : this.page.title lève une erreur (« ne se pose pas pendant render »).
  • Lire le titre : this.page.title se pose, il ne se lit pas ; le lire lève une erreur.
  • Une prop nommée title : c'est une propriété des éléments HTML (la démo l'appelle heading). page est réservé.

Créer un élément hors template

Dans un fichier .super, <CounterControls count={count} … /> monte l'enfant à cet emplacement (voir Parents et enfants) ; l'outillage le traduit en CounterControls.create(props, { on }). Hors template, pour le montage initial ou un test, on appelle ce create(props?, { on }?) directement : il renvoie l'élément.

Un composant ne s'écrit pas par son tag : <counter-screen> tapé dans un template ou dans index.html n'est pas supporté. Il passe toujours par sa classe, en balise (<CounterControls count={count} … />) ou par create.
