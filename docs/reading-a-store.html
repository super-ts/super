Reading a store

@contract name; gives the component the view of the store provided by the application. @selector chooses what it reads from it: the component only re-renders if that value changes.

@contract and @selector

  • @contract counter; is declared in the class body, once per store used, and is read through this.counter. The name is the contract's, checked by the compiler: @contract compteur; does not compile. For a different field name: @contract shop = 'catalog';.
  • @selector count = …; is also declared in the class body, after the @contract it reads. Its value is the reading of one selector; it is read through .value in render, with the selector's type. No type to write: it comes from the value.
  • All these declarations are described in Components. A component written in a .ts file keeps the methods: counter = this.contract('counter'), count = this.selector(…).
  • The selectors are the contract's, with the state already supplied, plus pending(…) to know whether a command is pending (see pending).
  • The component does not import the contract: it names it. Only types may come from @core/ (import type).

The rule is checked at compile time: a selector value carries a type brand that @selector requires. null and undefined cannot carry a brand: for them, Super checks at runtime, and throws an error explaining what to do. The reason: a @selector that computes might depend on no store and stay frozen, or mix the store with something else without Super knowing.

What @contract gives

MemberRole
selectorsThe contract's selectors, plus pending, read on the current state at each call. To pass to @selector, or to read directly in render.
send(name, body?)Sends a command and lets it run. Returns void; the outcome comes back through the selectors, or through name:done / name:failed.
on(name, listener)Listens to a store event, or a command's outcome. In a .super file, it is written on a method, @on('counter', 'increment:done'), which is called as long as the component is mounted: no signal to pass (see Listening to the outcome). In a .ts file, it is declared in the constructor; it is forbidden during render.
href(route, { params, query }?)For the router only: builds a typed link, without subscribing the component (see below).

The component does not receive the store itself: no raw state, no subscribe, no dispose, no emit. These capabilities stay with whoever created the store.

When the component re-renders

On every store state change, Super recomputes the @selectors read during the last render and compares each value with the one displayed. If nothing has changed, the component does not re-render.

Example: the "Coffees" screen reads count('coffees'). Incrementing "Push-ups" changes the store's state, but not the value read by the screen: it does not re-render.

What counts as a change

The value read is deeply compared with the previous one. It does not matter if a selector rebuilds it: only its content counts, and Super keeps the old reference as long as it is equal (structural sharing). Plain arrays and objects are compared element by element; a Date, a Map or a class instance, by reference.

ReadingRe-render when…
@selector count = () => this.counter.selectors.count(this.counterId)the number changes.
@selector busy = () => this.counter.selectors.pending()a command starts or finishes.
@selector lines = this.cart.selectors.linesa line changes. Unchanged lines keep their reference.
@selector catalog = this.counter.selectors.catalognever, if the catalogue does not change.

The value of .value is the same reference as long as its content does not change: passing it as props to a child does not re-render it needlessly. A child only re-renders if one of its props changes.

For a list: one component per row

On the counter list, each row is a small component (CounterListItem, above) that reads its own value. When a counter changes, only its row re-renders: the list does not move, and the DOM of the other rows is not recomputed.

Reading props in the reading

A @selector function can read props (this.counterId). It is recomputed on every render, so on every props change: if the screen goes from "Coffees" to "Push-ups", the reading follows, with no missed update. That is also why a selector with a parameter is written in a function: props are readable when the declaration initialises, but a value read at that moment would stay the one from creation.

Reading a selector directly in render

A selector called directly in render ({this.counter.selectors.count('coffees')}) also subscribes the component, as finely as a @selector: Super remembers each reading and its value, and on every store change, it redoes these readings. The component only re-renders if one of them gives a different value (deeply compared: a new array with the same content does not count).

The reading is recorded on the component that renders, even if the contract view comes from another one: a child that receives its parent's view as a prop and reads it in its own render subscribes itself, and re-renders on its own. That is what the kit's CommandButton does, reading pending on the contract of the screen that prepared it.

@selector is still useful to read a value outside render through .value, to name it once and reuse it, and for isValid() on a route value. Only what is read counts: what render shows without going through a selector (a module variable, Date.now()) triggers no render.

Showing nothing from a store

A component that sends commands or listens to events, but shows nothing from the store, declares the contract without @selector: it never re-renders for that store.

The router

The router is read through this.router, without declaring it: a view that is always available. The active route is read through this.router.current: name() (the active route's name), path(), params.<key>(), query.<key>(). Each one is passed as is to @selector, like a selector without a parameter.

this.router.href('counter', { params: { id: 'coffees' } }) builds a link, with the route and its parameters checked. It does not read the active route: a component that only shows links does not re-render on every navigation. See Router.

Several stores, or several readings

Declare as many @contract and @selector as needed. Each @selector is compared on its own: the component re-renders if any of them changes.
