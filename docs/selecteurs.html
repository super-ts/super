Sélecteurs

Les sélecteurs sont les lectures autorisées de l'état. Ce sont les méthodes du contrat, utilisées telles quelles par les composants, le store et les tests. Tu les écris avec l'état en premier paramètre, et Super le fournit à l'appel : tu écris count(s, id) dans le contrat, puis selectors.count(id) partout ailleurs.

Déclarer des sélecteurs

  • Chaque sélecteur reçoit l'état en premier paramètre. Annote-le (s: CounterState) : TypeScript n'infère pas les paramètres d'une méthode.
  • Il peut prendre d'autres paramètres après l'état : count(s, id: string) s'utilise en selectors.count('cafes').
  • Il peut ignorer l'état : catalog renvoie une donnée statique. C'est utile pour que les composants n'aient rien d'autre à demander que le contrat.
  • Il doit être pur : pas d'effet de bord, pas d'appel réseau, seulement une lecture.
  • pending est réservé : Super l'ajoute aux sélecteurs, pour savoir si une commande est en cours (selectors.pending('load')). Une méthode pending dans le contrat ne compile pas (erreur à la déclaration du store). Un sélecteur ne lit que l'état ; les commandes en cours n'en font pas partie.

Un sélecteur sans paramètre

Un sélecteur ne prend un paramètre que si la réponse en dépend. canDecrement a besoin de l'id (il faut savoir si ce compteur est au-dessus de 0). loadErrorMessage n'en a pas besoin : la réponse ne dépend que de l'état global. Côté composant, la différence se voit : un sélecteur sans paramètre se passe tel quel à @selector loadErrorMessage = this.counter.selectors.loadErrorMessage;, un sélecteur à paramètre s'appelle dans une fonction (voir Dans un composant).

Pourquoi des sélecteurs

  • Une seule définition. « Un compteur absent vaut 0 » est écrit une fois. Le store, les composants et les tests appliquent la même règle ; la changer dans le contrat la change partout.
  • Une porte fermée. Un composant ne voit jamais l'état brut : this.counter n'a pas de state(), et this.counter.selectors.counts ne compile pas, counts n'étant pas un sélecteur. La vue ne peut pas réinventer une règle de lecture dans son coin.
  • Moins de bruit. L'état est fourni par Super : pas de s à trimballer.

Dans un composant

Un @selector lit la valeur d'un sélecteur telle quelle ; la condition ou le calcul se font dans render, ou dans un nouveau sélecteur du contrat. Voir Lire un store pour les règles de re-rendu.

Dans le store

Chaque appel relit l'état courant : juste après un this.set, this.selectors.count(id) renvoie déjà la nouvelle valeur.

Dans un test

Pourquoi sur le handle, et pas sur le contrat ? Un contrat n'a pas d'état : il décrit un store, il n'en est pas un. Il peut exister plusieurs stores pour le même contrat. Les sélecteurs se lisent donc sur un store précis : son handle (store.selectors), sa vue dans un composant (this.counter.selectors), ou this.selectors dans le store lui-même. Chacun fournit l'état de ce store, et son cache.

Quoi mettre dans un sélecteur

  • Oui : toute lecture qu'un composant ou le store fait plus d'une fois, ou qui contient une règle (« vaut 0 si absent », « possible si rien n'est en cours »).
  • Oui : les données dont les composants ont besoin et qu'ils ne peuvent pas importer de @core/ (catalogue, libellés).
  • Oui : une valeur que l'écran affiche après une condition ou un calcul, quand ce calcul mérite un nom. @selector n'accepte qu'un sélecteur tel quel ; un sélecteur de plus garde le composant simple.
  • Non : un sélecteur qui renvoie tout l'état (all(s: CounterState) { return s; }). Ça rouvre la porte que les sélecteurs ferment.
  • Oui : les dérivations (lignes d'un panier, total, liste filtrée). Leur place est dans le contrat plutôt que dans les composants : elles sont partagées, testables sans DOM, et Super stabilise leur résultat (voir ci-dessous).

Dériver dans un sélecteur

Un sélecteur peut filtrer, trier ou construire de nouveaux objets sans précaution particulière. Chaque store garde un cache de ses sélecteurs, et Super évite les recalculs et les re-rendus inutiles en deux temps.

  • Recalculer ou non : Super note les champs de premier niveau de l'état que le sélecteur lit. Au changement d'état suivant, si aucun de ces champs n'a changé de référence, le résultat précédent est renvoyé sans recalcul.
  • Garder la référence : après un recalcul, le résultat est comparé en profondeur au précédent. S'il est égal, c'est l'ancienne référence qui est renvoyée. Sinon, les parties inchangées (une ligne qui n'a pas bougé) gardent la leur.

Exemple : une messagerie dont l'état contient les messages et la réponse en cours de saisie.

visible lit messages et folder. Une frappe dans draft crée un nouvel état, mais ne déclenche ni filtre, ni tri, ni re-rendu. Un message reçu déclenche le recalcul ; la liste se re-rend, et seule la ligne du nouveau message est nouvelle.

Ce qu'il faut savoir :

  • Le suivi s'arrête au premier niveau : un sélecteur qui renvoie s.messages[3].subject est recalculé dès qu'un message change. Le recalcul est sans conséquence, la comparaison du résultat évite le re-rendu.
  • Un sélecteur qui parcourt l'état entier (Object.keys(s), { ...s }) dépend de tout : il est recalculé à chaque changement.
  • La comparaison ne descend que dans les tableaux et les objets simples : une Date, une Map ou une instance de classe se compare par référence.
  • Un sélecteur ne lit que son état et ses arguments : ce qu'il lirait ailleurs (une variable de module, Date.now()) n'est pas suivi.

Un contrat sans sélecteurs

Les sélecteurs sont facultatifs, mais ce sont les seules lectures qu'un composant a. Sans eux, un composant peut envoyer des commandes au store et écouter ses événements, rien de plus : il ne voit jamais l'état brut. Le handle complet, lui, garde state() pour les tests, la racine de composition et les autres stores. Le router suit la même règle : les composants lisent la route active par this.router.current (name(), path(), params, query), jamais son état brut (voir Router).
