Errors

When a component crashes, Super can show a fallback render in place of the broken part, and report the error in a single place. Three levels, from the most local to the most global: a component's renderError, the router's '!' screen, and onError in the application.

Without declaring anything

Every case on this page can be triggered in the Errors example (npm run dev, then /errors): errors/index.super and its blocks, main.ts. Its log shows what onError receives.

Example: a counter screen calls label.toUpperCase() while label is null. Without an error boundary, the screen stays empty (or frozen on its last display if the error happens later), the error goes to the console, and the rest of the page keeps working. The user sees a blank area, with no explanation.

A component's renderError

renderError(error) is an optional method, next to render. It is shown in place of render when the component, or one of its descendants, crashes. It is written like render: it emits its elements, without return.

  • It receives the error, always an Error: a thrown value that is not one is converted. It has access to the props (this.broken) and the component's fields, like render.
  • It catches the descendants' errors: if a child crashes, on render as in its constructor, the whole parent switches to its renderError.
  • It catches a store not found at mount (setup phase): the instance exists, it can show a replacement. If it reads that store itself, it crashes in turn and the error goes up.
  • It does not catch the error of its own constructor: if the constructor (or a field) crashes, the instance does not exist. The error (setup phase) goes up to an ancestor's renderError.
  • Once in renderError, the component stays there until it is unmounted. It keeps re-rendering if its props change. A screen is remounted on each navigation, which resets it. To reset a block, you recreate it: the Errors example places its blocks in for (const _round of [round]; key _round), and "Start over" increments round, which changes the key and recreates the components (see Lists).
  • If it crashes itself, the error goes up to the next parent: no loop.

BrokenChild, written <BrokenChild /> in the panel's render, throws an error in its constructor. It is reported under the child's name (tag: 'broken-child', phase: 'setup') and caught by GuardedPanel (caughtBy: 'guarded-panel').

Why a separate method, and not an error passed to render If it is render that crashed, calling it again could crash at the same place. renderError is a second render, written to depend only on the error and the bare minimum.

Where to put a renderError

  • On a screen, for a message suited to the page ("Unable to show this counter").
  • On a self-contained part of a screen (a chart, a widget), so that the rest of the screen stays usable.
  • On the shell (AppShell), to cover errors outside the active screen, such as in the header.
  • No need to put them everywhere: the '!' screen acts as the default safety net for all screens.

The router's '!' screen

If a screen's error goes up to the RouterOutlet without being caught, the outlet shows the '!' screen in place of the active screen. The shell and the navigation stay usable.

  • The '!' screen receives the error and the path as props: it is the only screen that receives props from the router. The compiler requires its props to be { error: Error; path: string }: @prop error: Error; and @prop path: string;.
  • Any navigation closes it and mounts a fresh screen: going to another page then coming back, or simply clicking the link of the failed page again. If the screen crashes again, the '!' screen reappears.
  • If it crashes itself, the error keeps going up.

Reporting: onError

onError, in createApp, receives every error from a component rendered under the root, whether it was caught or not. It is the single place to log or notify a monitoring tool.

In production, you would rather plug a monitoring tool in there:

reportToMonitoring is a function of your project: Super calls it through onError, it does not implement it.

InformationContent
errorThe error, always an Error.
tagThe component that crashed ('fragile-card').
phase'setup' (constructor, or store not found at mount), 'render' or 'renderError': the display was broken. 'event', 'listener' or 'mount': an action failed (see below).
caughtByWhat caught it: the tag of a component with renderError, 'super-router-outlet' for the '!' screen, or null.

Without onError, a caught error goes to the console, and an uncaught error is thrown. With nested applications, the one closest to the component reports it, once.

Who catches what

An error goes up the component tree from the one that crashed. The first one able to handle it keeps it:

  1. the component that crashed, if it has a renderError (except for the error of its own constructor);
  2. otherwise its parent, then the parent's parent, up to the first one that has a renderError;
  3. otherwise, if it reaches the RouterOutlet, the '!' screen;
  4. otherwise nobody: the component stays empty.

In every case, onError is called once. The blocks of the Errors example cover each row:

What crashesWhat is shown

BrokenChild in its constructor, under GuardedPanel (with renderError)GuardedPanel's renderError, in place of the whole panel. tag: 'broken-child', phase: 'setup', caughtBy: 'guarded-panel'.

Action errors: on:event, on, mounted

An error in a template event handler, in a contract's on listener, or in mounted / unmounted is also reported to onError, with the component it comes from. Nothing to write: Super wraps these functions itself.

An error in…phaseOn screen
an on:click={…} handler (synchronous or asynchronous)'event'Nothing changes.
an @on('counter', '…') listener (this.counter.on(…) in a .ts file)'listener'Nothing changes.
mounted() or unmounted()'mount'Nothing changes.

The component does not switch to its renderError: when an action fails, the display is usually still correct. Replacing the whole screen for a failed click would be out of proportion. The error is only reported (to the console without onError), and caughtBy is null.

What is not covered

  • Code Super does not see go by: a setTimeout, or the function of a window.addEventListener set up by hand in mounted. An error there goes to the console.
  • unmounted of a component removed from the DOM: the error can no longer go up to the application. It goes to the console.
  • A handler built outside a component, in an html template created when a .ts module loads, for example: it is not attached to any component.
  • The constructor of a component created outside a template (AppShell.create() in main.ts): the error is thrown at the create call, as for any code.
  • Store errors: they do not go through here. A store catches its errors and publishes them through its state or an event (see Stores: errors).
  • Configuration errors thrown by Super itself (two stores for one contract, unknown route in href, missing static tag in a .ts component): these are programming errors, to be fixed.
