Getting started

Install the repository, run the example, then write a complete feature end to end.

Install

The @super-ts/* packages are published on npm and share one version. In 0.x, a minor version can break the API.

In your project

The Vite plugin compiles .super files, applies the architecture rules and declares the @core/ and @components/ aliases, resolved from src. Vitest goes through the same plugin.

The types of .super files are written under .super/ by super-tsc, the Vite plugin and the language server: the tsconfig merges that folder with the project (rootDirs) and doubles the two aliases (see Tooling).

npx super-tsc tsconfig.json checks the types of .ts and .super files, and npx super-fmt --write src formats .super files. For errors and completion in your editor, plug in the .super language server (see Tooling); the import order of Super is a shared Biome configuration, @super-ts/lint.

Working on Super itself

The repository contains the packages and an example app.

In the repository, @super-ts/… resolves to the sources (packages/*/src), without a build, through the aliases declared in the tsconfig.json files and vite.config.ts. In the app, the Super folders are imported through aliases too, from any file: '@core/counter/contract', '@components/app-shell' (see Architecture).

The example app

examples/demo is a single app that brings together Super's examples. npm run dev runs it on http://localhost:5173; its home page leads to each example:

  • Counters (/counters): a list of counters, a detail page per counter with + and − buttons, persistence in localStorage.
  • Profile form (/profile): every field type, rules, an asynchronous check, a dynamic list, and a simulated server (latency, address taken, network failure).
  • Shop (/shop): a store that depends on another, a hand-written event, a confirmation dialog, a guard.
  • Errors (/errors): each level of error handling, triggered for real, with the onError log.
  • Widget (/widget): a second application in the page, a mounted with cleanup through signal, a keyboard shortcut.
  • Kit (/kit): a table of contents and one page per component family of @super-ts/ui, wired to the demo's stores, including a table wired to a real API and a theme page.

Almost all the snippets in these docs come from it: when a snippet is taken from the example, a link leads to the full file. The Examples page details what each file shows.

Your first feature: a theme button

You are going to add a button that switches between light and dark mode. It is deliberately simple, but it goes through every step: contract, store, component, wiring and test.

Step 1: the contract

The contract describes what the store can do, without saying how. It is a class, in its own folder under src/@core/, that names itself in its constructor: that name is how you will ask for it.

The Vite plugin spots the contract and registers it in src/@core/contracts.d.ts, a generated file (to commit, never to write by hand). This is what makes 'theme' known to the compiler everywhere in the app. See Contracts and Selectors.

Step 2: the store

The store implements the contract: an initial state, and one method per command.

implements Commands<ThemeStore> has the compiler check the methods: a forgotten command, a parameter that differs from the contract or a public method outside the contract do not compile. This constructor takes nothing: the store is created with ThemeStore.create(). See Stores.

Step 3: the component

The component asks for the store by its contract's name, reads a selector and sends the command on click. It is reusable: it goes in src/@components/shared/, in a .super file.

render() returns nothing: the button is written as a statement, on:click sets up the listener and {…} displays a value (see Templates). The component imports nothing from src/@core/: @contract theme; is enough, and the compiler knows the contract's selectors and commands. See Components and Reading a store.

Step 4: the wiring

The composition root, main.ts, creates the stores and provides them to the app. The component can then be used anywhere under the root, for example in the shell's header: <ThemeToggle />, after import { ThemeToggle } from '@components/shared/theme-toggle'.

The app finds each store by its contract's name: a component that asks for 'theme' receives this one. See Wiring the application.

Step 5: the test

The test stays a .ts file: it imports the .super component without an extension and mounts it with mount. A test may import a store: the plugin does not check *.test.ts files. To test the component on its own, replace the real store with fakeStore('theme', { state: { mode: 'dark' } }). See Testing.
