UI kit

@super-ts/ui gathers the components an app always ends up writing: fields linked to a form, a button that sends a command, a navigation link, messages, windows, menus, a table. They have a plain look controlled by CSS variables, are accessible to the keyboard and to screen readers, and plug straight into Super's contracts, forms and router.

What the kit provides

The kit falls into four families:

  • Components specific to Super, which know its concepts: Field, Select, Checkbox, RadioGroup linked to a @form, CommandButton linked to a command, RouteLink linked to the router, Toasts to report command outcomes, ErrorPanel for a renderError or the '!' screen.
  • Accessible primitives, which take a long time to write correctly: Dialog, Modal, ConfirmDialog, Menu, Tabs, Disclosure, Tooltip, Popover, Combobox.
  • Display: Button, Badge, Spinner, Skeleton, EmptyState.
  • Data: Table, static or connected to a store.

They are Super components like yours (SuperElement, props, events, slots), written in .ts: an app imports them without configuring anything else. They render into the normal DOM, without shadow DOM: the app's styles reach them, and tests find them by their role and label.

The kit provides no layout components: no Stack, Grid or Card. Layout stays in the app's CSS, where it is simplest to read and change.

Importing the kit

  • Importing the kit loads its stylesheet: there is no CSS to add by hand.
  • @super-ts/ui depends on @super-ts/dom, and nothing else.
  • In this repository, it is resolved through an alias like the other packages (packages/ui/src, declared in vite.config.ts and in the paths of tsconfig.json): see Distribution.
  • A kit component is written by its class, like any child component: <Button>, not <super-button>.

A CSS layer with zero specificity

All the kit's rules are in the @layer super-ui layer, and their selectors are wrapped in :where(…), which brings their specificity down to zero. An app rule therefore always wins, without !important or heavier selectors: a rule outside a layer beats any rule inside a layer.

Light and dark

Each kit colour is declared with light-dark(light, dark). The browser picks the value according to the element's color-scheme, inherited from its ancestors:

  • Without color-scheme, the kit stays light, whatever the system theme.
  • With color-scheme: light dark on :root, the app follows the system theme, and the kit with it. This is what the examples app does in its src/styles.css.
  • A zone can force its own: color-scheme: dark on an element switches every kit component it contains to dark, even in a light page.

color-scheme sets the kit's colours and the browser's (scrollbars, native fields), not the background or text of the zone itself: the app sets those, as here. A colour override is also best written with light-dark(…), to stay readable in both themes.

For browsers that do not yet know light-dark(), nothing to do: Vite's CSS minifier (Lightning CSS) compiles it at build time into a fallback form they understand.

Form fields

Field, Select, Checkbox and RadioGroup are linked to a field of a @form (see Forms) through fieldOf(form, 'name'). Each one takes care of what gets repeated from one field to the next:

  • the label, linked to the control (<label for>, or the legend of a <fieldset> for RadioGroup);
  • the hint (hint), displayed under the field;
  • the rule or server error, displayed under the field when the form shows it;
  • "Checking…" during an asynchronous check;
  • aria-invalid when there is an error, and aria-describedby pointing to the hint and the error.

fieldOf is checked by the compiler, like edit.field('…'): a name absent from the form does not compile, and the type of the value must suit the component. A boolean field cannot go into a <Field>, a text field cannot go into a <Checkbox>.

ComponentField valueOwn props
Fieldstring, number or nulltype (text by default, email, password, number, url, tel, search, date, time, datetime-local, color, range), multiline and rows for a text area, placeholder, autocomplete.
Selectstring, or a list with multipleoptions ({ value, label }[]), multiple.
Checkboxboolean, or a list with valuevalue: the box is then one of a group, whose field is a list.
RadioGroupstringoptions: one radio button per option.

All of them receive field, label, and optionally hint and class.

fieldOf is written in the render of the component that owns the form

That component is the one that re-renders when a value, an error or a check changes, and the kit field with it. The form is therefore not passed to a sub-component that would call fieldOf on its side: the fields there would stay frozen. The screen's render(), as above, or a render method of the same class is fine.

Sending a command: CommandButton

CommandButton sends a command on click, and stays disabled while it is pending, with aria-busy="true". The command is prepared with commandOf(view, 'command', input): the contract, the command name and its input are checked by the compiler.

  • "Pending" comes from pending on this command and this input (see pending): another button that resets another counter is not disabled.
  • pendingLabel replaces the content while sending; without it, the content stays displayed.
  • variant (primary by default, secondary, danger) and disabled work as on Button.
  • The outcome comes back as for any send: through the selectors, or through name:done and name:failed listened to with @on (see Listening to the outcome). The button displays no outcome itself.
  • The button reads the contract of the component that prepared it, during its own render: it is the one, and the only one, that re-renders when the command starts or finishes (see Reading a selector directly in render).

Preparing a command: commandOf

commandOf brings together the contract view, the command name and its input. Each argument is typed by the previous one, which gives checking and completion in the editor as you type:

ArgumentIts type comes fromThe editor suggests
this.counterthe view declared by @contract counter;the component's contracts
'reset'the commands of this contractload, increment, decrement, reset
{ id: 'coffees' }the input of this commandid
  • A command without input is written without a third argument: commandOf(this.counter, 'load').
  • commandOf sends nothing: it prepares. Sending happens when the button is clicked, through the contract view, so to the store of the component that prepared it.
  • The same input is used for pending: the button is only disabled for this command with this input.
  • fieldOf(this.edit, 'email') follows the same principle for fields: the form sets the suggested names, and the type of the value carries through to the component (see fields).

Navigation links: RouteLink

RouteLink is a link to a route, which marks itself aria-current="page" when it leads to the displayed page. Its target to is written and checked like that of navigate.

  • Active: the link's path is that of the displayed page, ignoring the query and a trailing slash. /counters?sort=label keeps the "Counters" link active.
  • activeFor adds route names for which the link is also active: a section, its list and its detail.
  • exact also compares the query: useful for links that differ only by it (a sort order, a filter).
  • The click is handled by the router, as for any internal link (see Link interception).
  • Params and query are given as for navigate: to={{ to: 'counter', params: { id } }}.

Reporting an outcome: Toasts

A message queue is created with createToasts() in the component that wants to report something, and is displayed with <Toasts of={…} />. The component pushes into it the outcomes of the commands it listens to:

Command outcomes turn into messages in the methods that listen to them, declared with @on:

  • show(message, { tone, duration }): tone is info (default), success or error; duration is in milliseconds, 5000 by default, and 0 keeps the message until it is closed. show returns an identifier, to pass to dismiss(id) to remove it earlier.
  • Each message has its own close button.
  • An error message is announced immediately by screen readers (role="alert"), the others politely (role="status").
  • The area is fixed at the bottom right of the screen; .super-toasts can be repositioned by an app rule.

Displaying an error: ErrorPanel

ErrorPanel presents an error: a title, the message, and the technical detail (the path and the stack) collapsed under "Details". It is used in a renderError (see A component's renderError), or as is as the router's '!' screen, which passes it error and path:

Props: error, path, title ("Something went wrong" by default), canRetry which displays the button that emits retry, retryLabel. The panel has the alert role.

Windows: Dialog, Modal, ConfirmDialog

Like any Super component, a mounted window is open: the parent decides whether to render it or not, often according to its local state. The window does not close itself: it asks the parent to with an event, and the parent removes the window from its render (see A dialog).

WindowContentEvent
Dialogtitle, the children, and footer actions in the <:actions> slot.close { reason }
ModalThe same mechanics, without actions: title and the children.close { reason }
ConfirmDialogquestion, title ("Confirmation" by default), confirmLabel, cancelLabel, danger for a red confirm button.answered { confirmed }: true for confirmation, false for cancel, Escape, the close button or the backdrop.
  • reason says what requested the close: 'escape', 'backdrop' (a click on the backdrop) or 'button' (the close button).
  • closeOn sets each way of closing: { escape, backdrop, button }. By default, Escape and the close button, not the click on the backdrop, which is too often made by accident. { button: false } removes the close button.
  • A real <dialog> opened as modal: the rest of the page becomes inert (no click, no focus, no screen reader), and the background is darkened by --super-backdrop.
  • On opening, focus moves into the window (to the autofocus element, otherwise the first focusable element); on closing, it returns to the element that had it. Page scrolling is locked while the window is open.
  • The title names the window for screen readers (aria-labelledby); closeLabel names the close button ("Close" by default).

Accessible primitives

Each one follows the expected ARIA pattern (roles, states, keyboard). Those that hold a display state (open, selected tab) hold it themselves, and notify the parent with an event.

Menu

  • A button opens the list of actions. Keyboard: up and down arrows, Home, End, Enter or Space to choose, Escape to close and return to the button. Disabled entries are skipped.
  • A click outside the menu closes it.
  • The choice is emitted by select { id }.

Tabs

  • panels is a list of slots (Children[]), one per tab and in the same order, filled by render methods (see Named slots).
  • Keyboard: left and right arrows, Home, End; disabled tabs are skipped.
  • Without selected, the tabs keep their own choice (the first at the start). With selected, the parent holds it, notified by change { id }: useful to put the tab in the route's query.

Disclosure

Collapsible content, on <details> and <summary>: the browser already makes it an accessible element. open opens it on first display; toggle { open } notifies on each opening and closing.

Tooltip

The tooltip appears on hover and on focus, and Escape hides it. The first focusable element of the content is linked to it with aria-describedby: a screen reader reads the text along with the button.

Popover

Floating content behind a button, non-modal: the rest of the page stays usable. Escape closes it and gives focus back to the button; a click outside the content closes it too. toggle { open } notifies the parent; title names the content (default: label).

Combobox

An input with suggestions, in two modes.

With hard-coded values: the combobox filters its options against the input itself, ignoring accents and case ("peach" finds "Peach").

Connected to an API: the parent searches, the combobox displays. filter={false} makes it display the options as they are, loading displays "Loading…", and the parent reacts to search { text }, emitted on every keystroke. In the kit's "Primitives" page, the suggestions come from the public dummyjson.com test API, through the catalogue store:

The combobox emits one search per keystroke; it is up to the store not to flood the server. The catalogue store waits for typing to stop, sends only the last request, and ignores an overtaken response:

  • The choice is emitted by select { value, label }, and the chosen label stays in the input. value gives the initially chosen value.
  • Keyboard: arrows to browse, Enter to choose, Escape to close the list.
  • The browsed option is announced through aria-activedescendant: focus stays in the input.
  • With no option to show, the list displays emptyLabel ("No results" by default). Nothing typed and nothing to suggest: the list stays closed, focus does not open an empty list.

The table

Columns are declared with columns<Row>([…]), typed by the row type: value receives a typed row.

Column keyRole
key, labelIts identifier (the one used for sorting) and its title.
valueThe value displayed and sorted, computed from the row. By default, row[key].
sortableThe header becomes a button: one click sorts in ascending order, a second reverses it.
align'end' aligns right, for numbers.

The table has two modes, depending on whether you give it total or not.

Static: all the rows

Without total, rows contains all the rows: the table sorts and paginates them itself, and asks nobody for anything. Without pageSize, no pagination. With pageSizes ([10, 20, 50]), a "Rows per page" choice is added to the pagination, and takes you back to the first page.

A table wider than the screen

By default, a table too wide for the available space scrolls horizontally within its own area: it keeps its natural width, cells on one line, and neither the page nor the pagination moves. The title (caption) stays above, visible while scrolling. The area is reachable with the keyboard (tabindex="0"), to scroll with the arrows, and carries the table's name.

scroll={false} removes this behaviour: the table takes the width of its container, its cells wrap, and any overflow is left to the app's CSS.

Connected: one page at a time

With total (the number of rows on the server side), rows is the current page, already sorted. The table emits request { sort, page, pageSize } on mount, then on every change of sort order, page or page size, and the parent connects it to a command that loads the requested page. In the simplest case, the table keeps its own sort order and page, and the parent only has to pass the request on; a new sort order then takes you back to the first page.

So that a link, a reload or the browser's back button find the same page again, the parent can drive the sort order, the page and the page size through the sort, page and pageSize props, read from the route's query. This is what the kit's "Table" page does in the examples app, connected to the public dummyjson.com test API (see Examples). The query is described in the route, and typed:

The screen reads this query through selectors, passes it to the table, changes the URL when the table announces a sort order (sort), a page (page) or a page size (pageSize), and loads the data when it requests it (request):

  • The URL is the single source: sorting or paginating navigates (/kit/table?sort=price&order=desc&page=3&size=20), the table follows its props, then emits request. The screen answers by reading the query again (#query()), without using the event's argument.
  • Changing only the query does not remount the screen: the table stays mounted, and requests its data again when its sort, page or pageSize props change.
  • When the parent drives the page, it is up to the parent to go back to the first page on a new sort order or a new page size (page: 1 in on:sort and on:pageSize above).
  • The size chosen in the table gives way to the parent's: if the parent passes a different pageSize again (going back in the history), that is the one displayed.
  • sort is { key, direction: 'asc' | 'desc' }, or null for no sorting. The key received by on:sort is a string: isProductSort narrows it to the domain type.
  • An unknown value in the URL (?sort=whatever&page=abc&size=7) is replaced by the query's default value: no sorting, page 1, 10 rows.
  • request is emitted after rendering, never twice in a row for the same request.
  • loading (here pending('load')) sets aria-busy on the table, and displays "Loading…" until a row has arrived.
  • The failure stays with the screen: the table displays no error. The store keeps a message (loadErrorMessage), and the screen displays it with a button that retries the same request.
  • Responses can arrive out of order: one sort then another send two loads. The catalogue store ignores a response overtaken by a more recent request (see Examples).

In both modes, sortable headers carry aria-sort and a space reserved for the sort arrow (sorting changes no width), the pagination is a <nav> "Pagination" with "Previous", "Page 2 of 5" and "Next", caption names the table, and emptyLabel is displayed when there are no rows ("No data" by default).

Limitations

  • No layout components: no Stack, Grid or Card. Arrangement stays in the app's CSS.
  • fieldOf is written in the render of the component that owns the form: passed to a sub-component, the field would no longer follow the form's changes.
  • No browser popover API: menus, popovers, tooltips and combobox lists are positioned with position: absolute under their trigger. An ancestor with overflow: hidden can clip them, and they do not reposition at the edge of the screen.
  • The texts are in English by default: most can be changed through a prop (Default texts), a few cannot yet.
  • The table sorts on one column at a time, and has neither row selection nor resizable columns.
