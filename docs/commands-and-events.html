Commandes et événements

La vue envoie et laisse filer. Le store fait le travail, attend ce qu'il doit attendre, puis réussit ou échoue. Super suit chaque commande de bout en bout : il sait quand elle est en cours, et publie son issue.

Le trajet d'un clic

Ce qui se passe quand on clique sur « + » dans l'écran d'un compteur :

  1. CounterControls émet increment vers son parent (événement de composant).
  2. CounterScreen envoie la commande : this.counter.send('increment', { id: 'cafes' }). Il n'attend rien.
  3. Super note que increment est en cours : this.counter.selectors.pending() devient vrai, l'écran se re-rend avec les boutons désactivés.
  4. La méthode increment du store attend this.#repository.save(…), met à jour counts et retourne { count: 3 }.
  5. Super note que la commande est finie (les boutons se réactivent) et publie increment:done avec { input: { id: 'cafes' }, result: { count: 3 } }.
  6. L'écran affiche la nouvelle valeur (elle a changé dans l'état) et « Incrémenté : 3 » (grâce à l'événement, reçu par sa méthode @on('counter', 'increment:done')).

Envoyer une commande

Dans un composant, send renvoie void. Il n'y a rien à attendre : écrire await this.counter.send(…) n'a pas de sens, et aucune donnée ne revient à l'appelant.

Pourquoi pas d'await dans un composant

  • Un seul endroit pour l'asynchrone. Les attentes et les erreurs vivent dans le store ; le suivi « en cours / réussi / échoué » est fait par Super. La vue reste une fonction de ce qu'elle lit.
  • Pas de vue qui attend une réponse qui n'arrivera jamais. Si l'écran est démonté pendant la sauvegarde, rien ne casse : le store finit son travail et Super publie l'issue à qui l'écoute.
  • Tout le monde voit l'issue. Une réponse ne profite qu'à l'appelant ; un événement profite à tous les composants concernés.

Le cycle de vie d'une commande

Chaque commande passe par trois moments, que Super suit sans que le store ait rien à écrire :

MomentCe que Super exposeCôté composant
En coursLa méthode du store a commencé et n'a pas fini.this.counter.selectors.pending('increment') vaut true : re-rendu automatique.
RéussieLa méthode a fini sans erreur. Événement increment:done, avec le body (input) et le résultat (result).@on('counter', 'increment:done') onIncremented({ input, result }) { … }
ÉchouéeLa méthode a appelé this.fail(raison), ou levé une exception. Événement increment:failed, avec le body, la raison et l'erreur.@on('counter', 'increment:failed') onIncrementFailed({ input, reason }) { … }

pending redevient faux avant que :done ou :failed soit émis : un écouteur voit déjà la commande comme terminée.

Déclarer l'issue dans le contrat

Une commande déclare ce que produit son succès et pourquoi elle peut échouer, avec Outcome<Résultat, Raisons> :

  • Le résultat ({ count: number }) est ce que Super publie dans increment:done. Il ne revient jamais à celui qui a envoyé la commande.
  • Les raisons sont une liste fermée de codes, propres à ce contrat. Elles décrivent les refus prévus : 'unknown' pour un compteur hors catalogue, 'below-min' pour un compteur déjà à 0, 'storage' quand l'enregistrement échoue.
  • Une commande sans Outcome (load(): void) a quand même son cycle de vie : load:done sans résultat, et load:failed pour une exception inattendue.

Dans le store : retourner ou échouer

  • Chaque commande du contrat est une méthode du store, qui reçoit le body. implements Commands<CounterStore> vérifie qu'aucune ne manque et que leurs paramètres sont exactement ceux du contrat.
  • this.fail(raison) fait échouer la commande et ne revient pas. Seules les raisons déclarées par le contrat sont acceptées : this.fail('nope') ne compile pas.
  • La méthode retourne le résultat déclaré. L'oublier, ou retourner autre chose, ne compile pas.
  • Le code partagé s'écrit en méthode #privée : une méthode publique hors contrat est refusée par le compilateur.
  • Plus de drapeau « en cours » à remettre à zéro dans un catch, ni d'événement d'issue à émettre : Super s'en charge.

return this.fail(…) ou this.fail(…)

this.fail est déclaré comme ne revenant jamais (never), et le compilateur en tient compte : après un this.fail(…) conditionnel, le type se resserre. Le store du profil l'écrit avec return, qui rend la sortie visible à la lecture :

  • Les deux formes font exactement la même chose, à la compilation comme à l'exécution : this.fail interrompt la méthode dans tous les cas.
  • return this.fail(…) se lit mieux quand la suite dépend de la condition, comme ici ; un simple this.fail(…) suffit pour une garde, comme if (!this.selectors.find(id)) this.fail('unknown').
  • Un appel à this.fail dans une fonction fléchée (le .catch(() => this.fail('network')) ci-dessus) fait aussi échouer la commande : l'exception remonte jusqu'à elle.

L'échec inattendu : la raison 'error'

Une exception que le store n'a pas prévue (un bug, un undefined.x) fait aussi échouer la commande, avec la raison 'error' et l'exception dans error. L'interface ne reste donc jamais bloquée en « en cours ». Elle part aussi dans la console, alors qu'un échec déclaré, prévu, n'y apparaît pas.

Savoir qu'une commande est en cours : pending

  • pending est fourni par Super avec les sélecteurs du contrat : lu dans un @selector (ou dans render), il re-rend le composant quand une commande commence ou finit.
  • Le body se filtre champ par champ : { id: 'cafes' } correspond à toute commande dont le body a id === 'cafes'.
  • Si deux commandes identiques sont en cours, pending reste vrai jusqu'à la fin de la dernière.
  • Dans le store, this.selectors.pending(…) donne la même information ; hors composant, store.pending(…).
  • pending est réservé : un contrat ne peut pas déclarer de sélecteur de ce nom.

Écouter l'issue

  • Une méthode par événement : @on('counter', 'increment:done') appelle la méthode à chaque issue, avec un paramètre typé par l'événement ({ input, result }). Le nom de l'événement s'écrit tel quel, sans gabarit : pour plusieurs commandes, une méthode chacune, qui délèguent à une méthode privée. @on n'exige pas de @contract (voir les déclarations).
  • Le body est joint à l'issue (input) : l'écran de « Cafés » reconnaît ses propres commandes, sans que le store ait à recopier l'id.
  • La route se lit dans la méthode (this.counterId()), au moment où l'issue arrive : elle voit la route à jour.
  • Transforme l'issue en état local pour l'afficher : un événement ne dure pas, l'état local si (voir État local).
  • Rien à nettoyer : une méthode @on est appelée tant que le composant est monté, et plus après. Dans un composant écrit en .ts, l'équivalent est this.counter.on(…) dans un champ ou le constructeur ; on est interdit pendant render.

Une issue durable : l'état

Un événement est ponctuel : un composant monté plus tard ne le voit pas. Ce qui doit durer va dans l'état.

Par l'étatPar l'issue d'une commande
NatureUne donnée qui dure : une valeur, une erreur de chargement.Un fait ponctuel : « c'est enregistré », « c'est refusé ».
Exemplecounts, loadErrorMessageincrement:done, increment:failed
Côté composantLu avec @selector x = () => this.counter.selectors.…;.Écouté avec @on('counter', '…') sur une méthode.
Un composant monté plus tardVoit la valeur.Ne voit rien : l'événement est passé.

Dans l'exemple des compteurs, une erreur de chargement doit rester affichée sur la liste, même si on y revient plus tard : le store la range dans loadErrorMessage plutôt que de faire échouer load. Un refus d'écriture, lui, n'a de sens que sur le moment : c'est l'issue de la commande.

Les événements écrits à la main

Dans l'exemple Boutique : @core/cart/contract.ts, @core/cart/store.ts, @components/shop/index.super. Le panier émet emptied quand il devient vide, que ce soit par clear ou par le dernier remove.

Le cycle de vie couvre l'issue des commandes. Pour un fait qui n'est pas l'issue d'une commande (une synchronisation de fond terminée, une donnée arrivée d'un serveur), le contrat déclare ses propres événements, et le store les émet :

Le emit d'un composant n'est pas celui d'un store Un composant a aussi un this.emit, mais il émet les événements du composant vers son parent (ceux déclarés dans son type emits). Le store et ses abonnés ne le voient jamais. C'est voulu : un composant ne peut pas annoncer une écriture qui n'a jamais eu lieu.

Les commandes dans les tests

Hors composant (tests, autres stores, racine de composition), send renvoie une promesse : elle se résout quand la commande a réussi, et se rejette quand elle échoue, avec une CommandFailure qui porte la raison.
