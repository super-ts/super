Commands and events

The view sends and lets go. The store does the work, waits for what it has to wait for, then succeeds or fails. Super tracks each command from end to end: it knows when it is pending, and publishes its outcome.

The journey of a click

What happens when you click "+" on a counter's screen:

  1. CounterControls emits increment to its parent (component event).
  2. CounterScreen sends the command: this.counter.send('increment', { id: 'coffees' }). It waits for nothing.
  3. Super notes that increment is pending: this.counter.selectors.pending() becomes true, the screen re-renders with the buttons disabled.
  4. The store's increment method awaits this.#repository.save(…), updates counts and returns { count: 3 }.
  5. Super notes that the command is finished (the buttons are enabled again) and publishes increment:done with { input: { id: 'coffees' }, result: { count: 3 } }.
  6. The screen shows the new value (it changed in the state) and "Incremented: 3" (thanks to the event, received by its @on('counter', 'increment:done') method).

Sending a command

In a component, send returns void. There is nothing to wait for: writing await this.counter.send(…) makes no sense, and no data comes back to the caller.

Why no await in a component

  • One place for asynchrony. Waiting and errors live in the store; the "pending / succeeded / failed" tracking is done by Super. The view stays a function of what it reads.
  • No view waiting for a reply that will never come. If the screen is unmounted during the save, nothing breaks: the store finishes its work and Super publishes the outcome to whoever listens.
  • Everyone sees the outcome. A reply only benefits the caller; an event benefits every component concerned.

The lifecycle of a command

Each command goes through three moments, which Super tracks without the store having to write anything:

MomentWhat Super exposesComponent side
PendingThe store's method has started and has not finished.this.counter.selectors.pending('increment') is true: automatic re-render.
SucceededThe method finished without error. increment:done event, with the body (input) and the result (result).@on('counter', 'increment:done') onIncremented({ input, result }) { … }
FailedThe method called this.fail(reason), or threw an exception. increment:failed event, with the body, the reason and the error.@on('counter', 'increment:failed') onIncrementFailed({ input, reason }) { … }

pending becomes false again before :done or :failed is emitted: a listener already sees the command as finished.

Declaring the outcome in the contract

A command declares what its success produces and why it can fail, with Outcome<Result, Reasons>:

  • The result ({ count: number }) is what Super publishes in increment:done. It never comes back to whoever sent the command.
  • The reasons are a closed list of codes, specific to this contract. They describe the expected refusals: 'unknown' for a counter outside the catalogue, 'below-min' for a counter already at 0, 'storage' when saving fails.
  • A command without an Outcome (load(): void) still has its lifecycle: load:done without a result, and load:failed for an unexpected exception.

In the store: return or fail

  • Each command of the contract is a store method, which receives the body. implements Commands<CounterStore> checks that none is missing and that their parameters are exactly the contract's.
  • this.fail(reason) fails the command and does not return. Only the reasons declared by the contract are accepted: this.fail('nope') does not compile.
  • The method returns the declared result. Forgetting it, or returning something else, does not compile.
  • Shared code is written as a #private method: a public method outside the contract is refused by the compiler.
  • No more "pending" flag to reset in a catch, and no outcome event to emit: Super takes care of it.

return this.fail(…) or this.fail(…)

this.fail is declared as never returning (never), and the compiler takes it into account: after a conditional this.fail(…), the type narrows. The profile store writes it with return, which makes the exit visible when reading:

  • Both forms do exactly the same thing, at compile time as at runtime: this.fail interrupts the method in every case.
  • return this.fail(…) reads better when what follows depends on the condition, as here; a plain this.fail(…) is enough for a guard, like if (!this.selectors.find(id)) this.fail('unknown').
  • A call to this.fail inside an arrow function (the .catch(() => this.fail('network')) above) also fails the command: the exception propagates up to it.

With a code, the component can also react differently depending on the case: offering to free up space for 'storage', or displaying nothing for 'below-min'.

The unexpected failure: the 'error' reason

An exception the store did not expect (a bug, an undefined.x) also fails the command, with the reason 'error' and the exception in error. So the interface never stays stuck "pending". It also goes to the console, whereas a declared, expected failure does not show up there.

Knowing that a command is pending: pending

  • pending is supplied by Super with the contract's selectors: read in a @selector (or in render), it re-renders the component when a command starts or finishes.
  • The body is filtered field by field: { id: 'coffees' } matches any command whose body has id === 'coffees'.
  • If two identical commands are pending, pending stays true until the last one finishes.
  • In the store, this.selectors.pending(…) gives the same information; outside a component, store.pending(…).
  • pending is reserved: a contract cannot declare a selector with that name.

Listening to the outcome

  • One method per event: @on('counter', 'increment:done') calls the method on each outcome, with a parameter typed by the event ({ input, result }). The event name is written as is, without a pattern: for several commands, one method each, delegating to a private method. @on does not require a @contract (see the declarations).
  • The body is attached to the outcome (input): the "Coffees" screen recognises its own commands, without the store having to copy the id.
  • The route is read in the method (this.counterId()), when the outcome arrives: it sees the up-to-date route.
  • Turn the outcome into local state to display it: an event does not last, local state does (see Local state).
  • Nothing to clean up: an @on method is called as long as the component is mounted, and not after. In a component written in .ts, the equivalent is this.counter.on(…) in a field or the constructor; on is forbidden during render.

A lasting outcome: the state

An event is one-off: a component mounted later does not see it. What must last goes in the state.

Through the stateThrough a command's outcome
NatureData that lasts: a value, a load error.A one-off fact: "it is saved", "it is refused".
Examplecounts, loadErrorMessageincrement:done, increment:failed
Component sideRead with @selector x = () => this.counter.selectors.…;.Listened to with @on('counter', '…') on a method.

In the counters example, a load error must stay displayed on the list, even if you come back to it later: the store keeps it in loadErrorMessage rather than failing load. A write refusal, on the other hand, only makes sense at the moment: it is the command's outcome.

Hand-written events

In the Shop example: @core/cart/contract.ts, @core/cart/store.ts, @components/shop/index.super. The cart emits emptied when it becomes empty, whether through clear or through the last remove.

The lifecycle covers the outcome of commands. For a fact that is not a command's outcome (a background sync that finished, data arriving from a server), the contract declares its own events, and the store emits them:

A component's emit is not a store's A component also has a this.emit, but it emits the component's events to its parent (those declared in its emits type). The store and its subscribers never see it. This is intended: a component cannot announce a write that never happened.

Commands in tests

Outside a component (tests, other stores, composition root), send returns a promise: it resolves when the command has succeeded, and rejects when it fails, with a CommandFailure carrying the reason.
