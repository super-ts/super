Testing

Each building block is tested at its own level: the store without a DOM, the adapter on its own, the component with a fake store, the whole app with an in-memory router. And the typing guarantees have their own tests.

Configuration

Tests run under Vitest with happy-dom, a simulated DOM. They live next to the code they test (@core/counter/store.test.ts next to @core/counter/store.ts, @components/counter/index.test.ts next to the screen, index.super).

A test stays a .ts file, even for a component written in .super. Vitest reuses the plugins from vite.config.ts: the Super plugin compiles .super files there as in dev, and import { CounterControls } from './counter-controls' finds counter-controls.super.

Node 25 and later Node exposes a native localStorage that hides happy-dom's ("localStorage.clear is not a function"). The execArgv: ['--no-experimental-webstorage'] option disables it in the test workers.

Testing a store

A store is tested without a DOM, with an in-memory adapter. XStore.create(deps) returns the handle, as in main.ts; await send(…) waits for the command to finish, then you check the state, the selectors and the events.

  • store.selectors.x(…) reads the current state through the contract's selectors; store.state() gives the raw, frozen state.
  • store.pending(…) tells whether a command is pending: any (pending()), one command (pending('load')), or one command for a body (pending('increment', { id: 'coffees' })).
  • record(store, event) records the payloads, including lifecycle ones ('increment:done'): calls (all), last (the last one), stop() (stops listening).

A store that depends on another is tested with the real one: you create the cart, then the checkout that receives it as a dependency, exactly as in main.ts.

Testing an adapter

The localStorage adapter is tested against happy-dom's localStorage, or against any compatible object thanks to its storage option. Nothing from Super here: it is user-land.

Testing a component on its own

A presentational component, without a store, is mounted with its props; its events are listened to through on, typed by its emits. The component is a .super file, the test a .ts file that imports it without an extension.

mount

mount(Class, options) takes the class exported by the .super file (not an element already created), mounts it in document.body under a test application, waits for the first render and returns:

OptionRole
propsThe component's props, typed by its class.
storesThe stores to provide (real or fake), found by their contract name as with createApp.
routerA router, usually createRouter(Router, { mode: 'memory', initialPath }). A screen mounted on its own reads its route from it: initialPath: '/counters/coffees' gives it id === 'coffees'.
onListeners for the component's events, typed by its emits.
onErrorReceives the errors of mounted components, like createApp({ onError }). See Testing errors.
Return valueRole
containerThe container, to pass to testing-library's within().
elementThe mounted instance, typed by its class.
setProps(props)Changes the props and waits for the render.
unmount()Unmounts (done automatically by cleanup).

flush

Store notifications and renders are batched at the end of the task. After an action that changes a store without going through testing-library (an emit on a fake store, a send on a real one), await flush() lets the pending renders through. testing-library's findBy* wait on their own.

Testing a screen with a fake store

fakeStore('name', { state, commands? }) creates a store for the contract of that name, without an implementation. The screen finds it as it would find the real one, through @contract counter: that is what the rule "a component only knows the contract" allows. The given state is typed by the contract, and the contract's selectors read it normally.

Fake store memberRole
sentThe commands received, in order: { name, args }.
setState(patch)Changes the state, as the store would.
emit(name, payload)Emits a contract event, or a command's outcome ('decrement:failed'), as the store and Super would.
selectors, state(), on…The rest of a store's handle, like a real one.
commands (option)Implementations for some commands. The others are recorded and finish without publishing an outcome: it is up to the test to emit :done or :failed, with values that match the contract.

FakeCommands<'counter'> types these implementations by the contract name. Each one receives the body, then { fail }, and returns the result declared by the Outcome: Super then publishes the outcome as for a real store.

Testing the whole application

The app is assembled as in main.ts: real stores, adapters without latency, in-memory router. mount receives the shell, AppShell, which shows the route's screen.

Type tests: the *.test-d.ts files

Part of what Super promises is compile errors: an unknown route, a missing parameter, a screen with the wrong props. A Vitest test cannot observe that a line is rejected by the compiler. The *.test-d.ts files are there for that.

  • The "d" comes from .d.ts: these files test typing, not behaviour. It is the Vitest convention.
  • They are never run. It is npm run typecheck (super-tsc, which runs tsc) that compiles them.
  • Each // @ts-expect-error asserts "this line must be rejected". If a change makes it acceptable, compilation fails ("Unused '@ts-expect-error' directive").
  • npm run check runs the type check then the tests: these files are checked on every run.

The template of a .super file does not need type tests: npm run typecheck checks it directly (a child's props, attributes, events, interpolations). The types a test sees of a .super component (its props for mount, its emits for on) come from the virtual TypeScript, through the declaration super-tsc writes into .super/types/ (see Tooling).
