Ports et adapters

Les sources de données externes (localStorage, API HTTP, IndexedDB) ne sont pas un concept Super : ce sont de simples dépendances de tes stores. L'app d'exemples les organise en ports et adapters, un choix de projet : un localStorage pour les compteurs, un serveur simulé pour le formulaire, une vraie API HTTP (dummyjson.com) pour la table branchée du kit.

Le principe

  • Un port est une interface : ce dont le store a besoin, exprimé dans ses termes (« charger tous les compteurs », « enregistrer un compteur »).
  • Un adapter est une implémentation de ce port pour une technologie donnée.
  • Le store dépend du port, jamais d'un adapter.
  • La racine de composition choisit l'adapter.

Résultat : on change de stockage sans toucher au store, et on teste le store avec un adapter en mémoire.

Les brancher

Où les ranger

ports/ et adapters/ sont des dossiers user-land : Super ne les connaît pas. Tu peux les appeler autrement, ou mettre le port à côté du store, dans son dossier de @core/. Une règle de bon sens : un composant n'importe jamais un adapter. Le plugin ne l'interdit pas (les adapters sont en user-land), mais un composant qui appellerait un adapter contournerait le store, et perdrait l'état partagé et les événements.

Les erreurs des adapters

Un adapter peut échouer (quota dépassé, réseau coupé). C'est au store de décider comment le publier : loadErrorMessage dans l'état pour un chargement (l'erreur doit rester visible), une raison d'échec pour une écriture. Voir Stores : les erreurs.
