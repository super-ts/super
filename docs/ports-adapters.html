Ports and adapters

External data sources (localStorage, HTTP API, IndexedDB) are not a Super concept: they are plain dependencies of your stores. The examples app organises them into ports and adapters, a project choice: localStorage for the counters, a simulated server for the form, a real HTTP API (dummyjson.com) for the kit's wired table.

The principle

  • A port is an interface: what the store needs, expressed in its own terms ("load all counters", "save a counter").
  • An adapter is an implementation of that port for a given technology.
  • The store depends on the port, never on an adapter.
  • The composition root chooses the adapter.

The result: you change storage without touching the store, and you test the store with an in-memory adapter.

Wiring them

Where to put them

ports/ and adapters/ are user-land folders: Super does not know about them. You can name them differently, or put the port next to the store, in its @core/ folder. A common-sense rule: a component never imports an adapter. The plugin does not forbid it (adapters are in user-land), but a component that called an adapter would bypass the store, and lose the shared state and the events.

Adapter errors

An adapter can fail (quota exceeded, network down). It is up to the store to decide how to publish it: loadErrorMessage in the state for a load (the error must stay visible), a failure reason for a write. See Stores: errors.
