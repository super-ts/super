FAQ

The questions people ask when discovering Super, with a short answer and a link to the details.

Architecture

Why are the folders called @core and @components?

The @ prefix marks what belongs to Super: a prefixed folder follows Super's rules, a folder without a prefix is yours. $ was ruled out because a shell reads it as a variable (cd src/$core lands in src/). Details.

How do I import from @core without counting "../"?

Through aliases: import { CounterStore } from '@core/counter/store' in main.ts or a test, import type { CounterState } from '@core/counter/contract' from a component. The Vite plugin declares them by itself; for TypeScript, declare them in the paths of your tsconfig.json, each with a second target pointing to the virtual TypeScript of the .super files. Details.

Vite says "this module is not loaded". Why?

The architecture plugin rejected the module: a contract, a store or a component defined outside its folder, a component that imports something other than types from @core/, or a module in @core/ that imports @super-ts/dom. The message says which name is the problem. Move the file, go through @contract …;, or add a selector to the contract. The four rules.

How does a component find its store without importing it?

Through the name of its contract: @contract counter;. The Vite plugin writes the dictionary of contracts to src/@core/contracts.d.ts, which gives the compiler the selectors, commands and events of each one. On mount, the nearest application provides the store with that name. Details.

Why can't a component import a function from @core?

So that it sees a store only through its contract. A utility function (countOf, findCounter) or a constant (MIN_COUNT, the catalogue) becomes a selector of the contract: the component accesses it through this.counter.selectors. A domain rule unrelated to a store can also live in domain/, in user-land. What to put in a selector.

Where do I put a repository, an HTTP client, a port?

In user-land, wherever you like. The examples app uses ports/ for interfaces and adapters/ for implementations, but Super knows nothing about these folders. Ports and adapters.

Can I replace lit-html with another template engine?

No. lit-html is a deliberate but hidden dependency of Super: you write your components in .super, which the Vite plugin compiles into lit-html templates, without ever importing lit. Templates.

Why is a component a .super file and not a .ts?

So that its template is checked like the rest of the code: an unknown tag, a missing or extra prop, an event the child does not emit, an object displayed by mistake do not compile. A .super remains a TypeScript module: only the methods that contain elements and the component declarations (@tag, @prop, @emit, @title) change. Contracts, stores, routes and tests stay .ts. .super files.

My editor does not understand .super files. What do I do?

Hook up the language server for .super files (packages/lang-server): errors, completion, hover, go to definition. On the command line, npm run typecheck checks the .super files with the rest. Tooling.

Contracts and stores

Are state, commands and events required?

state yes; commands and events no. Watch out: a misspelt key is not reported. The three keys.

Are commands the actions that modify the state?

Often, but not necessarily: a command can also just call an adapter and emit an event. The rule that matters: only the store modifies its state, a component sends a command. commands.

Why does a command return nothing?

So that the view never waits. The store does the asynchronous work and publishes the result through its state or an event, which every component concerned sees. Why no await.

How do I know a command is pending, to disable a button?

With @selector incrementing = () => this.counter.selectors.pending('increment', { id: this.counterId() });: Super tracks each command, there is no flag to manage in the store. pending.

How do I know whether a command succeeded or failed?

Super publishes increment:done (with the body and the result) and increment:failed (with the body and the reason). The contract declares both with Outcome<Result, Reasons>. The lifecycle.

Do I have to write return this.fail(…)?

It is not required: this.fail is declared as never returning, and the type narrows after an if (!result.ok) this.fail(result.reason). The return only makes the exit visible when reading. Details.

What are reasons like 'unknown' | 'below-min' | 'storage' for?

They are the possible causes of failure, declared by the contract. The store fails with this.fail('below-min'), and the component maps each reason to the message of its choice. The compiler checks both sides. Failure reasons.

Do I publish the result through the state or through an event?

Through the state if it is data that lasts (a value, a "pending", a loading error). Through an event if it is a one-off fact ("saved", "refused"). The decision table.

Why not call the selectors on the contract?

A contract has no state: there can be several stores for the same contract. Selectors are therefore read on a store, already bound to its state: this.selectors.count(id) in the store, this.counter.selectors.count(id) in a component, store.selectors.count(id) in a test. Selectors.

Why do some selectors have no parameter?

A selector only takes a parameter if the answer depends on it. loadErrorMessage depends only on the global state, canDecrement depends on the counter. Without a parameter, it is passed as is: @selector loadError = this.counter.selectors.loadErrorMessage;. Details.

Can a store send a command to another store?

Yes, if it receives it as a dependency in its constructor: await this.#cart.send('clear'). It can wait for the processing to finish, but receives no data: it then reads the other store's state or listens to its events. Full example.

Can there be two stores for the same contract?

Not in the same application (error "two stores provided"). Yes in two separate or nested applications, and of course in tests, which create a fresh store for each case. Multiple applications.

Components

What is set up in the fields? How is it different from render?

The declarations in the class body run once, at construction: they request the stores (@contract), create the local state (@state), the reads (@selector), the references (@ref) and the forms (@form), and set the listeners (@on). render runs on every render and writes the elements to display. Set up, then render.

How do I know whether a line goes in a field or in render?

If it must exist only once for the instance (store, state, read, listener, handler): a declaration (@contract, @state, @selector, @on…) or a field. If it is recomputed from the current values (reading .value, the props, deciding, displaying): render. These declarations are not written in render; in a component written in .ts, Super throws an error if you call this.contract, this.state, this.selector or on during rendering. The line-by-line table.

Where do I run a command on mount, or set a listener on window?

In mounted(), called after the first render, on every mount: the example's shell sends this.counter.send('load') there. A listener on window takes { signal: this.signal }, and disappears on unmount. Examples.

Can I read a prop in the constructor?

Yes: Super sets the props before constructing the component, so they can be read from the fields onwards. A value copied at construction (a local state, the initial values of a form) does not follow later changes; for an always up-to-date value, read the prop (this.name) in render or in the function of a selector, recomputed on every render.

Why can't my prop be called title or id?

Because a component is an HTML element, and a prop is read through this.name: this.title, this.id or this.hidden already exist. The compiler rejects @prop title: string; ("'title' is already a property of HTML elements: choose another name"); choose a name that says what it is (heading, counterId). For the tab title, it is @title, a component declaration and not a prop. Names already taken.

My component does not update. Why?

  • You copied a store value into an ordinary field (in mounted, for example): it is frozen. Declare a @selector and read .value in render. The classic mistake.
  • Your selector does not read the value you display: the component only re-renders if the selector's value changes.
  • You read the local state with a copied value instead of calling this.local.get() in render.

When the store's state changes, is the view notified?

Yes. A selector subscribes the component; on every change, Super recomputes the value and re-renders if it has changed. A selector read directly in render subscribes in the same way: the component only re-renders if the value read has changed. Nothing to write on your side. Details.

Can a component read the store's raw state?

No. @contract counter; only gives the selectors, send and on: never the raw state, never the store instance. Details.

Why does the counter list have one component per row?

A list read in one block re-renders entirely as soon as a value changes. One component per row (counter-list-item.super) reads its own value and only re-renders for it. What counts as a change.

Why write null as string | null?

The type of the local state is inferred from the initial value: @state local = { message: null as string | null };. Without the as, the field would be of type null and could never receive text. Details.

Does this message go in the local state or in the store?

In the local state if it only concerns this component and can disappear with it. In the store if another component needs it or if it must survive navigation. The table.

Forms

How do I bind a form field to a value?

With @form edit = { … }; in the class, then <input {this.edit.field('email')} /> in the template. The kind of element decides the value: text, number (or null), boolean, array, file. All the kinds of field.

How do I handle radio buttons or a group of checkboxes?

Pass the value of each button or box as the second argument: field('plan', 'pro'), field('interests', 'sport'). Radios, checkboxes.

Can I use Zod or another validation library?

Yes: a rule is a plain function that returns true or a message. Super imposes nothing. Rules.

How do I display a server error under the right field?

Attach the command's failure reason to a field in failures.fields, or to the form in failures.form. Server errors.

How do I check a value on the server while the user types?

With checks: a store command, triggered after a pause in typing, whose stale responses are ignored. Asynchronous checks.

Why @form and not a <Form> component?

Because a form is component state: its values, its errors, its checks and its submission are read all over the template (this.edit.field('name'), this.edit.values(), the "Saving…" button). The tag already exists: it is the native <form>, connected with <form {this.edit.bind()}>. A <Form> component would hide this state and lose the typing of the fields. <Table> is a different case: a display component. A declaration rather than a component.

How do I handle a variable number of rows (phone numbers, addresses)?

Declare an array of objects in initial, then phones = this.edit.list('phones') in a field, with item.key as the loop key: for (const item of this.phones.items(); key item.key) { … }. Dynamic lists.

Events and asynchrony

Can I write await this.counter.send(…) in a component?

No: in a component, send returns void, there is nothing to wait for. The result comes back through the state or an event. Commands and events.

What is signal for? Do I need to pass it to on?

this.signal is aborted at the end of life: on unmount for a component, on dispose() for a store. It is only for listeners set outside Super, such as window.addEventListener('keydown', …, { signal: this.signal }) in mounted. Between Super and Super, never: listeners declared with @on, like those set by a store on a store received as a dependency, stop by themselves. A component's tools, a store that depends on another.

Can a component emit a store event, like increment:done?

No. The view given by @contract has no emit. The component's this.emit emits its own events, to its parent, on another channel. Who can emit.

Why does on appear in the parent and not in the child?

The child emits (this.emit('increment')), the parent listens (<CounterControls … on:increment={…} />). The child does not know who is listening, just as an HTML button does not know who listens to its click. emit and on.

How do I open a dialog and get the answer without await?

The parent opens the dialog by passing it a prop (question), the dialog answers with an event (answered). The full pattern.

What happens if a store command throws an error?

The command fails with the reason 'error': Super publishes name:failed with the exception in error, and the exception goes to the console. Outside a component, the promise from send is rejected. An expected failure is better written this.fail('reason'), which the view knows how to display. Errors.

Router

Do I have to declare the routes globally to type the links?

No. defineRouter returns a Router already typed by your paths, and the Vite plugin registers it under 'router' in src/@core/contracts.d.ts. A component builds its links with this.router.href('counter', { params: { id } }); Router.href is for code outside components. Declaring routes.

How does a screen read the identifier from the URL?

Through this.router.current, not through its props: this.router.current.params.id(), or @selector counterId = this.router.current.params.id; then this.counterId.value (a field cannot be called id: it is a property of HTML elements). The value is typed by the screen's route, without declaring anything: the Vite plugin links each screen to its route. Reading the route in the screen.

My param is a number: what happens on /counters/abc?

The route's screen is still displayed, with an id that is undefined, and isValid() returns false. The screen displays a message, or the route's guard redirects: ({ params }) => params.id.isValid() || { to: 'counters' }. An invalid query key, on the other hand, simply takes its default value. An invalid value in the URL.

How do I point a path to another page, for the time being?

Declare redirect({ to: 'home' }) instead of the screen, in .screens(…). Links to this path stay correct, and the day the page exists, you replace the redirect with the screen. Redirects.

How do I protect a page, for example one reserved for logged-in users?

With a guard, declared before the screens: .guards(({ read }) => ({ account: () => read('session').isLoggedIn() || { to: 'login' } })). It reads the store by the name of its contract, and the refused path does not enter the history. Guards.

Why are screens declared separately, in .screens(...)?

Because the type of the screens depends on Router (this.router reads it in contracts.d.ts), and Router contains the screens. With the paths set separately in defineRouter(...), and .screens(...) as the last call, the compiler types Router without reading the screens. A form that mixed paths and screens in the same object could not be typed: the router would fall back to any. .screens(...) must therefore stay the last call. Details.

Why does .screens(() => ({ … })) take a function?

To avoid a cycle at load time: routes.ts imports the screens, and a module that a screen imports can import routes.ts in turn (for Router.href, for example). The function delays reading the screens until the router is created, by createRouter, when everything is loaded. Details.

A link reloads the page instead of navigating. Why?

It is external, relative, has a target, a download or data-native attribute, or the click used a modifier key. Or it is rendered outside the application's root. Link interception.

Why does my screen's local state start from scratch when I change page?

Each change of path mounts a new instance of the screen, even for the same route with a different param. Data that must survive navigation goes in a store. RouterOutlet.

Errors

A component crashes and leaves a blank area. How do I display something else?

Give it a renderError(error) method, or give one to one of its ancestors. For all screens at once, declare the '!' screen in the router. What catches what.

renderError or the '!' screen: which one is displayed?

The one nearest to the component that crashed: its own renderError, then an ancestor's, then the '!' screen if the error reaches the RouterOutlet. A constructor error is only caught by an ancestor. The table.

Is an error in an on:click or an on listener caught?

It is reported to onError (phase 'event', 'listener', or 'mount' for mounted and unmounted), but the display does not change: an action that fails does not break the screen. Action errors.

How do I get back to the page after the '!' screen?

Any navigation closes it and mounts a fresh screen: another link, or a new click on the link of the page in error. The '!' screen.

How do I send errors to a tracking tool?

With onError in createApp: it receives every component error, caught or not, with the component, the phase and what caught it. onError.

Tests

What are *.test-d.ts files for, and why "-d"?

They are type tests, checked by npm run typecheck and never run. Each // @ts-expect-error asserts that a line must be rejected by the compiler. The "d" comes from .d.ts, it is Vitest's convention. Type tests.

Should I test the router or the selectors in my app?

No: how Super works is tested in the packages. Your app tests its own behaviour. Who tests what.

My test fails with "no store provided for the contract".

Pass the store, real (CounterStore.create(…)) or fake (fakeStore('counter', { state })), to mount(Component, { stores: [counter] }). If the component contains links or reads the router, pass router too. mount.

"localStorage.clear is not a function" in tests.

Node 25 exposes a native localStorage that hides happy-dom's. Add execArgv: ['--no-experimental-webstorage'] to the Vitest configuration. Configuration.
