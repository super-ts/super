Questions fréquentes

Les questions qu'on se pose en découvrant Super, avec une réponse courte et un lien vers le détail.

Architecture

Pourquoi les dossiers s'appellent @core et @components ?

Le préfixe @ marque ce qui appartient à Super : un dossier préfixé suit les règles de Super, un dossier sans préfixe est à toi. $ a été écarté parce qu'un shell le lit comme une variable (cd src/$core arrive dans src/). Détails.

Comment importer depuis @core sans compter les « ../ » ?

Par alias : import { CounterStore } from '@core/counter/store' dans main.ts ou un test, import type { CounterState } from '@core/counter/contract' depuis un composant. Le plugin Vite les déclare tout seul ; pour TypeScript, déclare-les dans le paths de ton tsconfig.json, chacun avec une seconde cible vers le TS virtuel des .super. Détails.

Vite affiche « ce module n'est pas chargé ». Pourquoi ?

Le plugin d'architecture a refusé le module : un contrat, un store ou un composant défini hors de son dossier, un composant qui importe autre chose que des types depuis @core/, ou un module de @core/ qui importe @super-ts/dom. Le message dit quel nom pose problème. Déplace le fichier, passe par @contract …;, ou ajoute un sélecteur au contrat. Les quatre règles.

Comment un composant trouve-t-il son store sans l'importer ?

Par le nom de son contrat : @contract counter;. Le plugin Vite écrit le dictionnaire des contrats dans src/@core/contracts.d.ts, ce qui donne au compilateur les sélecteurs, les commandes et les événements de chacun. Au montage, l'application la plus proche fournit le store de ce nom. Détails.

Pourquoi un composant ne peut-il pas importer une fonction de @core ?

Pour qu'il ne voie un store qu'à travers son contrat. Une fonction utilitaire (countOf, findCounter) ou une constante (MIN_COUNT, le catalogue) devient un sélecteur du contrat : le composant y accède par this.counter.selectors. Une règle métier sans lien avec un store peut aussi vivre dans domain/, en user-land. Quoi mettre dans un sélecteur.

Où mettre un repository, un client HTTP, un port ?

En user-land, où tu veux. L'app d'exemples utilise ports/ pour les interfaces et adapters/ pour les implémentations, mais Super ne connaît pas ces dossiers. Ports et adapters.

Peut-on remplacer lit-html par un autre moteur de templates ?

Non. lit-html est une dépendance assumée de Super, mais cachée : tu écris tes composants en .super, que le plugin Vite compile en gabarits lit-html, sans jamais importer lit. Templates.

Pourquoi un composant est-il un fichier .super et pas un .ts ?

Pour que son template soit vérifié comme le reste du code : une balise inconnue, une prop manquante ou en trop, un événement que l'enfant n'émet pas, un objet affiché par erreur ne compilent pas. Un .super reste un module TypeScript : seules les méthodes qui contiennent des éléments et les déclarations du composant (@tag, @prop, @emit, @title) changent. Contrats, stores, routes et tests restent des .ts. Les fichiers .super.

Mon éditeur ne comprend pas les fichiers .super. Que faire ?

Branche le serveur de langage des .super (packages/lang-server) : erreurs, complétion, survol, aller à la définition. En ligne de commande, npm run typecheck vérifie les .super avec le reste. Outillage.

Contrats et stores

state, commands et events sont-ils obligatoires ?

state oui ; commands et events non. Attention : une clé mal orthographiée n'est pas signalée. Les trois clés.

Les commandes sont-elles les actions qui modifient l'état ?

Souvent, mais pas forcément : une commande peut aussi seulement appeler un adapter et émettre un événement. La règle qui compte : seul le store modifie son état, un composant envoie une commande. commands.

Pourquoi une commande ne renvoie-t-elle rien ?

Pour que la vue n'attende jamais. Le store fait le travail asynchrone et publie le résultat par son état ou un événement, que tous les composants concernés voient. Pourquoi pas d'await.

Comment savoir qu'une commande est en cours, pour désactiver un bouton ?

Avec @selector incrementing = () => this.counter.selectors.pending('increment', { id: this.counterId() }); : Super suit chaque commande, il n'y a aucun drapeau à gérer dans le store. pending.

Comment savoir qu'une commande a réussi ou échoué ?

Super publie increment:done (avec le body et le résultat) et increment:failed (avec le body et la raison). Le contrat déclare l'un et l'autre avec Outcome<Résultat, Raisons>. Le cycle de vie.

Faut-il écrire return this.fail(…) ?

Ce n'est pas obligatoire : this.fail est déclaré comme ne revenant jamais, et le type se resserre après un if (!result.ok) this.fail(result.reason). Le return rend seulement la sortie visible à la lecture. Détails.

À quoi servent les raisons comme 'unknown' | 'below-min' | 'storage' ?

Ce sont les causes possibles d'échec, déclarées par le contrat. Le store échoue avec this.fail('below-min'), et le composant associe à chaque raison le message de son choix. Le compilateur vérifie les deux côtés. Les raisons d'échec.

Je publie le résultat par l'état ou par un événement ?

Par l'état si c'est une donnée qui dure (une valeur, un « en cours », une erreur de chargement). Par un événement si c'est un fait ponctuel (« enregistré », « refusé »). Le tableau de décision.

Pourquoi ne pas appeler les sélecteurs sur le contrat ?

Un contrat n'a pas d'état : il peut exister plusieurs stores pour le même contrat. Les sélecteurs se lisent donc sur un store, déjà liés à son état : this.selectors.count(id) dans le store, this.counter.selectors.count(id) dans un composant, store.selectors.count(id) dans un test. Sélecteurs.

Pourquoi certains sélecteurs n'ont pas de paramètre ?

Un sélecteur ne prend un paramètre que si la réponse en dépend. loadErrorMessage ne dépend que de l'état global, canDecrement dépend du compteur. Sans paramètre, il se passe tel quel : @selector loadError = this.counter.selectors.loadErrorMessage;. Détails.

Un store peut-il envoyer une commande à un autre store ?

Oui, s'il le reçoit en dépendance dans son constructeur : await this.#cart.send('clear'). Il peut attendre la fin du traitement, mais ne reçoit aucune donnée : il lit ensuite l'état de l'autre store ou écoute ses événements. Exemple complet.

Peut-on avoir deux stores pour le même contrat ?

Pas dans la même application (erreur « deux stores fournis »). Oui dans deux applications distinctes ou imbriquées, et bien sûr dans les tests, qui créent un store neuf à chaque cas. Plusieurs applications.

Composants

Qu'est-ce qui se prépare dans les champs ? Quelle différence avec render ?

Les déclarations du corps de la classe s'exécutent une fois, à la construction : elles demandent les stores (@contract), créent l'état local (@state), les lectures (@selector), les références (@ref) et les formulaires (@form), et posent les écouteurs (@on). render s'exécute à chaque rendu et écrit les éléments à afficher. Préparer, puis rendre.

Comment savoir si une ligne va dans un champ ou dans render ?

Si ça doit exister une seule fois pour l'instance (store, état, lecture, écouteur, handler) : une déclaration (@contract, @state, @selector, @on…) ou un champ. Si ça se recalcule à partir des valeurs du moment (lire .value, les props, décider, afficher) : render. Ces déclarations ne s'écrivent pas dans render ; dans un composant écrit en .ts, Super lève une erreur si tu appelles this.contract, this.state, this.selector ou on pendant le rendu. Le tableau ligne par ligne.

Où lancer une commande au montage, ou poser un écouteur sur window ?

Dans mounted(), appelé après le premier rendu, à chaque montage : la coquille de l'exemple y envoie this.counter.send('load'). Un écouteur sur window prend { signal: this.signal }, et disparaît au démontage. Exemples.

Puis-je lire une prop dans le constructeur ?

Oui : Super dépose les props avant de construire le composant, elles sont lisibles dès les champs. Une valeur copiée à la construction (un état local, les valeurs initiales d'un formulaire) ne suit pas les changements suivants ; pour une valeur toujours à jour, lis la prop (this.nom) dans render ou dans la fonction d'un selector, recalculée à chaque rendu.

Pourquoi ma prop ne peut-elle pas s'appeler title ou id ?

Parce qu'un composant est un élément HTML, et qu'une prop se lit par this.nom : this.title, this.id ou this.hidden existent déjà. Le compilateur refuse @prop title: string; (« « title » est déjà une propriété des éléments HTML : choisis un autre nom ») ; choisis un nom qui dit ce que c'est (heading, counterId). Pour le titre de l'onglet, c'est @title, une déclaration du composant et pas une prop. Les noms déjà pris.

Mon composant ne se met pas à jour. Pourquoi ?

  • Tu as copié une valeur du store dans un champ ordinaire (dans mounted, par exemple) : elle est figée. Déclare un @selector et lis .value dans render. L'erreur classique.
  • Ton selector ne lit pas la valeur que tu affiches : le composant ne se re-rend que si la valeur du sélecteur change.
  • Tu lis l'état local avec une valeur copiée au lieu d'appeler this.local.get() dans render.

Quand l'état du store change, la vue est-elle prévenue ?

Oui. Un selector abonne le composant ; à chaque changement, Super recalcule la valeur et re-rend si elle a changé. Un sélecteur lu directement dans render abonne de la même façon : le composant ne se re-rend que si la valeur lue a changé. Rien à écrire de ton côté. Détails.

Un composant peut-il lire l'état brut du store ?

Non. @contract counter; ne donne que les sélecteurs, send et on : jamais l'état brut, jamais l'instance du store. Détails.

Pourquoi la liste des compteurs a-t-elle un composant par ligne ?

Une liste lue d'un bloc se re-rend en entier dès qu'une valeur change. Un composant par ligne (counter-list-item.super) lit sa propre valeur et ne se re-rend que pour elle. Ce qui compte comme un changement.

Pourquoi écrire null as string | null ?

Le type de l'état local est déduit de la valeur initiale : @state local = { message: null as string | null };. Sans le as, le champ serait de type null et ne pourrait jamais recevoir de texte. Détails.

Ce message, je le mets dans l'état local ou dans le store ?

Dans l'état local s'il ne concerne que ce composant et peut disparaître avec lui. Dans le store si un autre composant en a besoin ou s'il doit survivre à la navigation. Le tableau.

Formulaires

Comment lier un champ de formulaire à une valeur ?

Avec @form edit = { … }; dans la classe, puis <input {this.edit.field('email')} /> dans le template. Le type d'élément décide de la valeur : texte, nombre (ou null), booléen, tableau, fichier. Tous les types de champs.

Comment gérer des boutons radio ou un groupe de cases à cocher ?

Passe la valeur de chaque bouton ou case en second argument : field('plan', 'pro'), field('interests', 'sport'). Radios, cases à cocher.

Puis-je utiliser Zod ou une autre bibliothèque de validation ?

Oui : une règle est une simple fonction qui renvoie true ou un message. Super n'impose rien. Les règles.

Comment afficher une erreur du serveur sous le bon champ ?

Rattache la raison d'échec de la commande à un champ dans failures.fields, ou au formulaire dans failures.form. Les erreurs du serveur.

Comment vérifier une valeur côté serveur pendant la saisie ?

Avec checks : une commande du store, déclenchée après une pause dans la frappe, dont les réponses périmées sont ignorées. Les vérifications asynchrones.

Pourquoi @form et pas un composant <Form> ?

Parce qu'un formulaire est de l'état du composant : ses valeurs, ses erreurs, ses vérifications et sa soumission sont lus partout dans le template (this.edit.field('name'), this.edit.values(), le bouton « Enregistrement… »). La balise existe déjà : c'est le <form> natif, relié par <form {this.edit.bind()}>. Un composant <Form> cacherait cet état et ferait perdre le typage des champs. <Table> est un autre cas : un composant d'affichage. Une déclaration plutôt qu'un composant.

Comment gérer un nombre variable de lignes (téléphones, adresses) ?

Déclare un tableau d'objets dans initial, puis phones = this.edit.list('phones') dans un champ, avec item.key comme clé de la boucle : for (const item of this.phones.items(); key item.key) { … }. Les listes dynamiques.

Événements et asynchrone

Je peux écrire await this.counter.send(…) dans un composant ?

Non : dans un composant, send renvoie void, il n'y a rien à attendre. Le résultat revient par l'état ou un événement. Commandes et événements.

À quoi sert signal ? Dois-je le passer à on ?

this.signal est avorté à la fin de vie : au démontage pour un composant, au dispose() pour un store. Il sert uniquement aux écouteurs posés hors de Super, comme window.addEventListener('keydown', …, { signal: this.signal }) dans mounted. Entre Super et Super, jamais : les écouteurs déclarés par @on, comme ceux posés par un store sur un store reçu en dépendance, s'arrêtent tout seuls. Les outils d'un composant, un store qui dépend d'un autre.

Un composant peut-il émettre un événement de store, comme increment:done ?

Non. La vue que donne @contract n'a pas d'emit. Le this.emit du composant émet ses propres événements, vers son parent, sur un autre canal. Qui peut émettre.

Pourquoi on apparaît dans le parent et pas dans l'enfant ?

L'enfant émet (this.emit('increment')), le parent écoute (<CounterControls … on:increment={…} />). L'enfant ne sait pas qui l'écoute, comme un bouton HTML ne sait pas qui écoute son click. emit et on.

Comment ouvrir un dialogue et récupérer la réponse sans await ?

Le parent ouvre le dialogue en lui passant une prop (question), le dialogue répond par un événement (answered). Le motif complet.

Que se passe-t-il si une commande du store lève une erreur ?

La commande échoue avec la raison 'error' : Super publie nom:failed avec l'exception dans error, et l'exception part dans la console. Hors composant, la promesse de send est rejetée. Un échec prévu s'écrit plutôt this.fail('raison'), que la vue sait afficher. Les erreurs.

Router

Faut-il déclarer les routes globalement pour typer les liens ?

Non. defineRouter renvoie un Router déjà typé par tes chemins, et le plugin Vite l'inscrit sous 'router' dans src/@core/contracts.d.ts. Un composant construit ses liens avec this.router.href('counter', { params: { id } }) ; Router.href sert au code hors composants. Déclarer les routes.

Comment un écran lit-il l'identifiant de l'URL ?

Par this.router.current, pas par ses props : this.router.current.params.id(), ou @selector counterId = this.router.current.params.id; puis this.counterId.value (un champ ne peut pas s'appeler id : c'est une propriété des éléments HTML). La valeur est typée par la route de l'écran, sans rien déclarer : le plugin Vite relie chaque écran à sa route. Lire la route dans l'écran.

Mon paramètre est un nombre : que se passe-t-il sur /counters/abc ?

L'écran de la route s'affiche quand même, avec un id qui vaut undefined, et isValid() renvoie false. L'écran affiche un message, ou le guard de la route redirige : ({ params }) => params.id.isValid() || { to: 'counters' }. Une clé de query invalide, elle, prend simplement sa valeur par défaut. Une valeur invalide dans l'URL.

Comment faire pointer un chemin vers une autre page, en attendant ?

Déclare redirect({ to: 'home' }) à la place de l'écran, dans .screens(…). Les liens vers ce chemin restent justes, et le jour où la page existe, tu remplaces la redirection par l'écran. Redirections.

Comment protéger une page, par exemple réservée aux utilisateurs connectés ?

Avec un guard, déclaré avant les écrans : .guards(({ read }) => ({ account: () => read('session').isLoggedIn() || { to: 'login' } })). Il lit le store par le nom de son contrat, et le chemin refusé n'entre pas dans l'historique. Guards.

Pourquoi les écrans sont-ils déclarés à part, dans .screens(...) ?

Parce que le type des écrans dépend de Router (this.router le lit dans contracts.d.ts), et que Router contient les écrans. Avec les chemins posés à part dans defineRouter(...), et .screens(...) en dernier appel, le compilateur type Router sans lire les écrans. Une forme qui mélangerait chemins et écrans dans un même objet ne pourrait pas être typée : le router retomberait en any. .screens(...) doit donc rester le dernier appel. Détails.

Pourquoi .screens(() => ({ … })) prend une fonction ?

Pour éviter un cycle au chargement : routes.ts importe les écrans, et un module qu'un écran importe peut importer routes.ts à son tour (pour Router.href, par exemple). La fonction retarde la lecture des écrans à la création du router, par createRouter, quand tout est chargé. Détails.

Un lien recharge la page au lieu de naviguer. Pourquoi ?

Il est externe, relatif, a un target, un attribut download ou data-native, ou le clic utilisait une touche de modification. Ou bien il est rendu hors de la racine de l'application. L'interception des liens.

Pourquoi l'état local de mon écran repart de zéro quand je change de page ?

Chaque changement de chemin monte une nouvelle instance de l'écran, même pour la même route avec un autre paramètre. Une donnée qui doit survivre à la navigation va dans un store. RouterOutlet.

Erreurs

Un composant plante et laisse une zone blanche. Comment afficher autre chose ?

Donne-lui une méthode renderError(error), ou à un de ses ancêtres. Pour tous les écrans d'un coup, déclare l'écran '!' dans le router. Qui rattrape quoi.

renderError ou écran '!' : lequel s'affiche ?

Le plus proche du composant qui a planté : son propre renderError, puis celui d'un ancêtre, puis l'écran '!' s'il atteint le RouterOutlet. Une erreur de constructeur n'est rattrapée que par un ancêtre. Le tableau.

Une erreur dans un on:click ou un écouteur on est-elle rattrapée ?

Elle est signalée à onError (phase 'event', 'listener', ou 'mount' pour mounted et unmounted), mais l'affichage ne change pas : une action qui échoue ne casse pas l'écran. Les erreurs d'action.

Comment revenir à la page après l'écran '!' ?

Toute navigation le referme et remonte un écran neuf : un autre lien, ou un nouveau clic sur le lien de la page en erreur. L'écran '!'.

Comment envoyer les erreurs à un outil de suivi ?

Avec onError dans createApp : il reçoit toute erreur de composant, rattrapée ou non, avec le composant, la phase et ce qui l'a rattrapée. onError.

Tests

À quoi servent les fichiers *.test-d.ts, et pourquoi « -d » ?

Ce sont des tests de types, vérifiés par npm run typecheck et jamais exécutés. Chaque // @ts-expect-error affirme qu'une ligne doit être refusée par le compilateur. Le « d » vient de .d.ts, c'est la convention de Vitest. Tests de types.

Dois-je tester le router ou les sélecteurs dans mon app ?

Non : le fonctionnement de Super est testé dans les paquets. Ton app teste son propre comportement. Qui teste quoi.

Mon test échoue avec « aucun store fourni pour le contrat ».

Passe le store, vrai (CounterStore.create(…)) ou faux (fakeStore('counter', { state })), à mount(Composant, { stores: [counter] }). Si le composant contient des liens ou lit le router, passe aussi router. mount.

« localStorage.clear is not a function » dans les tests.

Node 25 expose un localStorage natif qui masque celui de happy-dom. Ajoute execArgv: ['--no-experimental-webstorage'] à la configuration de Vitest. Configuration.
