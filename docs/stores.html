Stores

Un store implémente un contrat. Il garde l'état, traite les commandes, attend ce qu'il doit attendre (un adapter, le réseau), puis met à jour son état et annonce ce qui s'est passé.

Définir un store

Un store vit dans src/@core/<nom>/store.ts, à côté de son contrat. Il étend SuperStore<CounterContract> : la classe du contrat ne s'importe que comme type, le lien à l'exécution passe par le nom donné à super({ contract: 'counter' }).

Le constructeur : contrat, état initial, dépendances

Le constructeur reçoit les dépendances et appelle super avec deux choses :

  • contract : le nom du contrat implémenté, celui de son super({ name }). Un nom inconnu, ou celui d'un autre contrat, ne compile pas.
  • initialState : l'état de départ, conforme au state du contrat. Il est copié à chaque create() : deux instances ne partagent jamais leur état.

Le constructeur range ses dépendances dans des champs #privés et peut écouter les stores reçus (voir plus bas). Il ne lit ni ne modifie l'état : this.get(), this.set() ou this.send() y lèvent une erreur. L'état n'existe qu'une fois le store créé.

Les commandes : une méthode par commande

Chaque commande du contrat est une méthode publique du store, du même nom. implements Commands<CounterStore> fait vérifier le tout par le compilateur :

  • Une méthode pour chaque commande : en oublier une ne compile pas.
  • Les paramètres du contrat, exactement : increment({ id }: { id: string }). Annote-les à la main, TypeScript n'infère pas les paramètres d'une méthode de classe. Un paramètre plus étroit ({ id: 'cafes' }) ne compile pas.
  • Synchrone ou asynchrone : une méthode peut être async. C'est dans le store, et seulement là, qu'on attend un adapter.
  • Elle retourne le résultat déclaré par l'Outcome de sa commande (rien pour une commande void), ou échoue avec this.fail(raison). Super publie l'issue (increment:done, increment:failed) et suit la commande en cours : pas de drapeau à gérer. Voir Déclarer l'issue.
  • Aucune autre méthode publique : le code partagé entre commandes s'écrit en méthode #privée, comme #write. Une méthode publique hors contrat ne compile pas.

Sans implements Commands<Self>, rien de cela n'est vérifié : Super prendrait toute méthode publique pour une commande. Garde-le sur chaque store.

Les outils

Le store hérite d'outils protected, utilisables dans ses méthodes. Ces noms sont réservés.

OutilRôle
this.get()L'état courant, gelé en profondeur : une mutation en place (this.get().items.push(x)) lève une erreur. On le remplace avec set.
this.selectorsLes sélecteurs du contrat, état fourni : this.selectors.count(id). Chaque appel relit l'état courant. Plus this.selectors.pending(…) pour les commandes en cours.
this.set(patch)Fusionne le patch dans l'état (un niveau). Les champs que le patch ne touche pas gardent leur référence : c'est ce qui permet à Super de savoir ce qui a changé. Accepte un objet ou une fonction (état) => patch. L'état est mis à jour tout de suite ; les abonnés sont prévenus une seule fois à la fin de la tâche, même après plusieurs set.
this.emit(nom, payload?)Annonce un événement déclaré dans events (pas l'issue d'une commande : Super la publie). Le payload est typé ; un événement void s'émet sans argument.
this.send(nom, body?)Envoie une commande de ce même store, suivie par Super comme une autre (en cours, :done, :failed). Pour partager du code sans ce suivi, appelle une méthode #privée.
this.fail(raison)Fait échouer la commande en cours avec une raison déclarée. Ne revient pas. Le compilateur accepte les raisons de toutes les commandes du contrat, pas seulement celles de la commande en cours.
this.signalAbortSignal avorté par dispose(). Inutile pour les stores reçus en dépendance (voir plus bas) ; il sert aux écouteurs posés hors de Super, comme un window.addEventListener('online', …, { signal: this.signal }).

Les dépendances

Les dépendances sont les paramètres du constructeur. create(…) prend exactement ces arguments, avec leurs types.

Un store sans dépendance a un constructeur sans paramètre et se crée avec create(), comme CartStore.create().

Créer une instance : le handle

Déclarer la classe ne crée rien. C'est CounterStore.create(deps) qui fabrique une instance, en général dans main.ts ou dans un test. Il renvoie un handle, jamais l'instance : les méthodes du store ne s'appellent pas directement, elles se déclenchent par send.

MembreRôle
state()L'état courant, figé.
selectorsLes sélecteurs du contrat, lus sur l'état courant, plus pending(…).
send(nom, body?)Envoie une commande. La promesse ne porte aucune donnée : elle se résout si la commande réussit, et se rejette si elle échoue (avec une CommandFailure qui porte la raison pour un échec déclaré), si la commande est inconnue ou si le store est disposé.
on(nom, écouteur, { signal }?)Écoute un événement déclaré, ou le cycle de vie d'une commande (increment:done, increment:failed). Retourne la fonction de désabonnement.
pending(commande?, body?)Une commande est-elle en cours ? Toutes, une commande, ou une commande pour un body.
subscribe(écouteur, { signal }?)Écoute chaque changement d'état (regroupés par tâche).
dispose()Retire les écouteurs internes ; les send suivants sont rejetés.
contractLe contrat lu par Super (son nom), utile au fournisseur de createApp.
Le handle complet n'est pas pour les composants Les composants reçoivent une vue réduite par @contract counter; : selectors, send() (qui renvoie void) et on(), jamais l'état brut ; ils écoutent ses événements par une méthode @on('counter', 'increment:done'). Le handle complet sert aux tests, à la racine de composition et aux autres stores. Son type se déduit du nom du contrat : StoreOfContract<'counter'>.

subscribe : être prévenu de chaque changement d'état

Dans l'exemple Boutique : main.ts, adapters/saved-cart.ts. Le panier est enregistré dans le localStorage à chaque changement, et survit au rechargement de la page.

subscribe appelle ta fonction après chaque changement d'état, avec le nouvel état (plusieurs set dans la même tâche ne donnent qu'un appel). Il renvoie une fonction qui arrête l'écoute.

C'est l'usage type de subscribe : synchroniser l'état avec un système extérieur (un stockage, un outil d'analytics, un autre onglet), hors de tout composant, sans que le store le sache. CartStore reçoit seulement ses quantités de départ ({ quantities }) et ignore où elles sont gardées ; changer de stockage ne touche que main.ts et l'adapter.

Le compteur fait autrement, et à raison : son store parle à un port, CounterRepository (voir Les dépendances), parce que la persistance fait partie de son métier. Le chargement est asynchrone, une écriture peut échouer, et l'écran doit l'afficher : ces cas passent par les commandes et l'état du store. Quand le stockage n'est qu'un reflet de l'état, sans erreur à remonter ni donnée à attendre, subscribe suffit.

Dans un composant, tu n'en as pas besoin : @selector fait la même chose en plus fin (seulement quand la valeur lue change) et se désabonne tout seul au démontage. subscribe sert au code hors composants : main.ts, un outil de journalisation pendant le développement, un test qui compte les changements.

dispose : mettre fin à la vie du store

Dans l'exemple Widget : timer-widget.ts. Fermer le minuteur libère son application et son store.

dispose retire les écouteurs internes du store et avorte son signal : s'il écoutait un autre store, cette écoute s'arrête. Les commandes envoyées ensuite sont rejetées.

Dans une app classique, les stores vivent aussi longtemps que la page : tu n'appelles jamais dispose. Il sert aux stores qui vivent moins longtemps : un widget créé avec sa propre application puis retiré de la page, un store créé pour une session et libéré à sa fin, ou un test qui vérifie qu'un store libéré refuse les commandes.

Un store qui dépend d'un autre store

Dans l'exemple Boutique : checkout/store.ts, checkout/store.test.ts. Le store de commande reçoit le panier, le lit, lui envoie clear et écoute ses événements.

Un store peut recevoir un autre store en dépendance, écouter ses événements ou lui envoyer des commandes. Le type de la dépendance se déduit du nom du contrat : StoreOfContract<'cart'>. Rien à nettoyer : Super lie les on et subscribe des stores reçus en dépendance à la durée de vie du store qui les reçoit. L'écoute s'arrête d'elle-même à son dispose().

L'écoute se pose dans le constructeur, mais son écouteur ne s'exécute qu'après create : il peut alors appeler this.set.

Envoyer une commande à un autre store

Un store peut aussi envoyer des commandes au store qu'il reçoit, et attendre la fin du traitement : on est dans un store, c'est le seul endroit où l'on attend.

  • Pas de donnée en retour : la promesse de send dit seulement « c'est fini » (et se rejette si la commande échoue). Pour connaître le résultat, lis l'autre store ensuite, ou écoute ses événements.
  • Lire l'autre store : this.#cart.selectors passe par ses sélecteurs. this.selectors ne couvre que le store lui-même.
  • Un seul sens : le panier est créé avant et passé à la création. Deux stores ne peuvent pas dépendre l'un de l'autre ; si le panier doit réagir au checkout, il écoute un événement du checkout au lieu de le recevoir en dépendance.
Au premier niveau des dépendances Super reconnaît les stores passés directement dans l'objet de dépendances, premier argument du constructeur ({ cart }). Un store rangé plus profond ({ stores: { cart } }) n'est pas lié : garde les stores au premier niveau.

Les erreurs

Un composant envoie ses commandes sans attendre : c'est donc le store qui décide comment une erreur se publie.

  • Un refus prévu (compteur inconnu, déjà à 0, stockage plein) : this.fail(raison), avec une raison déclarée dans l'Outcome. Le composant écoute :failed et affiche le message de son choix.
  • Une erreur qui doit rester visible, même pour un écran monté plus tard : dans l'état, comme loadErrorMessage.
  • Une exception inattendue : rien à faire. La commande échoue avec la raison 'error', pending redevient faux, et l'exception part dans la console.
SituationEffet
Commande absente du storesend se rejette : « commande inconnue "x" sur le store "counter" ».
Store disposésend se rejette : « store "counter" disposé : commande "x" refusée ».
Méthode qui appelle this.fail('storage'):failed avec reason: 'storage' ; la promesse de send se rejette avec une CommandFailure.
Méthode qui lève une exception:failed avec reason: 'error' et l'exception ; la promesse de send se rejette avec elle.
this.get(), this.set() ou this.send() dans le constructeurErreur à create : l'état n'existe qu'une fois le store créé.
