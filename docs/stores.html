Stores

A store implements a contract. It holds the state, handles the commands, waits for what it has to wait for (an adapter, the network), then updates its state and announces what happened.

Defining a store

A store lives in src/@core/<name>/store.ts, next to its contract. It extends SuperStore<CounterContract>: the contract class is only imported as a type, the runtime link goes through the name given to super({ contract: 'counter' }).

The constructor: contract, initial state, dependencies

The constructor receives the dependencies and calls super with two things:

  • contract: the name of the implemented contract, the one in its super({ name }). An unknown name, or another contract's name, does not compile.
  • initialState: the starting state, matching the contract's state. It is copied on every create(): two instances never share their state.

The constructor stores its dependencies in #private fields and can listen to the stores it receives (see below). It neither reads nor changes the state: this.get(), this.set() or this.send() throw an error there. The state only exists once the store is created.

Commands: one method per command

Each command of the contract is a public method of the store, with the same name. implements Commands<CounterStore> has the compiler check it all:

  • One method for each command: forgetting one does not compile.
  • Exactly the contract's parameters: increment({ id }: { id: string }). Annotate them by hand, TypeScript does not infer the parameters of a class method. A narrower parameter ({ id: 'coffees' }) does not compile.
  • Synchronous or asynchronous: a method can be async. The store, and only the store, is where you wait for an adapter.
  • It returns the result declared by its command's Outcome (nothing for a void command), or fails with this.fail(reason). Super publishes the outcome (increment:done, increment:failed) and tracks the pending command: no flag to manage. See Declaring the outcome.
  • No other public method: code shared between commands is written as a #private method, like #write. A public method outside the contract does not compile.

Without implements Commands<Self>, none of this is checked: Super would take any public method for a command. Keep it on every store.

The tools

The store inherits protected tools, usable in its methods. These names are reserved.

ToolRole
this.get()The current state, deeply frozen: an in-place mutation (this.get().items.push(x)) throws an error. You replace it with set.
this.selectorsThe contract's selectors, with the state supplied: this.selectors.count(id). Each call rereads the current state. Plus this.selectors.pending(…) for pending commands.
this.set(patch)Merges the patch into the state (one level). Fields the patch does not touch keep their reference: that is how Super knows what changed. Accepts an object or a function (state) => patch. The state is updated right away; subscribers are notified only once at the end of the task, even after several set calls.
this.emit(name, payload?)Announces an event declared in events (not a command's outcome: Super publishes that). The payload is typed; a void event is emitted without an argument.
this.send(name, body?)Sends a command of this same store, tracked by Super like any other (pending, :done, :failed). To share code without this tracking, call a #private method.
this.fail(reason)Fails the pending command with a declared reason. Does not return. The compiler accepts the reasons of every command in the contract, not only those of the pending command.
this.signalAbortSignal aborted by dispose(). Not needed for stores received as dependencies (see below); it is for listeners added outside Super, such as window.addEventListener('online', …, { signal: this.signal }).

Dependencies

Dependencies are the constructor's parameters. create(…) takes exactly these arguments, with their types.

A store without dependencies has a constructor without parameters and is created with create(), like CartStore.create().

Creating an instance: the handle

Declaring the class creates nothing. CounterStore.create(deps) is what builds an instance, usually in main.ts or in a test. It returns a handle, never the instance: the store's methods are not called directly, they are triggered by send.

MemberRole
state()The current state, frozen.
selectorsThe contract's selectors, read on the current state, plus pending(…).
send(name, body?)Sends a command. The promise carries no data: it resolves if the command succeeds, and rejects if it fails (with a CommandFailure carrying the reason for a declared failure), if the command is unknown or if the store is disposed.
on(name, listener, { signal }?)Listens to a declared event, or to a command's lifecycle (increment:done, increment:failed). Returns the unsubscribe function.
pending(command?, body?)Is a command pending? Any command, one command, or one command for a body.
subscribe(listener, { signal }?)Listens to every state change (batched per task).
dispose()Removes the internal listeners; later send calls are rejected.
contractThe contract read by Super (its name), useful to the createApp provider.
The full handle is not for components Components receive a reduced view through @contract counter;: selectors, send() (which returns void) and on(), never the raw state; they listen to its events through an @on('counter', 'increment:done') method. The full handle is for tests, the composition root and other stores. Its type is inferred from the contract's name: StoreOfContract<'counter'>.

subscribe: being notified of every state change

In the Shop example: main.ts, adapters/saved-cart.ts. The cart is saved to localStorage on every change, and survives a page reload.

subscribe calls your function after every state change, with the new state (several set calls in the same task give only one call). It returns a function that stops listening.

This is the typical use of subscribe: syncing the state with an external system (a storage, an analytics tool, another tab), outside any component, without the store knowing. CartStore only receives its starting quantities ({ quantities }) and does not know where they are kept; changing storage only touches main.ts and the adapter.

The counter does it differently, and rightly so: its store talks to a port, CounterRepository (see Dependencies), because persistence is part of its job. Loading is asynchronous, a write can fail, and the screen must show it: these cases go through the store's commands and state. When storage is only a reflection of the state, with no error to report and no data to wait for, subscribe is enough.

In a component, you do not need it: @selector does the same thing more finely (only when the value read changes) and unsubscribes by itself on unmount. subscribe is for code outside components: main.ts, a logging tool during development, a test that counts changes.

dispose: ending the store's life

In the Widget example: timer-widget.ts. Closing the timer releases its application and its store.

dispose removes the store's internal listeners and aborts its signal: if it was listening to another store, that listening stops. Commands sent afterwards are rejected.

In a typical app, stores live as long as the page: you never call dispose. It is for stores that live shorter lives: a widget created with its own application then removed from the page, a store created for a session and released at its end, or a test that checks that a released store refuses commands.

A store that depends on another store

In the Shop example: checkout/store.ts, checkout/store.test.ts. The checkout store receives the cart, reads it, sends it clear and listens to its events.

A store can receive another store as a dependency, listen to its events or send it commands. The type of the dependency is inferred from the contract's name: StoreOfContract<'cart'>. Nothing to clean up: Super ties the on and subscribe of stores received as dependencies to the lifetime of the store receiving them. Listening stops by itself on its dispose().

The listener is added in the constructor, but it only runs after create: it can then call this.set.

Sending a command to another store

A store can also send commands to the store it receives, and wait for the processing to finish: we are in a store, the only place where you wait.

  • No data in return: the promise from send only says "it is done" (and rejects if the command fails). To know the result, read the other store afterwards, or listen to its events.
  • Reading the other store: this.#cart.selectors goes through its selectors. this.selectors only covers the store itself.
  • One direction only: the cart is created first and passed at creation. Two stores cannot depend on each other; if the cart must react to the checkout, it listens to a checkout event instead of receiving it as a dependency.
At the top level of the dependencies Super recognises the stores passed directly in the dependency object, the constructor's first argument ({ cart }). A store nested deeper ({ stores: { cart } }) is not tied: keep stores at the top level.

Errors

A component sends its commands without waiting: so the store decides how an error is published.

  • An expected refusal (unknown counter, already at 0, storage full): this.fail(reason), with a reason declared in the Outcome. The component listens to :failed and shows the message of its choice.
  • An error that must stay visible, even for a screen mounted later: in the state, like loadErrorMessage.
  • An unexpected exception: nothing to do. The command fails with the reason 'error', pending becomes false again, and the exception goes to the console.
SituationEffect
Command missing from the storesend rejects: "[super] unknown command "x" on the store "counter"".
Store disposedsend rejects: "[super] store "counter" disposed: command "x" rejected".
Method that calls this.fail('storage'):failed with reason: 'storage'; the promise from send rejects with a CommandFailure.
Method that throws an exception:failed with reason: 'error' and the exception; the promise from send rejects with it.
