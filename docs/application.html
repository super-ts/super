Application

The composition root, main.ts, is the only place that chooses the adapters, creates the stores and the router, and provides them to the components.

The composition root

  1. Create the stores with XStore.create(deps): this is where you choose localStorage, an HTTP API or an in-memory version, and pass a store to the one that depends on it (checkout receives cart). create returns the store handle, never the class instance.
  2. Create the router from the Router declared in routes.ts, with the frame for the tab title (title: { default, suffix }, see The page title).
  3. Create the application on a root element, providing it with stores and router.
  4. Mount the root component, created by AppShell.create(). main.ts stays a .ts file: it has no template, so it creates the component with create() instead of writing <AppShell />. The import @components/app-shell, without an extension, finds app-shell/index.super.

main.ts is user-land: Super imposes nothing on it. No injection container, no hidden configuration: the whole assembly can be read in this file. It can also use the handles directly, as here with cart.subscribe, which saves the cart to localStorage on every change (through the adapter adapters/saved-cart.ts): the cart read back at startup (CartStore.create({ quantities: savedCart.load() })) thus survives a page reload.

This is a good use of subscribe: syncing state with an external system (storage, analytics, another tab), outside any component, without the store knowing. CartStore knows nothing about storage, the composition root wires it in. The counter does the opposite: its store talks to a port, CounterRepository, because persistence is part of its domain (asynchronous loading, errors to display). See subscribe.

How a component finds its store

A component declares @contract counter;. When it mounts, it asks the DOM, walking up from itself: "who provides a store for the contract counter?". The nearest application that has one answers. In practice:

  • A component works anywhere under the root, at any depth, without passing it the store as props.
  • The contract name is the key: the one in super({ name: 'counter' }) in @core/counter/contract.ts. The component imports neither the contract nor the store; the Vite plugin rejects two contracts with the same name and generates @core/contracts.d.ts, which types @contract counter (and this.contract('counter') in a component written in .ts).
  • A component mounted without a store for that name throws an explicit error (phase setup): "no store provided for the contract "counter". Add it to createApp({ stores }) or to mount(..., { stores })".

Multiple applications

In the Widget example: widgets/timer-widget.ts, @components/widget/index.super. The timer lives in a second application, nested in the first, with its own store.

You can create several applications, and even nest them: the one nearest to the component answers first. This is useful for a widget that has its own stores in the middle of a page. Only one store per contract in an application Providing two stores for the same contract to the same application throws an error: "two stores provided for the contract "counter"".
