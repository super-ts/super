Brancher l'application

La racine de composition, main.ts, est le seul endroit qui choisit les adapters, crée les stores et le router, et les fournit aux composants.

La racine de composition

  1. Créer les stores avec XStore.create(deps) : c'est ici qu'on choisit localStorage, une API HTTP ou une version en mémoire, et qu'on passe un store à celui qui en dépend (checkout reçoit cart). create renvoie le handle du store, jamais l'instance de la classe.
  2. Créer le router à partir du Router déclaré dans routes.ts, avec le cadre du titre de l'onglet (title: { default, suffix }, voir Le titre de la page).
  3. Créer l'application sur un élément racine, en lui fournissant stores et router.
  4. Monter le composant racine, créé par AppShell.create(). main.ts reste un fichier .ts : il n'a pas de template, il crée le composant par create() au lieu de l'écrire <AppShell />. L'import @components/app-shell, sans extension, trouve app-shell/index.super.

main.ts est du user-land : Super ne lui impose rien. Pas de conteneur d'injection, pas de configuration cachée : tout l'assemblage se lit dans ce fichier. Il peut aussi utiliser les handles directement, comme ici cart.subscribe, qui enregistre le panier dans le localStorage à chaque changement (par l'adapter adapters/saved-cart.ts) : le panier relu au démarrage (CartStore.create({ quantities: savedCart.load() })) survit ainsi au rechargement de la page.

C'est un bon usage de subscribe : synchroniser l'état avec un système extérieur (stockage, analytics, autre onglet), hors de tout composant, sans que le store le sache. CartStore ne connaît pas le stockage, c'est la racine de composition qui le branche. Le compteur fait l'inverse : son store parle à un port, CounterRepository, parce que la persistance fait partie de son métier (chargement asynchrone, erreurs à afficher). Voir subscribe.

Comment un composant trouve son store

Un composant déclare @contract counter;. À son montage, il demande au DOM, en remontant depuis lui-même : « qui fournit un store pour le contrat counter ? ». L'application la plus proche qui en a un répond. Conséquences pratiques :

  • Un composant fonctionne partout sous la racine, à n'importe quelle profondeur, sans qu'on lui passe le store en props.
  • Le nom du contrat sert de clé : celui de super({ name: 'counter' }) dans @core/counter/contract.ts. Le composant n'importe ni le contrat ni le store ; le plugin Vite refuse deux contrats du même nom et génère @core/contracts.d.ts, qui type @contract counter (et this.contract('counter') dans un composant écrit en .ts).
  • Un composant monté sans store pour ce nom lève une erreur explicite (phase setup) : « aucun store fourni pour le contrat "counter". Ajoute-le à createApp({ stores }) ou à mount(..., { stores }) ».

Plusieurs applications

Dans l'exemple Widget : widgets/timer-widget.ts, @components/widget/index.super. Le minuteur vit dans une seconde application, imbriquée dans la première, avec son propre store.

On peut créer plusieurs applications, et même les imbriquer : la plus proche du composant répond en premier. C'est utile pour un widget qui a ses propres stores au milieu d'une page. Un seul store par contrat dans une application Fournir deux stores pour le même contrat à la même application lève une erreur : « deux stores fournis pour le contrat "counter" ».
