Ce que le compilateur vérifie

La plupart des erreurs d'usage de Super sont détectées avant l'exécution : par TypeScript, ou par le plugin Vite. Cette page liste ce qui est vérifié, où, et ce qui ne l'est pas.

Sauf la section sur les templates, chaque extrait ci-dessous vient des tests de types du dépôt (packages/*/src/*.test-d.ts) : chaque @ts-expect-error y fait échouer npm run typecheck si l'erreur attendue disparaît. Les extraits utilisent leur contrat d'essai basket : commandes add({ sku }), clear() et save({ id }) (qui déclare Outcome<{ count: number }, 'empty' | 'offline'>), événements emptied et saved: { id }, sélecteurs quantity(sku), count(), entries().

Contrats et stores

  • Une commande déclarée avec une réponse directe, ou avec plusieurs paramètres.
  • Un super({ contract }) qui nomme un contrat inconnu, ou un état initial non conforme.
  • Avec implements Commands<Self> : une commande sans méthode, une méthode aux paramètres différents de ceux du contrat, une méthode qui renvoie autre chose que le résultat déclaré (ou qui l'oublie), une méthode publique hors contrat.
  • Un événement inconnu, un payload mal typé ou oublié ; une raison d'échec inconnue du contrat ; une commande inconnue dans this.send.
  • Des dépendances manquantes ou mal typées à la création.

Templates des fichiers .super

Le template d'un composant .super est vérifié par npm run typecheck (super-tsc), et chaque erreur est rapportée à sa position dans le .super. L'extrait vient du projet d'essai de packages/lang : chaque ligne marquée ERREUR doit être signalée, et aucune autre (packages/lang/src/check.test.ts) ; il y en a 16. Greeting y est un composant aux props { name: string }, qui émet closed ; Panel déclare @prop heading: string;, @prop content: Children; et @prop footer?: Children;.

  • Une balise sans tiret qui n'est pas une balise HTML connue.
  • Une valeur peut-être null lue sans test ; le rétrécissement d'un if vaut pour les éléments qu'il contient.
  • Une clé de boucle (key) qui n'existe pas sur l'élément parcouru.
  • Un objet affiché par {…} (fini les [object Object]).
  • Un écouteur on: pour un événement que la balise n'a pas, et le type de l'événement reçu (e.currentTarget est l'HTMLInputElement).
  • Une référence ref={…} posée sur un élément d'un autre type que le sien.
  • Un switch non exhaustif, avec default: {assertNever(x)}.
  • Sur un composant enfant : une prop inconnue, une prop mal typée, un on: pour un événement absent de ses emits.
  • Des enfants pour un composant qui ne déclare pas content, des enfants obligatoires qui manquent, un emplacement <:nom> qui n'est pas une prop du composant.
  • Un texte qui commence comme une instruction sans en être une, avec la correction proposée : {'for (more info) see below'}.
  • Une prop qui porte le nom d'une propriété des éléments HTML (@prop title, id, hidden…) : « « title » est déjà une propriété des éléments HTML : choisis un autre nom ».

Le message de TypeScript est rapporté tel quel (« 'nam' does not exist in type 'Props'. Did you mean to write 'name'? »). Le parser refuse aussi, avec le message et souvent la correction (packages/lang/src/parser.test.ts, packages/lang/src/compile.test.ts) :

  • la syntaxe de lit : @click, ?disabled, .value (« Syntaxe de lit : écris on:click={…} ») ;
  • < et } dans le texte, avec la correction {'<'}, {'}'} ;
  • une balise fermante qui ne correspond pas (« </i> ferme <b> ») ;
  • return x; dans une méthode qui émet des éléments (return; reste permis, comme return x; dans une fonction imbriquée) ;
  • un élément hors d'une méthode de classe ;
  • un bloc dont le } manque avant la balise fermante du parent ;
  • un emplacement <:nom> hors d'un composant, avec des attributs, rempli deux fois, ou nommé content.

Déclarations d'un composant

Les déclarations @tag, @title, @prop et @emit sont lues par le parser, qui refuse (parser.test.ts, « parse : déclarations d’un composant ») :

  • un composant sans @tag (« Un composant déclare son tag : `@tag = 'mon-composant';` »), sauf une classe abstract ;
  • static tag = '…'; dans un .super (« Dans un `.super`, le tag se déclare par `@tag = '…';` ») ;
  • un tag qui n'est pas une chaîne écrite telle quelle, en minuscules, avec un tiret ;
  • un générique SuperElement<…> écrit à la main (« Dans un `.super`, les props et les événements se déclarent dans la classe : `@prop nom: Type;` et `@emit nom: Type;` ») ;
  • une déclaration en double (« `@tag` déclaré deux fois », « `@prop a` déclaré deux fois ») ;
  • une prop sans type (@prop label;), une prop facultative avec une valeur par défaut (@prop size?: number = 2; : « retire le ? »), un événement avec une valeur ;
  • une déclaration hors d'un composant (« `@prop` ne s’écrit que dans un composant (`extends SuperElement`) »).

Les types du composant en sont tirés (virtual.test.ts) : @prop question: string; devient une prop obligatoire, @prop tone: … = 'neutral'; et @prop size?: number; des props facultatives, @emit answered: { confirmed: boolean }; un événement. Ce sont eux que vérifient les balises qui utilisent le composant (prop inconnue, mal typée, on: inconnu, ci-dessus).

Les déclarations de préparation (@contract, @selector, @state, @form, @ref, @on) sont lues elles aussi, et le parser refuse (parser.test.ts, « parse : déclarations de préparation et écouteurs ») :

  • un contrat déclaré deux fois, même sous un autre nom de champ (« Le contrat `cart` est déjà déclaré par `@contract cart` ») ;
  • @contract router; (« Le router se lit par `this.router`, sans `@contract` ») ;
  • un contrat qui n'est pas une chaîne écrite telle quelle (@contract cart = name;) ;
  • un type sur @selector (« Pas de type sur `@selector` : il vient de la valeur ») ;
  • un @ref sans type (« Une référence déclare le type de son élément : `@ref input: HTMLInputElement;` ») ;
  • un @on mal écrit (@on('cart') : « `@on` s’écrit `@on('contrat', 'événement')`, au-dessus d’une méthode ») ;
  • l'ancienne forme dans un composant (cart = this.contract('cart');, this.selector(…), this.state(…), this.ref<T>()), avec la ligne réécrite en correction (@contract cart;, @state local = { open: false };…) ; hors composant, la même ligne reste du TS ordinaire ;
  • un écouteur posé dans le constructeur (« Dans un `.super`, un écouteur se déclare sur une méthode : `@on('cart', 'événement') onEvent(payload) { … }` »).

Le TS virtuel en tire les champs qu'on écrivait à la main (virtual.test.ts) : @contract cart; devient readonly cart = this.contract('cart');, @selector, @state et @ref les champs this.selector(…), this.state(…), this.ref<T>(), et @on('profile', 'save:done') onSaved(…) un écouteur this.contract('profile').on('save:done', …) : le paramètre de la méthode a donc le type du payload de l'événement, vérifié comme dans un écouteur écrit à la main. @on('router', 'navigated') devient this.router.on('navigated', …).

Titre de la page

@title = …; et this.page.title = … sont vérifiés à l'exécution (packages/dom/src/page.test.ts) :

  • un titre posé pendant render lève « `this.page.title` ne se pose pas pendant render » ;
  • this.page.title ne se lit pas : « `this.page.title` se pose, il ne se lit pas » ;
  • la pile est testée : le dernier composant monté qui pose un titre l'emporte, celui du dessous suit ses données sans s'afficher et revient au démontage ; un titre en fonction suit les valeurs qu'il lit, comme render.

Le code compilé garde les numéros de ligne de la source, et sa source map ramène le JS final à la ligne et à la colonne du .super (compile.test.ts). Voir Templates et Outillage.

Architecture (plugin Vite)

Ces règles ne sont pas des erreurs de type : le plugin refuse de charger le module, en dev, au build et en test. Pour un .super, elles s'appliquent à son code compilé. Les fichiers de test (*.test.ts) n'y sont pas soumis.

  • Un module qui importe SuperContract ou SuperStore hors de src/@core/.
  • Un module qui importe SuperElement hors de src/@components/.
  • Un composant qui importe de @core/ autre chose qu'un type (un contrat, un store, une constante, ou import * as) : il parle aux stores par @contract nom; (this.contract('nom') dans un .ts).
  • Un module de @core/ qui importe une valeur de @super-ts/dom.

Le plugin lit aussi les contrats et le router pour générer src/@core/contracts.d.ts. Il s'arrête avec une erreur sur :

  • un contrat (export class X extends SuperContract) qui ne se nomme pas par super({ name: '…' }) ;
  • deux contrats du même nom ;
  • un contrat nommé 'router' quand l'app déclare un router ;
  • deux export const … = defineRouter(…) dans le src.

Ce qui n'est pas vérifié

  • Un store sans implements Commands<Self> : ni commande manquante, ni paramètres, ni résultat, ni méthode en trop. Une commande sans méthode n'est alors signalée qu'au send (« commande inconnue »).
  • this.fail accepte les raisons de toutes les commandes du contrat, pas seulement celles de la commande en cours.
  • Un événement déclaré que le store n'émet jamais.
  • Un composant ne rattrape pas l'erreur de son propre constructeur : seul le renderError d'un ancêtre la reçoit.
  • Un seul router est typé : celui que le plugin trouve dans le src.
  • Une valeur de l'URL : elle vient de l'extérieur. Une valeur non conforme à la description est lue comme absente (query) ou undefined (paramètre), et isValid() le signale ; c'est à l'écran ou au guard d'en décider.
  • Le lien entre un écran et sa route vient de .screens(…), lu par le plugin Vite : un écran qu'il ne retrouve pas (classe sans @tag lisible, ou sans static tag dans un .ts, import qu'il ne résout pas) voit toutes les routes. La route qu'un composant .ts déclare à la main (SuperElement<{ route: 'counter' }>) n'est pas comparée à .screens(…).
  • Une liste oneOf incomplète : pour sort: 'label' | 'value', { oneOf: ['label'] } compile. Une valeur en trop est refusée, mais une valeur oubliée ne l'est pas : elle ne sera jamais lue comme valide dans l'URL. Le type étant donné à part (query<T>), TypeScript ne peut pas vérifier que la liste couvre toute l'union.
  • Un composant écrit par son tag (<counter-screen> dans un template) au lieu de sa classe (<CounterScreen />) : une balise avec tiret est un élément personnalisé quelconque, ni ses attributs ni ses événements ne sont vérifiés, et ce n'est pas supporté.
  • Un import * as de @super-ts/dom ou @super-ts/core hors des dossiers imposés : la règle de placement ne voit que les imports nommés.
