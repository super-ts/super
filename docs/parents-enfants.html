Parents et enfants

Props vers le bas, événements vers le haut. Un parent ne pilote jamais un enfant en appelant ses méthodes : il lui passe des props, et l'enfant répond par des événements.

Utiliser un sous-composant

Dans un template, un enfant se place en balise, au nom de sa classe : une balise qui commence par une majuscule est un composant, importé comme n'importe quelle classe (import { CounterControls } from './counter-controls').

  • Les attributs sont les props. Le compilateur les vérifie contre les @prop de l'enfant : une prop requise manquante, une prop en trop ou une valeur mal typée est une erreur. Une valeur fixe s'écrit entre guillemets (question="Vider le panier ?", une chaîne), une valeur calculée entre accolades.
  • on:nom branche un événement de l'enfant sur une fonction du parent. Le nom et le payload sont vérifiés contre les @emit de l'enfant.
  • La balise est l'équivalent de CounterControls.create({ count, … }, { on: { increment, … } }), l'appel qui sert hors template (voir Créer un élément hors template).
  • L'élément enfant est créé une fois par emplacement, puis ses props sont mises à jour à chaque rendu du parent. Il garde son état local. S'il reçoit des props égales (comparées clé par clé), il ne se re-rend pas.
  • Un composant peut aussi recevoir des éléments entre ses balises, s'il les déclare (voir Composer : des enfants).

Déclarer les props

Une prop se déclare dans le corps de la classe par @prop, avec son type, et se lit par this.nom. Le tag, les props et les événements s'écrivent au même endroit, sans générique (le détail de chaque déclaration est dans Composants : les déclarations) :

Une prop prend l'une de ces trois formes :

  • Une prop obligatoire manquante dans la balise du parent est une erreur de compilation.
  • Une prop facultative (?) vaut undefined quand le parent ne la passe pas. ? et une valeur par défaut ne vont pas ensemble : c'est une erreur.
  • La valeur par défaut rend la prop facultative ; elle est calculée une fois par instance (un [] par défaut n'est pas partagé entre deux éléments).
  • Un composant dont toutes les props sont facultatives se place sans attribut (<RouterOutlet />).
  • this.counterId est en lecture seule, et toujours à jour : un changement de prop re-rend l'enfant. this.props existe toujours (toutes les props, en lecture seule), mais on écrit this.nom.
  • Les props sont lisibles dès la construction (pour initialiser un @state, par exemple). Une copie faite à ce moment-là ne suit pas les changements suivants : lis this.nom dans render ou dans la fonction d'un @selector pour une valeur toujours à jour.

Les noms déjà pris par les éléments HTML

Un composant est un élément HTML : this.id, this.title, this.hidden ou this.slot existent déjà. Une prop ne peut donc pas porter l'un de ces noms, et le compilateur le dit :

Dans l'app d'exemples, title est devenu heading (Card, KitPage) et id est devenu counterId (CounterListItem). Un paramètre de route id se lit de même dans un champ nommé autrement : counterId = this.router.current.params.id;. Le nom page est lui aussi réservé (c'est this.page). Le contenu écrit entre les balises remplit pour la même raison une prop content (children est natif), voir Composer : des enfants.

emit chez l'enfant, on chez le parent

Les deux côtés emploient chacun leur vocabulaire. on: est le préfixe qui sert, côté parent, à écouter ; l'enfant ne le voit jamais.

Côté enfant (CounterControls)Côté parent (CounterScreen)
Déclarer@emit increment: void; et @emit decrement: void;, dans le corps de la classerien
Agirthis.emit('increment') : « j'annonce qu'on a cliqué »on:increment={…} : « quand tu annonces ça, je fais ceci »

L'enfant parle, le parent écoute. L'enfant ne sait pas qui l'écoute, ni même si quelqu'un l'écoute. C'est le même principe qu'un <button> HTML : il émet click, et c'est la page qui écrit on:click={…}, avec le même préfixe. Ailleurs, c'est $emit / @increment en Vue, dispatch / on:increment en Svelte.

Déclarer les événements d'un composant

@emit nom: T; déclare un événement et le type de ce qu'il transporte (void s'il ne transporte rien). Il n'a pas de valeur : @emit closed: void = … est une erreur. Un événement void s'émet sans argument. Le compilateur refuse un nom inconnu, un payload mal typé, ou un payload oublié.

Le trajet complet d'un clic sur « + »

  1. CounterControls émet increment.
  2. CounterScreen reçoit l'événement et appelle this.run('increment').
  3. run envoie this.counter.send('increment', { id: 'cafes' }) au store.
  4. Le store sauvegarde et met à jour son état ; Super publie increment:done.
  5. L'écran se re-rend ; la nouvelle valeur redescend dans CounterControls par la prop count.

CounterControls ne connaît ni le store, ni l'id, ni la commande : il reste réutilisable. C'est l'écran qui décide de ce que signifie « incrémenter ».

Un dialogue : le parent le rend, il répond par un événement

Dans l'exemple Boutique : shared/confirm-dialog.super, shop/index.super. « Vider le panier ? » est rendu par le parent et répond par un événement.

Même un dialogue de confirmation suit cette règle. Le parent l'ouvre en le rendant, avec sa question en prop ; le dialogue émet la réponse. Monté, il est ouvert : pas de prop nullable qui voudrait dire « fermé ». Personne n'attend rien, il n'y a pas d'await.

  1. Clic sur « Vider le panier » : le parent met dialog: 'confirm-clear' dans son état local.
  2. Le parent se re-rend ; la condition est vraie, le dialogue est monté avec sa question et s'affiche.
  3. Clic sur « Confirmer » : le dialogue émet answered { confirmed: true }.
  4. onClearAnswered remet dialog à null (le dialogue est démonté) et envoie la commande.

Ouvrir et fermer un dialogue, c'est changer une valeur dans l'état du parent. Avec plusieurs dialogues, garde un seul champ (dialog: 'confirm-clear' | 'confirm-delete' | null) et une condition par dialogue : chacun a sa question et son handler, et deux modales ne peuvent pas être ouvertes en même temps. Le même motif vaut pour un drawer ou un menu.

Un handler passé à un enfant : un champ fléché

onClearAnswered est un champ qui contient une fonction fléchée, pas une méthode. Une fonction fléchée garde le this du composant ; une méthode passée telle quelle (on:answered={this.onAnswered} avec onAnswered() { … }) le perdrait, et this.local serait undefined au moment de l'appel. Même règle pour une action passée à on:click sans fonction autour.

Les listes

Pour une liste d'enfants, utilise une boucle for avec une clé, écrite après key : un élément déplacé garde son DOM et son état local. Sans clé, le rendu suit la position (voir Listes).

Composer : des enfants

Une carte, une modale, des onglets : des composants de mise en page, dont le contenu vient du parent. Le composant déclare ce qu'il accepte par des props de type Children, et le place où il veut :

  • content reçoit le contenu écrit entre les balises. C'est une prop comme les autres : @prop content: Children;, lue par this.content. Elle ne s'appelle pas children parce que this.children est la propriété native des éléments HTML (la liste de leurs éléments enfants).
  • Un emplacement nommé est une autre prop de type Children, ici actions, lue par this.actions. Facultatif, il s'écrit avec ? (@prop footer?: Children;) ; un composant en déclare autant qu'il veut.

Le parent remplit content par les éléments écrits entre les balises, et actions par un emplacement nommé, ou par une méthode :

  • Les enfants appartiennent au parent : le clic sur « Remettre à zéro » appelle une méthode du parent, et this.count est lu par le parent. Les enfants suivent son rendu ; la carte les garde quand elle se re-rend seule.
  • Le compilateur vérifie le contrat : des enfants pour un composant qui ne déclare pas content, des enfants obligatoires qui manquent, un emplacement qui n'est pas une prop du composant sont des erreurs.
  • La syntaxe complète est dans Templates : des enfants et des emplacements nommés. L'exemple Composition de l'app d'exemples montre les deux façons côte à côte.

Ce qui n'existe pas, volontairement

  • Pas de référence vers un enfant pour appeler ses méthodes : un enfant n'expose pas d'API. Dans un template, <CounterControls … /> monte l'enfant, il ne donne pas une instance à garder.
  • Pas de callback en prop pour remonter une information : rien ne l'empêche techniquement, mais on utilise un événement, déclaré par @emit et typé. L'enfant reste découplé, et le test peut écouter l'événement avec mount(…, { on }).
  • Pas d'accès d'un enfant aux stores de son parent par les props : un enfant qui a besoin d'un store déclare lui-même @contract nom;.
  • Pas de tag écrit à la main : <counter-controls> en HTML brut n'est pas supporté. Un enfant passe toujours par sa classe, <CounterControls … /> (ou create hors template).
