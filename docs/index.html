Super

A minimalist front-end framework, typed end to end, that governs three things: stores, components and routing. Everything else belongs to your project.

Status: exploratory draft The API may still change: in 0.x, a minor version can break. The @super-ts/* packages are published on npm and share one version (see Install).

At a glance

A Super feature fits in three files: a contract that says what can be read, requested and listened to; a store that implements it; a component that displays and sends commands. Each one is a class.

The component is a .super file: TypeScript whose methods write their elements directly, like statements (see Templates). In its class it declares its tag and its props (@tag, @prop), the store it reads and the value it takes from it (@contract, @selector), and reads a prop by its name: this.counterId. It imports nothing from @core/: it requests the store by the name of its contract, and the compiler knows its selectors and commands. It sends a command and moves on; the store does the asynchronous work and updates its state; Super tracks the command (this.counter.selectors.pending('increment')) and publishes its outcome (increment:done, increment:failed). The component re-renders because the value it reads has changed.

Principles

  • Two required folders, the rest is free. Contracts and stores in src/@core/, components in src/@components/. The @ prefix marks what belongs to Super. Domain, ports, adapters, routes and composition root are organised however your project sees fit.
  • The contract is the only door to a store. Its selectors say what is read, its commands what is requested, its events what is listened to. A component requests the store by its name (@contract counter;) and imports only types from @core/.
  • The view sends and moves on. A command returns nothing: there is never an await in a component. The result comes back through the state or through an event.
  • Props down, events up. A parent never calls a method of a child.
  • Prepare, then display. The fields and constructor of a component prepare once (contracts, local state, reads, listeners); render displays on every render. Super refuses to prepare anything during render.
  • The compiler does the work. An unknown command, a missing body, a store method outside the contract, a link without its parameter, a screen with the wrong props or a mistake in a template do not compile.
  • Web standards first. A store is an EventTarget, a component is a custom element. .super files are compiled to lit-html, a deliberate but hidden dependency: you never import lit.

What Super deliberately does not do

  • No HTTP client, no injection container: you assemble everything in your composition root.
  • No imposed layers beyond @core/ and @components/.
  • No shadow DOM: components render in the light DOM, your global styles apply.

The packages

PackageContents
@super-ts/coreSuperContract, SuperStore : contracts, selectors, stores. No dependency on the DOM.
@super-ts/domSuperElement : components, rendering, createApp, router.
@super-ts/testingmount, fakeStore, record, flush, cleanup.
@super-ts/uiThe UI kit: fields bound to forms, CommandButton, RouteLink, toasts, dialogs, menus, table. See UI kit.
@super-ts/viteThe plugin that compiles .super files, enforces the architecture and generates the contract dictionary (@core/contracts.d.ts).
@super-ts/langThe .super language: parser, compilation to lit, type check (super-tsc). See Tooling.
@super-ts/language-serverThe language server for .super files in the editor (packages/lang-server), command super-language-server.
@super-ts/lintThe Biome configuration that fixes the import order.

With an AI assistant

The docs also exist in markdown, in the llms.txt format, to give them to an LLM or to a coding agent. These files are generated from these pages on every npm run check, and npm run docs:check fails if they are out of date.

  • llms.txt: the index, one line per page.
  • llms-full.txt: all the docs in one file, code included.
  • llms-small.txt: the same, without the FAQ, the examples catalogue or the references to the examples app, for small context windows.

In a project, just give the agent the path, for example in an AGENTS.md: "the Super docs are in docs/llms-full.txt".
