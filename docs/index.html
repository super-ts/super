Super

Un framework front minimaliste, typé de bout en bout, qui encadre trois choses : les stores, les composants et le routing. Tout le reste appartient à ton projet.

Statut : draft exploratoire L'API peut encore bouger. Les paquets ne sont pas publiés sur npm : ils vivent dans le dépôt, sous packages/.

En un coup d'œil

Une fonctionnalité Super tient en trois fichiers : un contrat qui dit ce qu'on peut lire, demander et écouter ; un store qui l'implémente ; un composant qui affiche et envoie des commandes. Chacun est une classe.

Le composant est un fichier .super : du TypeScript dont les méthodes écrivent leurs éléments directement, comme des instructions (voir Templates). Il déclare dans sa classe son tag et ses props (@tag, @prop), le store qu'il lit et la valeur qu'il en tire (@contract, @selector), et lit une prop par son nom : this.counterId. Il n'importe rien de @core/ : il demande le store par le nom de son contrat, et le compilateur connaît ses sélecteurs et ses commandes. Il envoie une commande et laisse filer ; le store fait le travail asynchrone et met à jour son état ; Super suit la commande (this.counter.selectors.pending('increment')) et publie son issue (increment:done, increment:failed). Le composant se re-rend parce que la valeur qu'il lit a changé.

Principes

  • Deux dossiers imposés, le reste libre. Contrats et stores dans src/@core/, composants dans src/@components/. Le préfixe @ marque ce qui appartient à Super. Domaine, ports, adapters, routes et racine de composition s'organisent comme ton projet l'entend.
  • Le contrat est la seule porte d'un store. Ses sélecteurs disent ce qu'on lit, ses commandes ce qu'on demande, ses événements ce qu'on écoute. Un composant demande le store par son nom (@contract counter;) et n'importe de @core/ que des types.
  • La vue envoie et laisse filer. Une commande ne renvoie rien : il n'y a jamais d'await dans un composant. Le résultat revient par l'état ou par un événement.
  • Props vers le bas, événements vers le haut. Un parent n'appelle jamais une méthode d'un enfant.
  • Préparer, puis afficher. Les champs et le constructeur d'un composant préparent une fois (contrats, état local, lectures, écouteurs) ; render affiche à chaque rendu. Super refuse de préparer quoi que ce soit pendant le rendu.
  • Le compilateur fait le travail. Une commande inconnue, un body manquant, une méthode de store hors contrat, un lien sans son paramètre, un écran aux mauvaises props ou une faute dans un template ne compilent pas.
  • Le standard web d'abord. Un store est un EventTarget, un composant est un custom element. Les fichiers .super sont compilés vers lit-html, une dépendance assumée mais cachée : tu n'importes jamais lit.

Ce que Super ne fait pas, volontairement

  • Pas de client HTTP, pas de conteneur d'injection : tu assembles tout dans ta racine de composition.
  • Pas de couches imposées au-delà de @core/ et @components/.
  • Pas de shadow DOM : les composants rendent en light DOM, tes styles globaux s'appliquent.

Avec un assistant IA

La doc existe aussi en markdown, au format llms.txt, pour la donner à un LLM ou à un agent de code. Ces fichiers sont générés à partir de ces pages à chaque npm run check, et npm run docs:check échoue s'ils ne sont plus à jour.

  • llms.txt : l'index, une ligne par page.
  • llms-full.txt : toute la doc en un fichier, code compris.
  • llms-small.txt : la même, sans la FAQ, le catalogue des exemples ni les renvois vers l'app d'exemples, pour les petites fenêtres de contexte.

Dans un projet, il suffit d'indiquer le chemin à l'agent, par exemple dans un AGENTS.md : « la doc de Super est dans docs/llms-full.txt ».
