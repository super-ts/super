Router

The router is built into @super-ts/dom. Routes are named and typed: a link without its parameter, a value of the wrong type or a wrong query description does not compile. And the router is a store like any other.

Declaring the routes

Everything is declared in a user-land file, src/routes.ts, which exports only one thing: Router.

The Router object has two uses. The Vite plugin spots it (export const Router = defineRouter(…)) and registers the router under the name 'router' in the contract dictionary it generates (src/@core/contracts.d.ts): a component reads and drives it through this.router, typed by the app's routes, without importing routes.ts. The plugin also links each screen to its route there (see The screen and its route). And Router.href builds a link in code that is not a component (a test, a user-land module). There is nothing else to export, and no declaration to write by hand: one router is typed per app.

defineRouter

A route is declared in two ways:

  • A string, when the values are text. A :name segment is a parameter: '/counters/:id' gives { id: string }. After ? come the query keys read by the route, [] marking a list: '/counters?sort&tag[]' gives { sort?: string; tag: string[] }. See Query.
  • An object { path, params?, query? }, when the values have a type: a number, a boolean, a closed list of values. The app writes the type, the description says how to read it from the URL. See Describing the values.
  • Each path must start with /, otherwise an error is thrown.
  • '*' and '!' are reserved for the "not found" and "error" screens: they cannot be route names (compile error, and runtime error).

Describing the values

In the object form, the app writes the type of its parameters and query, then describes it with params<T>({…}) and query<T>({…}), imported from @super-ts/dom. The compiler checks that the description matches the type, key by key. At runtime, it is used to read and convert the values from the URL.

DescriptionTypeValues accepted in the URL
StringstringAll, decoded.
NumbernumberA decimal number: 42, -3, 1.5, 1e3. abc is invalid.
Booleanbooleantrue or false, nothing else.
{ oneOf: ['label', 'value'] }'label' | 'value'One of the listed values.
[String], [Number], [{ oneOf: […] }]a listEach occurrence of the key (?tag=a&tag=b). Query only.
  • String, Number and Boolean are JavaScript's native constructors: they name the type and do the conversion.
  • A required query key has a default value, used when the key is absent or invalid: { type: Number, default: 1 }, { oneOf: [...], default: 'label' }.
  • An optional key has none (search?: string is described String): it is undefined when missing.
  • A path parameter never has a default: it is always present in the URL that matches the route.
  • params describes exactly the path parameters, no more, no less. Without params, path parameters are strings.
  • A oneOf list must cover the whole union: the compiler rejects a value outside the union, but not a forgotten value. With { oneOf: ['label'] } for 'label' | 'value', ?sort=value would always be read as invalid. See what is not checked.
  • In the object form, the query is not written in the path: { path: '/counters?sort' } is rejected, it is described through query.

These errors are also checked at runtime, with an explicit message: "route "counter": params must describe exactly the path parameters (id)".

.screens

Associates a screen with each route. A screen is a component class (SuperElement) without required props: it does not receive its route's values as props, it reads them through this.router.current (see Reading the route in the screen). The compiler requires one screen per route. Two optional keys can be added: '*', the screen shown when no path matches, and '!', the screen shown when a screen crashes without being caught (it is the only one to receive props, { error, path }, see Handling errors). Instead of a screen, a route can receive a redirect.

Reading the route in the screen

The screen reads its route through this.router.current: current.params.id() for a path parameter, current.query.sort() for a query key. On /counters/coffees, the route /counters/:id gives current.params.id() === 'coffees'. Values are decoded (/counters/caf%C3%A9 gives 'café'), and converted if the route describes them.

  • The field is not called id: id is a native property of HTML elements, and a field or prop cannot reuse its name. The id parameter is therefore kept in counterId (counterId = this.router.current.params.id;). The same goes for title, hidden or slot.
  • Each value is a function, which reads the active route when called. It can be kept in a field (counterId above), destructured (const { id } = this.router.current.params), or given as is to a @selector, like a selector without parameters: @selector sort = this.router.current.query.sort;, then this.sort.value.
  • Read during render, directly or through a @selector, it subscribes the component to the router: it re-renders when the value changes.
  • Route value or selection: kept as is (counterId = this.router.current.params.id), the value is read by calling it, this.counterId(), like a selector; given to a @selector (@selector counterId = this.router.current.params.id;), it becomes a selection, read through this.counterId.value and this.counterId.isValid(). Inside another @selector's function, you call the route value (this.counter.selectors.count(this.counterId())): a selection read there would not subscribe it to the router.
  • It is typed by the screen's route: params.id exists on the screen of /counters/:id, params.nope does not compile. See The screen and its route.
  • current.name() and current.path() give the name of the active route and the path as navigated.
  • In tests, you mount the screen alone with a router in memory mode set to the right path: see Testing with the router.

An invalid value in the URL

The URL comes from outside: /counters/abc for an id described Number, ?page=abc, ?sort=whatever. The router does not reject the navigation for all that:

  • An invalid query key is treated as absent: it takes its default value, or undefined. In a list, only the invalid items are removed (?tag=1&tag=x gives [1] for [Number]).
  • An invalid path parameter does not lead to the '*' screen: the route's screen is shown, and the value is undefined. It is up to the screen to decide what to show.

isValid() says whether the URL contained a conforming value. It exists on each value (current.params.id.isValid()) and on the selection @selector makes of it (this.counterId.isValid()). After this check, the value has the described type: number, and no longer number | undefined.

  • An absent key is valid: it takes its default (or undefined), as the description provides. isValid() is false only if the URL carried a non-conforming value, or if the active route does not declare that key.
  • For a list, isValid() is false as soon as an item has been removed.
  • The component re-renders if the value changes, or if only its validity changes (from ?page=1 to ?page=abc, the value stays 1 but becomes invalid).
  • A string parameter is always valid, like any value of a route declared by a string.

To redirect rather than show a message, two places fit: the route's guard (({ params }) => params.id.isValid() || { to: 'counters' }), and the screen is never rendered; or mounted(), with this.router.send('navigate', …), and the screen renders once before leaving. Navigating from render is not in the spirit of the framework: render describes the screen, it does not trigger anything.

The screen and its route

In a screen, this.router.current is typed by its own route, without writing anything by hand. The Vite plugin reads .screens(…) in routes.ts, finds each screen's tag, and generates the link in src/@core/contracts.d.ts:

  • The .super compiler adds the route to each component's type, based on its tag: CounterScreen sees params.id, and current.name() there is 'counter' | null.
  • A screen used on two routes sees their union: every key of either one, undefined where a route does not have it.
  • A component that is not a screen sees the union of all the app's routes, in the same way: current.params.id() is number | undefined if only the counter route has a numeric id. A key no route declares does not compile.
  • A component written in .ts, which keeps static tag and the generic, declares its route itself: SuperElement<{ route: 'counter' }>, or SuperElement<{ props: P; route: 'counter' }>.
  • The '*' and '!' screens have no route of their own: they see all routes.

Outside the screen: current and at

A header or a breadcrumb reads the active route in the same way, through this.router.current, typed by the union of all routes: @selector route = this.router.current.name; to know where you are.

A component shown only on a specific route, without being its screen (a child of the screen, for example), reads that route through this.router.at('counter'): its params and its query, typed by that route alone, instead of the union.

at can be declared anywhere, but reading one of its values while another route is active throws an error: "this.router.at('counter') read while the active route is 'counters'". A component shown on several routes therefore reads current, and checks current.name().

A screen that needs other props

The router has nothing to give a screen: .screens() rejects a component with a required prop. An optional prop compiles, but is always undefined when the screen is shown by its route.

So you separate the screen, which reads the route, from the component it shows, whose props are free and which can be reused elsewhere:

What the screen adds comes from a constant (the heading above), a store declared by @contract (preferences, user), or the route itself: if the value must be able to appear in the URL, declare it in the query.

Why paths and screens are declared separately Screens read the router through this.router, typed from Router, and Router contains the screens. The compiler can type Router without reading the screens only because the routes are set apart, in defineRouter(...), and .screens(...) is the last call of the declaration: the router's type does not depend on the screens. That is why guards, which depend only on the routes, come before. A merged form, such as defineRouter(() => ({ screens: { home: { path, component } } })), cannot be typed: the router's type would depend on the screens, which depend on the router, and everything would fall back to any.
Why screens are given by a function routes.ts imports the screens; if a module loaded by a screen in turn imports routes.ts (for Router.href, outside a component), the two modules import each other. If a screen is loaded first (in a test, for example), routes.ts is evaluated before the screen is initialised. With the function, screens are read only when the router is created, by createRouter, once everything is loaded.

Query

A route reads only the query keys it declares. In a string, they follow ?, separated by &, and a key followed by [] is a list; the values are strings. With query<T>({…}), they are typed and converted (see Describing the values). The screen reads them through this.router.current.query:

  • A simple key can be missing: it takes its default value, or undefined. Repeated in the URL, only the first value counts.
  • A list is always an array: ?tag=a&tag=b gives ['a', 'b'], and [] if the key is absent.
  • An invalid value is treated as absent (?sort=whatever gives the default 'original'): see An invalid value in the URL.
  • Undeclared keys are ignored: on /counters?sort=label&utm_source=mail, current.query has no utm_source. The URL is not rewritten for all that: current.path() is still '/counters?sort=label&utm_source=mail', and the address bar keeps it.
  • Parameters and query are read separately: a parameter and a query key can have the same name ('/items/:id?id'). An empty or duplicate key throws an error.
  • Changing only the query does not remount the screen: its local state is kept, and it re-renders if it reads a value that changed. See RouterOutlet.

To build a link or navigate, parameters and query are given separately, with their typed values:

  • Values are written into the URL with String(value): 2 gives page=2, false gives archived=false. A list repeats the key.
  • A key set to undefined or an empty list is omitted.
  • The query is optional, even for a required key: absent from the URL, it falls back to its default when read.

Redirects

A route can send to another one, by declaring redirect(…) in place of its screen. This is useful for a page that is planned but not yet built, an old path kept for existing links, or a path that has no screen of its own (in the examples app, /form redirects to /profile: see routes.ts).

  • Links stay correct: this.router.href('stats') gives /stats today. The day the page exists, you replace redirect(…) with the screen, without touching the links.
  • The target is typed like a navigate ({ to, params, query }): an unknown route or a missing parameter does not compile.
  • History stays clean: the redirected path never enters it. A navigation to /stats adds / to the history, and a redirected initial path replaces the current entry. The back button does not bring you back to a page that immediately sends you elsewhere.
  • Redirects chain (a redirect to a route that is itself redirected), up to 10 in a row. Beyond that, a loop is assumed and an error is thrown: "too many redirects starting from "/a"".

Guards

A guard decides, before showing a route, whether you go there or are redirected elsewhere, based on the app's state or the URL: "are we logged in?", "is this identifier valid?". It is declared one per route, before the screens:

  • A guard returns true to let through, or a target ({ to, params, query }) to redirect. The target is typed like a navigate.
  • It receives its route as this.router.at(…) gives it: { params, query }, typed by the route, each value to be called (params.id()) and equipped with isValid().
  • It reads stores by their contract name, with read('session'), like a component with @contract session;: it receives the contract's selectors (and pending), read at navigation time. An unknown contract name does not compile. The stores come from the application that receives the router: routes.ts knows no instance.
  • It only reads: it cannot send a command. Deciding on a navigation does not trigger a side effect.
  • It is declared before .screens(…), which must remain the last call. After the screens, guards does not exist: it does not compile. Placed after, it would force the compiler to read the screens to type the router, and the screens read the router: everything would fall back to any.
  • It is synchronous. An asynchronous check ("is the session still valid?") is done in the store; the guard reads its result.
  • Routes without a guard always pass.

The examples app protects the shop's checkout: /shop/checkout redirects to /shop as long as the cart is empty. See routes.ts and the Shop example.

When guards apply

  • On every navigation: navigate, visit, intercepted links, the browser's back button.
  • On the current path, when the router joins the application (createApp or mount): the application provides the stores. Before that, they are not evaluated.
  • A redirect decided by a guard follows the same rules as a declared redirect: the refused path does not enter the history.
  • A guard that redirects to the current page simply cancels the navigation.
A store read by a guard must be provided If a guard reads a contract the application does not provide, an error is thrown: "router guard: no store provided for the contract "session"". In tests, pass the store (real or fake) to mount(…, { stores, router }).

Links: this.router.href

  • this.router.href(name, { params, query }) builds the path and encodes the values ('a b' becomes 'a%20b'). params is required if the path has parameters, query always optional.
  • It does not subscribe the component: it does not read the active route, and a route change does not re-render a component that only builds links.
  • Values are typed by the route: { params: { id: '42' } } does not compile if id is described Number. The query follows the rules of Query.
  • this.router.href('counter') without id, or this.router.href('counterz', …), do not compile. A route without parameters or query rejects any value.
  • Outside a component (a test, a user-land module), Router.href, imported from routes.ts, does the same: Router.href('counter', { params: { id: 'coffees' } }).

Link interception

The application intercepts clicks on internal links (href starting with /) and turns them into navigation, without a reload. The browser keeps control in these cases:

  • external link (https://…, //…) or relative link (../x);
  • target attribute other than _self (target="_blank");
  • download or data-native attribute;
  • click with Cmd, Ctrl, Shift or Alt, or a button other than the left one;
  • event already cancelled by another listener.

Showing the screen: RouterOutlet

RouterOutlet shows the screen of the active route, which reads its values through this.router.current. It is a component like any other: you write <RouterOutlet /> in a shared layout, after importing it from @super-ts/dom.

The shell's links are RouteLinks, from the UI kit: the target is written as for navigate, and each link sets aria-current="page" itself when it leads to the displayed page. activeFor keeps "Counters" active on a counter, and "Shop" on the checkout.

Without the kit, the shell would read the name of the active route through this.router.current.name (it would re-render when the route changes) and build its links through this.router.href (which does not subscribe). aria-current would be 'page' on the link of the active route and null on the others: a computed attribute set to null is removed (see Attributes).

Each path change mounts a new instance of the screen: going from /counters/coffees to /counters/pushups builds a new screen, and its local state starts from scratch. A change of query or hash alone (/counters to /counters?sort=label) keeps the screen mounted: a filter or one more page does not lose the local state, and the screen re-renders if it reads a value that changed.

Pending renders run parents first. When the outlet replaces a screen, the old one therefore does not re-render with a route that is no longer its own: it is removed before.

createRouter only accepts a router whose screens are declared: passing it defineRouter({ … }) without .screens(...) does not compile. It returns the router handle, to pass to createApp({ router }), or to mount(…, { router }) in tests. This handle reads like a store's: router.state() gives the full state, and router.send('navigate', …) navigates.

The page title

The tab title follows the displayed screen. The router sets the frame, through the title option of createRouter (and not of defineRouter, whose keys are routes); the screen sets its own title through @title.

  • default is the title when no component sets one (the examples home page, for example). Without default, the document's original title comes back.
  • suffix is appended to the set title: the shop screen sets "Shop", the tab shows "Shop · Super".

In the screen, @title receives a string (a fixed title) or a function (a tracked title), recomputed after each render with the same reads as render:

  • The title is set on mount and removed on unmount: when the route changes, the old screen hands over and the new one sets its own.
  • Any component can set a title, not only a screen: titles form a stack, the last mounted component that sets one wins, and on its unmount the previous title comes back. In the demo, KitPage gives all the kit pages their title (@title = () => this.heading;).
  • Outside the declaration (mounted, a handler), this.page.title = … does the same.

The details (stack, imperative title, rules) are in Components: the page title.

The router in a component

A component reads and drives the router through this.router, without declaring anything: the active route (current), a specific route (at), navigation (send) and links (href); its events are listened to through a @on('router', 'navigated') method. Nothing to import from routes.ts: the view is typed by the app's routes. It can be read anywhere, render included, and a component that does not read it mounts without a router. @contract router is rejected: the router is read through this.router. See Components: the setup declarations.

The active route and the router state

A component reads the active route through this.router.current. Each value is called, or given to a @selector:

ValueContent
current.name()The name of the active route ('examples' | 'counters' | 'counter' | …, 'form' being redirected), or null if none matches.
current.path()The current path, as navigated (query and hash included).
current.params.<key>()A path parameter, decoded and converted: 'café' for /counters/caf%C3%A9. undefined if it is invalid, or if the active route does not have it.
current.query.<key>()A query key declared by the active route, converted: its value, its default, undefined, or [] for a list.
….isValid()On a parameter or a query key: the URL did not carry a non-conforming value, and the active route declares that key.

The handle returned by createRouter (in main.ts or a test) gives the full state through router.state(): path, name, params and query (converted), invalid (the keys for which the URL carried an invalid value: { params: ['id'], query: [] }), and two fields only RouterOutlet uses: screen, the screen to show (the '*' screen if no route matches; never a redirect, those are followed before), and errorScreen, the '!' screen. A component has no access to those two.

Router commands

CommandEffect
navigate({ to, params, query })Navigation typed by route name. params carries the path parameters, required if the path has any; query, optional, the declared query.
visit(path)Navigation by raw path (this is what intercepted links use).
back()Goes back to the previous history entry.

Each navigation emits navigated { from, to }. Navigating to the current path (clicking again on the link of the displayed page) adds nothing to the history and does not remount the screen, but still emits navigated, with from === to: this is what lets you leave the '!' screen by clicking again on the link of the page in error.

Path resolution

  • The trailing slash is ignored: /counters/coffees/ matches counter.
  • The query and hash are ignored to find the route, but kept in path. Declared query keys are read into query.
  • Only the shape of the path counts to find the route: /counters/abc matches counter even if id is described Number, with an invalid id.
  • A path with no match gives a null route and the '*' screen (nothing is shown if it is not declared).
  • Declared redirects and those from guards are followed before showing: path and the active route are those of the final destination.

Testing with the router

A component that reads this.router needs a router. In tests, create it in memory mode, on the desired path: the screen reads its route there, without props.
