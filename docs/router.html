Router

Le router est intégré à @super-ts/dom. Les routes sont nommées et typées : un lien sans son paramètre, une valeur du mauvais type ou une description de query fausse ne compilent pas. Et le router est un store comme un autre.

Déclarer les routes

Tout se déclare dans un fichier user-land, src/routes.ts, qui n'exporte qu'une chose : Router.

L'objet Router a deux usages. Le plugin Vite le repère (export const Router = defineRouter(…)) et inscrit le router sous le nom 'router' dans le dictionnaire des contrats qu'il génère (src/@core/contracts.d.ts) : un composant le lit et le pilote par this.router, typé par les routes de l'app, sans importer routes.ts. Le plugin y relie aussi chaque écran à sa route (voir L'écran et sa route). Et Router.href construit un lien dans le code qui n'est pas un composant (un test, un module user-land). Il n'y a rien d'autre à exporter, ni de déclaration à écrire à la main : un seul router est typé par app.

defineRouter

Une route se déclare de deux façons :

  • Une chaîne, quand les valeurs sont du texte. Un segment :nom est un paramètre : '/counters/:id' donne { id: string }. Après ?, les clés de query lues par la route, [] marquant une liste : '/counters?sort&tag[]' donne { sort?: string; tag: string[] }. Voir Query.
  • Un objet { path, params?, query? }, quand les valeurs ont un type : un nombre, un booléen, une liste fermée de valeurs. Le type est écrit par l'app, la description dit comment le lire dans l'URL. Voir Décrire les valeurs.
  • Chaque chemin doit commencer par /, sinon une erreur est levée.
  • '*' et '!' sont réservés aux écrans « introuvable » et « erreur » : ce ne sont pas des noms de route possibles (erreur de compilation, et erreur à l'exécution).

Décrire les valeurs

Dans la forme objet, l'app écrit le type de ses paramètres et de sa query, puis le décrit avec params<T>({…}) et query<T>({…}), importés de @super-ts/dom. Le compilateur vérifie que la description correspond au type, clé par clé. À l'exécution, elle sert à lire et convertir les valeurs de l'URL.

DescriptionTypeValeurs acceptées dans l'URL
StringstringToutes, décodées.
NumbernumberUn nombre décimal : 42, -3, 1.5, 1e3. abc est invalide.
Booleanbooleantrue ou false, rien d'autre.
{ oneOf: ['label', 'value'] }'label' | 'value'Une des valeurs listées.
[String], [Number], [{ oneOf: […] }]une listeChaque occurrence de la clé (?tag=a&tag=b). Query seulement.
  • String, Number et Boolean sont les constructeurs natifs de JavaScript : ils nomment le type et font la conversion.
  • Une clé de query obligatoire a une valeur par défaut, prise quand la clé est absente ou invalide : { type: Number, default: 1 }, { oneOf: [...], default: 'label' }.
  • Une clé facultative n'en a pas (search?: string se décrit String) : elle vaut undefined quand elle manque.
  • Un paramètre de chemin n'a jamais de défaut : il est toujours présent dans l'URL qui correspond à la route.
  • params décrit exactement les paramètres du chemin, ni plus ni moins. Sans params, les paramètres du chemin sont des chaînes.
  • Une liste oneOf doit couvrir toute l'union : le compilateur refuse une valeur hors de l'union, mais pas une valeur oubliée. Avec { oneOf: ['label'] } pour 'label' | 'value', ?sort=value serait toujours lu comme invalide. Voir ce qui n'est pas vérifié.
  • Dans la forme objet, la query ne s'écrit pas dans le chemin : { path: '/counters?sort' } est refusé, elle se décrit par query.

Ces erreurs sont aussi vérifiées à l'exécution, avec un message explicite : « route "counter" : params doit décrire exactement les paramètres du chemin (id) ».

.screens

Associe un écran à chaque route. Un écran est une classe de composant (SuperElement) sans props obligatoire : il ne reçoit pas les valeurs de sa route en props, il les lit par this.router.current (voir Lire la route dans l'écran). Le compilateur exige un écran par route. Deux clés facultatives s'ajoutent : '*', l'écran affiché quand aucun chemin ne correspond, et '!', l'écran affiché quand un écran plante sans être rattrapé (il est le seul à recevoir des props, { error, path }, voir Gérer les erreurs). À la place d'un écran, une route peut recevoir une redirection.

Lire la route dans l'écran

L'écran lit sa route par this.router.current : current.params.id() pour un paramètre du chemin, current.query.sort() pour une clé de query. Sur /counters/cafes, la route /counters/:id donne current.params.id() === 'cafes'. Les valeurs sont décodées (/counters/caf%C3%A9 donne 'café'), et converties si la route les décrit.

  • Le champ ne s'appelle pas id : id est une propriété native des éléments HTML, et un champ ou une prop ne peut pas en reprendre le nom. Le paramètre id se garde donc dans counterId (counterId = this.router.current.params.id;). Il en va de même pour title, hidden ou slot.
  • Chaque valeur est une fonction, qui lit la route active à l'appel. Elle se garde dans un champ (counterId ci-dessus), se déstructure (const { id } = this.router.current.params), ou se donne telle quelle à un @selector, comme un sélecteur sans paramètre : @selector sort = this.router.current.query.sort;, puis this.sort.value.
  • Lue pendant render, directement ou par un @selector, elle abonne le composant au router : il se re-rend quand la valeur change.
  • Valeur de route ou sélection : gardée telle quelle (counterId = this.router.current.params.id), la valeur se lit en l'appelant, this.counterId(), comme un sélecteur ; donnée à un @selector (@selector counterId = this.router.current.params.id;), elle devient une sélection, qui se lit par this.counterId.value et this.counterId.isValid(). Dans la fonction d'un autre @selector, on appelle la valeur de route (this.counter.selectors.count(this.counterId())) : une sélection lue là ne l'abonnerait pas au router.
  • Elle est typée par la route de l'écran : params.id existe sur l'écran de /counters/:id, params.nope ne compile pas. Voir L'écran et sa route.
  • current.name() et current.path() donnent le nom de la route active et le chemin tel que navigué.
  • En test, on monte l'écran seul avec un router en mode memory placé sur le bon chemin : voir Tester avec le router.

Une valeur invalide dans l'URL

L'URL vient de l'extérieur : /counters/abc pour un id décrit Number, ?page=abc, ?sort=nimporte. Le router ne rejette pas la navigation pour autant :

  • Une clé de query invalide est traitée comme absente : elle prend sa valeur par défaut, ou undefined. Dans une liste, seuls les éléments invalides sont retirés (?tag=1&tag=x donne [1] pour [Number]).
  • Un paramètre de chemin invalide ne mène pas à l'écran '*' : l'écran de la route est affiché, et la valeur vaut undefined. C'est à l'écran de décider quoi montrer.

isValid() dit si l'URL contenait une valeur conforme. Il existe sur chaque valeur (current.params.id.isValid()) et sur la sélection qu'en fait @selector (this.counterId.isValid()). Après ce test, la valeur est du type décrit : number, et non plus number | undefined.

  • Une clé absente est valide : elle prend son défaut (ou undefined), comme prévu par la description. isValid() n'est faux que si l'URL portait une valeur non conforme, ou si la route active ne déclare pas cette clé.
  • Pour une liste, isValid() est faux dès qu'un élément a été retiré.
  • Le composant se re-rend si la valeur change, ou si seule sa validité change (de ?page=1 à ?page=abc, la valeur reste 1 mais devient invalide).
  • Un paramètre string est toujours valide, comme toute valeur d'une route déclarée par une chaîne.

Pour rediriger plutôt qu'afficher un message, deux endroits conviennent : le guard de la route (({ params }) => params.id.isValid() || { to: 'counters' }), et l'écran n'est jamais rendu ; ou mounted(), avec this.router.send('navigate', …), et l'écran se rend une fois avant de partir. Naviguer depuis render n'est pas dans l'esprit du framework : render décrit l'écran, il ne déclenche rien.

L'écran et sa route

Dans un écran, this.router.current est typé par sa propre route, sans rien écrire à la main. Le plugin Vite lit .screens(…) dans routes.ts, retrouve le tag de chaque écran, et génère le lien dans src/@core/contracts.d.ts :

  • Le compilateur .super ajoute la route au type de chaque composant, d'après son tag : CounterScreen voit params.id, et current.name() y vaut 'counter' | null.
  • Un écran utilisé sur deux routes voit leur union : chaque clé de l'une ou l'autre, undefined là où une route ne l'a pas.
  • Un composant qui n'est pas un écran voit l'union de toutes les routes de l'app, de la même façon : current.params.id() vaut number | undefined si seule la route counter a un id numérique. Une clé qu'aucune route ne déclare ne compile pas.
  • Un composant écrit en .ts, qui garde static tag et le générique, déclare sa route lui-même : SuperElement<{ route: 'counter' }>, ou SuperElement<{ props: P; route: 'counter' }>.
  • Les écrans '*' et '!' n'ont pas de route propre : ils voient toutes les routes.

Hors de l'écran : current et at

Un en-tête ou un fil d'Ariane lit la route active de la même façon, par this.router.current, typé par l'union de toutes les routes : @selector route = this.router.current.name; pour savoir où l'on est.

Un composant qui n'est affiché que sur une route précise, sans en être l'écran (un enfant de l'écran, par exemple), lit cette route par this.router.at('counter') : ses params et sa query, typés par elle seule, au lieu de l'union.

at se déclare n'importe où, mais lire une de ses valeurs alors que la route active est une autre lève une erreur : « this.router.at('counter') lu alors que la route active est 'counters' ». Un composant affiché sur plusieurs routes lit donc current, et vérifie current.name().

Un écran qui a besoin d'autres props

Le router n'a rien à donner à un écran : .screens() refuse un composant qui a une prop obligatoire. Une prop facultative compile, mais vaut toujours undefined quand l'écran est affiché par sa route.

On sépare alors l'écran, qui lit la route, du composant qu'il affiche, dont les props sont libres et qui se réutilise ailleurs :

Ce que l'écran ajoute vient d'une constante (l'intitulé ci-dessus), d'un store déclaré par @contract (préférences, utilisateur), ou de la route elle-même : si la valeur doit pouvoir figurer dans l'URL, déclare-la dans la query.

Pourquoi les chemins et les écrans sont déclarés à part Les écrans lisent le router par this.router, typé d'après Router, et Router contient les écrans. Le compilateur ne peut typer Router sans lire les écrans que parce que les routes sont posées à part, dans defineRouter(...), et que .screens(...) est le dernier appel de la déclaration : le type du router ne dépend pas des écrans. C'est pourquoi les guards, qui ne dépendent que des routes, viennent avant. Une forme fusionnée, du genre defineRouter(() => ({ screens: { home: { path, component } } })), ne peut pas être typée : le type du router dépendrait des écrans, qui dépendent du router, et tout retomberait en any.
Pourquoi les écrans sont donnés par une fonction routes.ts importe les écrans ; si un module chargé par un écran importe à son tour routes.ts (pour Router.href, hors composant), les deux modules s'importent mutuellement. Si un écran est chargé en premier (dans un test, par exemple), routes.ts s'évalue avant que l'écran soit initialisé. Avec la fonction, les écrans ne sont lus qu'à la création du router, par createRouter, une fois tout chargé.

Query

Une route ne lit que les clés de query qu'elle déclare. Dans une chaîne, elles suivent ?, séparées par &, et une clé suivie de [] est une liste ; les valeurs sont des chaînes. Avec query<T>({…}), elles sont typées et converties (voir Décrire les valeurs). L'écran les lit par this.router.current.query :

  • Une clé simple peut manquer : elle vaut sa valeur par défaut, ou undefined. Répétée dans l'URL, seule la première valeur compte.
  • Une liste vaut toujours un tableau : ?tag=a&tag=b donne ['a', 'b'], et [] si la clé est absente.
  • Une valeur invalide est traitée comme absente (?sort=nimporte donne le défaut 'original') : voir Une valeur invalide dans l'URL.
  • Les clés non déclarées sont ignorées : sur /counters?sort=label&utm_source=mail, current.query n'a pas de utm_source. L'URL n'est pas réécrite pour autant : current.path() vaut toujours '/counters?sort=label&utm_source=mail', et la barre d'adresse la garde.
  • Paramètres et query se lisent séparément : un paramètre et une clé de query peuvent porter le même nom ('/items/:id?id'). Une clé vide ou en double lève une erreur.
  • Changer seulement la query ne remonte pas l'écran : son état local est conservé, et il se re-rend s'il lit une valeur qui a changé. Voir RouterOutlet.

Pour construire un lien ou naviguer, paramètres et query se donnent séparément, avec leurs valeurs typées :

  • Les valeurs s'écrivent dans l'URL par String(valeur) : 2 donne page=2, false donne archived=false. Une liste répète la clé.
  • Une clé à undefined ou une liste vide sont omises.
  • La query est facultative, même pour une clé obligatoire : absente de l'URL, elle reprend son défaut à la lecture.

Redirections

Une route peut renvoyer vers une autre, en déclarant redirect(…) à la place de son écran. C'est utile pour une page prévue mais pas encore construite, un ancien chemin qu'on garde pour les liens existants, ou un chemin qui n'a pas d'écran propre (dans l'app d'exemples, /form renvoie vers /profile : voir routes.ts).

  • Les liens restent justes : this.router.href('stats') donne /stats dès aujourd'hui. Le jour où la page existe, on remplace redirect(…) par l'écran, sans toucher aux liens.
  • La cible est typée comme un navigate ({ to, params, query }) : une route inconnue ou un paramètre manquant ne compilent pas.
  • L'historique reste propre : le chemin redirigé n'y entre jamais. Une navigation vers /stats ajoute / à l'historique, et un chemin initial redirigé remplace l'entrée courante. Le bouton retour ne ramène pas sur une page qui renvoie aussitôt ailleurs.
  • Les redirections s'enchaînent (une redirection vers une route elle-même redirigée), jusqu'à 10 de suite. Au-delà, une boucle est supposée et une erreur est levée : « trop de redirections à partir de "/a" ».

Guards

Un guard décide, avant d'afficher une route, si on y va ou si on est redirigé ailleurs, selon l'état de l'app ou l'URL : « est-on connecté ? », « cet identifiant est-il valide ? ». Il se déclare un par route, avant les écrans :

  • Un guard renvoie true pour laisser passer, ou une cible ({ to, params, query }) pour rediriger. La cible est typée comme un navigate.
  • Il reçoit sa route comme this.router.at(…) la donne : { params, query }, typés par la route, chaque valeur à appeler (params.id()) et munie de isValid().
  • Il lit les stores par le nom de leur contrat, avec read('session'), comme un composant avec @contract session; : il reçoit les sélecteurs du contrat (et pending), lus au moment de la navigation. Un nom de contrat inconnu ne compile pas. Les stores viennent de l'application qui reçoit le router : routes.ts ne connaît aucune instance.
  • Il ne fait que lire : il ne peut pas envoyer de commande. Décider d'une navigation ne déclenche pas d'effet de bord.
  • Il se déclare avant .screens(…), qui doit rester le dernier appel. Après les écrans, guards n'existe pas : ça ne compile pas. Placé après, il obligerait le compilateur à lire les écrans pour typer le router, et les écrans lisent le router : tout retomberait en any.
  • Il est synchrone. Une vérification asynchrone (« la session est-elle encore valide ? ») se fait dans le store ; le guard lit son résultat.
  • Les routes sans guard passent toujours.

L'app d'exemples protège la commande de la boutique : /shop/checkout renvoie vers /shop tant que le panier est vide. Voir routes.ts et l'exemple Boutique.

Quand les guards s'appliquent

  • À toutes les navigations : navigate, visit, les liens interceptés, le bouton retour du navigateur.
  • Au chemin courant, au moment où le router rejoint l'application (createApp ou mount) : c'est elle qui fournit les stores. Avant ce moment, ils ne sont pas évalués.
  • Une redirection décidée par un guard suit les mêmes règles qu'une redirection déclarée : le chemin refusé n'entre pas dans l'historique.
  • Un guard qui redirige vers la page courante annule simplement la navigation.
Un store lu par un guard doit être fourni Si un guard lit un contrat que l'application ne fournit pas, une erreur est levée : « guard du router : aucun store fourni pour le contrat "session" ». En test, passe le store (vrai ou faux) à mount(…, { stores, router }).

Liens : this.router.href

  • this.router.href(nom, { params, query }) construit le chemin et encode les valeurs ('a b' devient 'a%20b'). params est obligatoire si le chemin a des paramètres, query toujours facultative.
  • Il n'abonne pas le composant : il ne lit pas la route active, et un changement de route ne re-rend pas un composant qui ne fait que construire des liens.
  • Les valeurs sont typées par la route : { params: { id: '42' } } ne compile pas si id est décrit Number. La query suit les règles de Query.
  • this.router.href('counter') sans id, ou this.router.href('compteur', …), ne compilent pas. Une route sans paramètre ni query refuse toute valeur.
  • Hors composant (un test, un module user-land), Router.href, importé de routes.ts, fait la même chose : Router.href('counter', { params: { id: 'cafes' } }).

L'interception des liens

L'application intercepte les clics sur les liens internes (href commençant par /) et les transforme en navigation, sans rechargement. Le navigateur garde la main dans ces cas :

  • lien externe (https://…, //…) ou relatif (../x) ;
  • attribut target autre que _self (target="_blank") ;
  • attribut download ou data-native ;
  • clic avec Cmd, Ctrl, Shift ou Alt, ou autre bouton que le gauche ;
  • événement déjà annulé par un autre écouteur.

Afficher l'écran : RouterOutlet

RouterOutlet affiche l'écran de la route active, qui lit ses valeurs par this.router.current. C'est un composant comme un autre : on l'écrit <RouterOutlet /> dans une mise en page commune, après l'avoir importé de @super-ts/dom.

Les liens de la coquille sont des RouteLink, du kit d'interface : la cible s'écrit comme pour navigate, et chaque lien pose lui-même aria-current="page" quand il mène à la page affichée. activeFor garde « Compteurs » actif sur un compteur, et « Boutique » sur la commande.

Sans le kit, la coquille lirait le nom de la route active par this.router.current.name (elle se re-rendrait quand la route change) et construirait ses liens par this.router.href (qui, lui, n'abonne pas). aria-current vaudrait 'page' sur le lien de la route active et null sur les autres : un attribut calculé à null est retiré (voir Attributs).

Chaque changement de chemin monte une nouvelle instance de l'écran : passer de /counters/cafes à /counters/pompes construit un nouvel écran, et son état local repart de zéro. Un changement de query ou de hash seul (/counters vers /counters?sort=label) garde l'écran monté : un filtre ou une page de plus ne fait pas perdre l'état local, et l'écran se re-rend s'il lit une valeur qui a changé.

Les rendus en attente passent parents d'abord. Quand l'outlet remplace un écran, l'ancien ne se re-rend donc pas avec une route qui n'est plus la sienne : il est retiré avant.

Le titre de la page

Le titre de l'onglet suit l'écran affiché. Le router en fixe le cadre, par l'option title de createRouter (et non de defineRouter, dont les clés sont des routes) ; l'écran pose son propre titre par @title.

  • default est le titre quand aucun composant n'en pose (la page d'accueil des exemples, par exemple). Sans default, c'est le titre d'origine du document qui revient.
  • suffix est ajouté au titre posé : l'écran de la boutique pose « Boutique », l'onglet affiche « Boutique · Super ».

Dans l'écran, @title reçoit une chaîne (un titre fixe) ou une fonction (un titre suivi), recalculée après chaque rendu avec les mêmes lectures que render :

  • Le titre est posé au montage et retiré au démontage : en changeant de route, l'ancien écran rend la main et le nouveau pose le sien.
  • Tout composant peut poser un titre, pas seulement un écran : les titres forment une pile, le dernier composant monté qui en pose un l'emporte, et à son démontage le titre précédent revient. Dans la démo, KitPage donne leur titre à toutes les pages du kit (@title = () => this.heading;).
  • Ailleurs que dans la déclaration (mounted, un gestionnaire), this.page.title = … fait la même chose.

Le détail (pile, titre impératif, règles) est dans Composants : le titre de la page.

Le router dans un composant

Un composant lit et pilote le router par this.router, sans rien déclarer : la route active (current), une route précise (at), la navigation (send) et les liens (href) ; ses événements s'écoutent par une méthode @on('router', 'navigated'). Rien à importer de routes.ts : la vue est typée par les routes de l'app. Elle se lit partout, render compris, et un composant qui ne la lit pas se monte sans router. @contract router est refusé : le router se lit par this.router. Voir Composants : les déclarations de préparation.

La route active et l'état du router

Un composant lit la route active par this.router.current. Chaque valeur s'appelle, ou se donne à un @selector :

ValeurContenu
current.name()Le nom de la route active ('examples' | 'counters' | 'counter' | …, 'form' étant redirigée), ou null si aucune ne correspond.
current.path()Le chemin courant, tel que navigué (query et hash compris).
current.params.<clé>()Un paramètre du chemin, décodé et converti : 'café' pour /counters/caf%C3%A9. undefined s'il est invalide, ou si la route active ne l'a pas.
current.query.<clé>()Une clé de query déclarée par la route active, convertie : sa valeur, son défaut, undefined, ou [] pour une liste.
….isValid()Sur un paramètre ou une clé de query : l'URL ne portait pas de valeur non conforme, et la route active déclare cette clé.

Le handle renvoyé par createRouter (dans main.ts ou un test) donne l'état complet par router.state() : path, name, params et query (convertis), invalid (les clés dont l'URL portait une valeur invalide : { params: ['id'], query: [] }), et deux champs que seul RouterOutlet utilise : screen, l'écran à afficher (l'écran '*' si aucune route ne correspond ; jamais une redirection, elles sont suivies avant), et errorScreen, l'écran '!'. Un composant n'a pas accès à ces deux-là.

Les commandes du router

CommandeEffet
navigate({ to, params, query })Navigation typée par nom de route. params porte les paramètres du chemin, obligatoire si le chemin en a ; query, facultative, la query déclarée.
visit(chemin)Navigation par chemin brut (c'est ce qu'utilisent les liens interceptés).
back()Revient à l'entrée précédente de l'historique.

Chaque navigation émet navigated { from, to }. Naviguer vers le chemin courant (recliquer sur le lien de la page affichée) n'ajoute rien à l'historique et ne remonte pas l'écran, mais émet quand même navigated, avec from === to : c'est ce qui permet de quitter l'écran '!' en recliquant sur le lien de la page en erreur.

Résolution des chemins

  • Le slash final est ignoré : /counters/cafes/ correspond à counter.
  • La query et le hash sont ignorés pour trouver la route, mais conservés dans path. Les clés de query déclarées sont lues dans query.
  • Seule la forme du chemin compte pour trouver la route : /counters/abc correspond à counter même si id est décrit Number, avec un id invalide.
  • Un chemin sans correspondance donne une route null et l'écran '*' (rien n'est affiché s'il n'est pas déclaré).
  • Les redirections déclarées et celles des guards sont suivies avant d'afficher : path et la route active sont ceux de la destination finale.

Tester avec le router

Un composant qui lit this.router a besoin d'un router. En test, crée-le en mode memory, sur le chemin voulu : l'écran y lit sa route, sans props.
