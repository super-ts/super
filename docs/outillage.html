Outillage des .super

Un fichier .super n'est pas du TypeScript que tsc ou ton éditeur savent lire seuls. Trois outils s'en chargent : la vérification en ligne de commande, le plugin Vite qui le compile, et un serveur de langage pour l'éditeur. Tous partent du même principe : un TS virtuel.

Le principe : un TS virtuel

Chaque .super est traduit en un TypeScript équivalent pour le compilateur : le code du fichier est recopié tel quel, chaque élément devient une suite d'appels typés, et une table de correspondance relie chaque position du TS virtuel à sa position dans le .super. Le compilateur vérifie ce TS virtuel, et les erreurs sont rapportées à la bonne ligne et à la bonne colonne du .super.

  • Les instructions sont recopiées telles quelles (if, for, switch, déclarations) : le rétrécissement de types de TypeScript s'applique au template.
  • Un composant enfant devient l'appel de sa méthode create, dont le typage vérifie déjà props et événements.
  • Le TS virtuel est aussi écrit sur disque, dans .super/virtual/ à côté du tsconfig (ignoré par git), avec, dans .super/types/, une déclaration (.d.ts) des exports du fichier et sa source map vers le .super.
  • Les tsconfig déclarent ces dossiers (rootDirs, paths) : un .ts qui importe un composant .super, comme routes.ts, en voit les types par la déclaration. Le serveur TypeScript de l'éditeur suit sa source map : « aller à la définition » ouvre le .super, dans n'importe quel éditeur.

Vérifier les types : super-tsc

super-tsc écrit le TS virtuel de chaque .super couvert par le tsconfig (son include et son exclude), lance le tsc du projet (TypeScript 7), puis rapporte chaque erreur dans le .super. Les erreurs de syntaxe des .super (un texte ambigu, une balise non fermée) sont rapportées aussi. Les .ts du projet sont vérifiés dans la même passe.

Ce qui est vérifié est détaillé dans Ce que le compilateur vérifie.

Compiler : le plugin Vite

superPlugin compile chaque .super en code lit-html, en dev comme au build et dans les tests (Vitest passe par les mêmes plugins). Un import sans extension trouve un .super : @components/shop donne shop/index.super. Les règles d'architecture du plugin s'appliquent au code compilé, et le remplacement à chaud fonctionne comme pour un composant .ts.

  • Une erreur de syntaxe d'un .super arrête le chargement du module, avec sa position : overlay en dev, échec du build ou du test.
  • En dev, le plugin réécrit aussi le TS virtuel sur disque à chaque modification.

Source maps

Le code compilé garde les numéros de ligne du .super, et le plugin fournit une source map jusqu'à la colonne : une trace d'erreur dans le navigateur ou un point d'arrêt du débogueur pointent la source.

Dans l'éditeur : le serveur de langage

packages/lang-server est un serveur de langage (LSP) construit sur Volar. Il sert les .super, et seulement eux.

  • Les erreurs de TypeScript et de syntaxe, pendant la frappe, avec la correction rapide « Entourer d'accolades » pour un texte ambigu.
  • La réécriture des anciennes formes : une ligne écrite avec une méthode (cart = this.contract('cart');, lines = this.selector(this.cart.selectors.lines);, local = this.state({ … });, input = this.ref<HTMLInputElement>();) est une erreur dans un .super, avec la correction rapide « Écrire @contract » (ou @selector, @state…) qui la remplace par @contract cart;. Un écouteur posé dans le constructeur n'a pas de correction automatique : il devient à la main une méthode @on('cart', 'événement').
  • La complétion dans les expressions, y compris pendant la frappe (if (this., une clé de boucle, une déclaration pas encore terminée).
  • La complétion dans les balises : après <, les composants (ceux du projet pas encore importés ajoutent leur import) et les balises HTML ; après </, la balise à fermer ; dans une balise, ses attributs, ref et ses événements, ou les props (obligatoires d'abord) et les événements d'un composant.
  • La complétion des déclarations : après @ dans le corps d'un composant (hors de ses méthodes), tag, title, prop, emit, puis contract, selector, state, ref, form et on, avec un gabarit (@tag = 'mon-composant';, @prop nom: string;, @contract nom;…). @t propose tag et title, @em propose emit ; un @tag ou un @title déjà écrit n'est plus proposé. Après @contract , les contrats de l'app que le composant ne déclare pas encore sont proposés (@contract cart;, ou errorLog = 'error-log'; pour un nom qui n'est pas un identifiant) ; dans @contract x = '…', les noms de contrats aussi ; dans @on('…', '…'), les contrats puis les événements du contrat choisi (router s'écrit à la main).
  • Le survol et l'aller à la définition ; le survol de @tag, @title, @prop, @emit et des déclarations de préparation (@contract, @on…) affiche leur documentation (forme, valeurs permises, exemple).
  • Le formatage du fichier (voir Formater).
  • Le TS virtuel écrit sur disque à chaque frappe : un .ts ouvert à côté voit tout de suite une nouvelle prop.
TypeScript 6 dans l'éditeur, TypeScript 7 en ligne de commande Volar ne sait pas encore piloter TypeScript 7. Le serveur de langage a donc son propre paquet (packages/lang-server, avec ses dépendances) et tourne sur TypeScript 6, tandis que super-tsc utilise le TypeScript 7 du projet. Les deux donnent les mêmes erreurs sur ce que fait la démo.

Formater

Le TS d'un .super est formaté par Biome, avec la configuration du dépôt : chaque élément de premier niveau y est remplacé par une instruction de substitution, que Biome place et indente comme les autres. Le formateur des .super imprime ensuite les templates à ces emplacements :

  • Une balise sur une ligne si elle tient dans la largeur (140 colonnes), sinon un attribut par ligne et les enfants indentés.
  • Un composant qui reçoit des enfants, et un emplacement <:nom>, toujours sur plusieurs lignes, même s'ils tiennent : ce qui va dans quel emplacement se lit d'un coup d'œil.
  • Du texte suivi remplit les lignes, avec ses éléments en ligne (<code>, <strong>) ; une liste d'éléments sans texte garde un élément par ligne.
  • Les instructions (if, for, switch, déclarations) et leurs blocs sont indentés, les lignes vides entre enfants sont gardées (une au plus).
  • Les déclarations d'un composant (@tag = …;, @title = …;, @prop, @emit) sont gardées et indentées comme les autres membres de la classe, bien que @tag et @title ne soient pas du TS valide.

Le rendu ne change jamais : une ligne n'est coupée que là où il y a déjà un blanc, ou au bord d'un élément, d'un bloc ou d'une instruction, où les blancs ne rendent rien (voir les espaces). Les tests le vérifient sur chaque .super du dépôt. Un fichier qui a des erreurs de syntaxe n'est pas formaté.

Dans l'éditeur, le serveur de langage formate le fichier (formatage à l'enregistrement dans Zed, voir ci-dessous).

Zed

L'extension de editors/zed déclare le langage « Super » pour les fichiers .super et lance le serveur : celui du paquet super-language-server s'il est installé dans le projet, sinon packages/lang-server, avec le Node du PATH. Comme les .super ont leur propre langage, vtsls, le serveur TypeScript habituel de Zed, ne les voit pas.

  • Installer : Rust par rustup, puis zed: install dev extension sur le dossier editors/zed (voir son README). La compilation se suit dans zed: open log.
  • Coloration : la grammaire Tree-sitter des .super (editors/tree-sitter-super), celle de TSX étendue aux instructions écrites entre les balises : if, for … ; key, switch et les déclarations y sont colorés comme du code, pas comme du texte. Elle connaît aussi @tag = …; et @title = …; dans le corps d'une classe (règle super_declaration), que TSX refuserait.
  • Commentaires : entre des balises, cmd+/ écrit {/* … */}.
  • Formatage : par le serveur, à l'enregistrement ; jamais par Prettier.
  • Aller à la définition depuis un .ts : vtsls suit la source map de la déclaration du composant et ouvre le .super (voir le principe).

Après une mise à jour du serveur, relance-le depuis un .super ouvert : editor: restart language server. Après une modification de l'extension elle-même : Rebuild dans le panneau des extensions. Après une mise à jour de la grammaire (comme l'ajout de @tag et @title), réinstalle l'extension : zed: install dev extension sur editors/zed.

Les limites de ce montage sont listées dans Limites.
