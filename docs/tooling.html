Tooling

A .super file is not TypeScript that tsc or your editor can read on their own. Three tools handle it: the command-line check, the Vite plugin that compiles it, and a language server for the editor. All of them rest on the same principle: a virtual TypeScript.

The principle: a virtual TypeScript

Each .super file is translated into equivalent TypeScript for the compiler: the file's code is copied as is, each element becomes a sequence of typed calls, and a mapping table links each position in the virtual TS to its position in the .super file. The compiler checks this virtual TS, and errors are reported at the right line and column of the .super file.

  • Statements are copied as is (if, for, switch, declarations): TypeScript's type narrowing applies to the template.
  • A child component becomes a call to its create method, whose typing already checks props and events.
  • The virtual TS is also written to disk, in .super/virtual/ next to the tsconfig (ignored by git), with, in .super/types/, a declaration (.d.ts) of the file's exports and its source map back to the .super file.
  • The tsconfig files declare these folders (rootDirs, paths): a .ts file that imports a .super component, such as routes.ts, sees its types through the declaration. The editor's TypeScript server follows its source map: "go to definition" opens the .super file, in any editor.

Type check: super-tsc

super-tsc writes the virtual TS of each .super file covered by the tsconfig (its include and exclude), runs the project's tsc (TypeScript 7), then reports each error in the .super file. Syntax errors in .super files (ambiguous text, an unclosed tag) are reported too. The project's .ts files are checked in the same pass.

What is checked is detailed in What the compiler checks.

Compiling: the Vite plugin

superPlugin compiles each .super file into lit-html code, in dev, at build time and in tests (Vitest goes through the same plugins). An import without an extension finds a .super file: @components/shop resolves to shop/index.super. The plugin's architecture rules apply to the compiled code, and hot replacement works as it does for a .ts component.

  • A syntax error in a .super file stops the module from loading, with its position: overlay in dev, failed build or test.
  • In dev, the plugin also rewrites the virtual TS to disk on each change.

Source maps

The compiled code keeps the line numbers of the .super file, and the plugin provides a source map down to the column: an error trace in the browser or a debugger breakpoint points to the source.

In the editor: the language server

packages/lang-server is a language server (LSP) built on Volar. It serves .super files, and only them.

  • Errors from TypeScript and syntax, as you type, with the quick fix "Wrap in braces" for ambiguous text.
  • Rewriting old forms: a line written with a method (cart = this.contract('cart');, lines = this.selector(this.cart.selectors.lines);, local = this.state({ … });, input = this.ref<HTMLInputElement>();) is an error in a .super file, with the quick fix "Write @contract" (or @selector, @state…) that replaces it with @contract cart;. A listener set up in the constructor has no automatic fix: you turn it by hand into an @on('cart', 'event') method.
  • Completion in expressions, including while typing (if (this., a loop key, an unfinished declaration).
  • Completion in tags: after <, components (those of the project not yet imported add their import) and HTML tags; after </, the tag to close; inside a tag, its attributes, ref and its events, or a component's props (required ones first) and events.
  • Declaration completion: after @ in a component's body (outside its methods), tag, title, prop, emit, then contract, selector, state, ref, form and on, with a snippet (@tag = 'my-component';, @prop name: string;, @contract name;…). @t suggests tag and title, @em suggests emit; an @tag or @title already written is no longer suggested. After @contract , the app's contracts that the component does not declare yet are suggested (@contract cart;, or errorLog = 'error-log'; for a name that is not an identifier); in @contract x = '…', contract names too; in @on('…', '…'), contracts then the events of the chosen contract (router is written by hand).
  • Hover and go to definition; hovering @tag, @title, @prop, @emit and the setup declarations (@contract, @on…) shows their documentation (form, allowed values, example).
  • File formatting (see Formatting).
  • The virtual TS written to disk on each keystroke: a .ts file open alongside sees a new prop straight away.
TypeScript 6 in the editor, TypeScript 7 on the command line Volar cannot drive TypeScript 7 yet. The language server therefore has its own package (packages/lang-server, with its dependencies) and runs on TypeScript 6, while super-tsc uses the project's TypeScript 7. Both give the same errors on what the demo does.

Formatting

The TS of a .super file is formatted by Biome, with the repository's configuration: each top-level element is replaced by a placeholder statement, which Biome places and indents like the others. The .super formatter then prints the templates at those positions:

  • A tag on one line if it fits within the width (140 columns), otherwise one attribute per line and indented children.
  • A component that receives children, and an <:name> slot, always on several lines, even if they fit: what goes into which slot is readable at a glance.
  • Running text fills the lines, with its inline elements (<code>, <strong>); a list of elements without text keeps one element per line.
  • Statements (if, for, switch, declarations) and their blocks are indented, blank lines between children are kept (one at most).
  • A component's declarations (@tag = …;, @title = …;, @prop, @emit) are kept and indented like the other class members, even though @tag and @title are not valid TS.

The rendering never changes: a line is only broken where there is already whitespace, or at the edge of an element, a block or a statement, where whitespace renders nothing (see whitespace). The tests check this on every .super file in the repository. A file with syntax errors is not formatted.

In the editor, the language server formats the file (format on save in Zed, see below).

Zed

The extension in editors/zed (id super-lang) declares the "Super" language for .super files and starts the server. It installs @super-ts/language-server from npm at the version of @super-ts/lang in the project, so the editor and the compiler agree, or the latest version in a project without Super, and runs it with Zed's Node. A binary set in the settings (lsp.super-language-server.binary) takes precedence: the Super repository uses it to run the server from its sources (.zed/settings.json). Since .super files have their own language, vtsls, Zed's usual TypeScript server, does not see them.

  • Installing: Rust via rustup, then zed: install dev extension on the editors/zed folder (see its README). You can follow the build in zed: open log.
  • Highlighting: the Tree-sitter grammar for .super files (editors/tree-sitter-super), the TSX one extended to statements written between tags: if, for … ; key, switch and declarations are highlighted as code, not as text. It also knows @tag = …; and @title = …; in a class body (rule super_declaration), which TSX would reject.
  • Comments: between tags, cmd+/ writes {/* … */}.
  • Formatting: by the server, on save; never by Prettier.
  • Go to definition from a .ts file: vtsls follows the source map of the component's declaration and opens the .super file (see the principle).

After a server update, restart it from an open .super file: editor: restart language server. After a change to the extension itself: Rebuild in the extensions panel. After a grammar update (such as the addition of @tag and @title), reinstall the extension: zed: install dev extension on editors/zed.

The limitations of this setup are listed in Limitations.
