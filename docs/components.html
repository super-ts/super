Components

A component is a typed custom element, written as a class that extends SuperElement. Its declarations and fields prepare the instance once; render() displays on every render.

Defining a component

A component lives in a .super file under src/@components/, for example src/@components/shop/index.super. It is an ordinary TypeScript module, with one difference: in its methods, HTML is written directly, as elements placed like statements (see Templates). An import without an extension finds it: @components/shop refers to shop/index.super.

A component class is made of four parts:

PartRole
extends SuperElementThe base class, with no generic in a .super file: the compiler derives the component's types from its declarations.
The declarations@tag (the custom element name, required, with a hyphen), then as needed @prop for the props received, @emit for the events emitted to the parent, @title for the page title. See Component declarations. A screen receives no props from the router: it reads its route through this.router.current, typed from its route without declaring anything (see The screen and its route).
The preparationContracts (@contract), read values (@selector), local state (@state), the form (@form), references (@ref), listeners (@on on a method), and actions as fields. See Preparing.
render()The component's HTML, required, written as elements in the method body, with no return. An optional renderError(error) method replaces it if the component or a descendant crashes (see Handling errors).

The component imports nothing from @core/, except types: it talks to stores through @contract name; (and to the router through this.router), and the Vite plugin checks this.

Component declarations

What describes the component from the outside is written at the top of its class body: its tag, its props, its events, and the page title while it is mounted. No generic on SuperElement, no type Props above the class: the compiler derives the component's types from these lines, and checks them at every tag that uses it. What the component prepares once (contracts, reads, state, form, references, listeners) is declared the same way: see Preparing.

DeclarationMeaning
@tag = 'x-y';The custom element name. Required (except for an abstract class), a lowercase string with a hyphen. Unique in the app: a second component with the same tag throws an error on its first create.
@prop name: T;A required prop, read through this.name.
@prop name?: T;An optional prop (T | undefined).
@prop name: T = value;An optional prop with a default value, computed once per instance.
@emit name: T;An event, emitted through this.emit('name', payload) (void if it carries nothing).
@title = …;The page title while the component is mounted: a string, or a tracked function. See The page title.

Props

A prop is read by its name, this.question, anywhere in the class and from the fields onwards. Reading always gives the current value, and a prop change re-renders the component. this.props still exists (all the props, read-only), but you write this.name. The three forms are detailed in Parents and children.

  • The content written between the tags fills the content prop. It is declared like the others (@prop content: Children;) and read through this.content. See Composing: children.
  • Native property names are rejected. The component is a DOM element: a prop cannot be called id, title, hidden, slot… The type error says so: "title is already a property of HTML elements: choose another name". In the demo, title became heading (KitPage, Card) and id became counterId (CounterListItem). A route parameter id is likewise read into a field with a different name: counterId = this.router.current.params.id;.
  • page is reserved: it is this.page, which holds the page title.

Events

@emit name: T; declares an event and what it carries (void if it carries nothing). The component emits it through this.emit('name', payload), the parent listens to it through on:name={…} on the tag. See emit in the child, on in the parent.

What the compiler rejects

  • A missing tag, one written static tag = … (a quick fix rewrites it as @tag), or one that is not a lowercase string with a hyphen.
  • A hand-written generic: "In a .super file, props and events are declared in the class: @prop name: Type; and @emit name: Type;".
  • A duplicate declaration, a prop without a type, a ? with a default value, an @emit with a value, a declaration outside a component.

A component written in a .ts file (RouterOutlet, the components of @super-ts/ui, the framework's tests) does not have these declarations: it keeps static tag and the generic, and reads its props through this.props. It also prepares through methods (this.contract(…), this.selector(…), this.state(…), this.form(…), this.ref<T>(), .on(…) in the constructor).

Preparing: stores, reads, state, form, references, listeners

What the component prepares once, when it is constructed, is also declared in its class body: the contracts it reads, its read values, its local state, its form, its references and its listeners. Most components therefore no longer have a constructor.

  • No type on @contract, @selector, @state, @form: it comes from the value. To widen it, write as in the value (null as string | null). @ref, conversely, declares the type of its element and has no value.
  • The value of @contract x = '…' is a string written as is, the contract name: @contract log = 'error-log'; reads the error-log contract under the name this.log.
  • Order matters, as with fields: a @selector or a @form that reads this.cart comes after @contract cart.

Listeners: @on

A listener is declared on a method: @on('contract', 'event') above it, and the method is called on every event while the component is mounted. No more need for a constructor to set up a listener.

  • @on does not require @contract: it opens access to the contract itself. A component that only listens to profile does not need @contract profile;.
  • The method's parameter is typed by the event: for save:done, { input, result }; for save:failed, { input, reason }. No need to annotate it.
  • @on('router', 'navigated') listens to the router, like this.router.on('navigated', …).
  • The event name is a string written as is, with no template literal (`${change}:done`): one method per event. In the demo, CounterScreen declares onIncremented, onDecremented, onReset, onIncrementFailed…, which all call #done or #failed (see the excerpt at the top of the page).

Why @form and not a <Form> component

A form is component state: its values, its errors, its checks, its submission, read throughout the template (this.edit.field('name'), this.edit.values(), the "Saving…" button). The tag itself already exists: it is the native <form>, bound through <form {this.edit.bind()}>. A <Form> would hide this state and lose the typing of the fields. <Table>, on the other hand, is a component because it only displays.

Preparation errors

  • A contract declared twice: "The contract cart is already declared by @contract cart".
  • @contract router: "The router is read through this.router, without @contract".
  • A type on @contract, @selector, @state or @form: "No type on @selector: it comes from the value".
  • The old forms, in a .super file: local = this.state({ … }) gives "In a .super file, this.state(…) is declared with @state: @state local = …;", with a quick fix that rewrites the line (likewise for this.contract, this.selector, this.form and this.ref).
  • A this.x.on(…) in the constructor: "In a .super file, a listener is declared on a method: @on('x', 'event') onEvent(payload) { … }". No automatic fix: the method has to be written.

Outside a component, nothing changes: a store that listens to another store keeps cart.on('add:done', …) in its constructor, main.ts keeps cart.subscribe(…), and a store's handle, in a test, keeps counter.on('increment:done', …).

In the editor

An @ typed in a component body suggests tag, title, prop, emit, contract, selector, state, form, ref and on, with a template to fill in; @t only suggests tag and title, and an @tag or @title already written is no longer suggested. Hovering each declaration shows its documentation. After @contract , the editor suggests the app's contracts that the component does not declare yet. In @contract x = '…' and @on('…', '…'), the editor completes the names of the app's contracts, then those of the events of the chosen contract. @prop and @emit are valid TypeScript (decorated fields); @tag = … and @title = … are not, but the formatter and Zed's Tree-sitter grammar know them (see Tooling).

Preparation is blocked during render. In a .super file, it is only written through declarations, outside render. The methods they call (contract, state, selector, ref and form, written as is in a .ts file) throw an error if they are called during render: you cannot resolve a store or create state on every render. A contract's on listener is allowed in a handler or in mounted, but throws an error during a render; so does this.page.title (see The page title). The error goes through the component's renderError, like any render error.

Props are readable from the declarations and fields onwards: Super sets them before constructing the instance. A value copied at that point (@state local = { draft: this.text };, the initial values of an edit form) does not follow later changes: for an always up-to-date value, read the prop (this.text) in render, in a selector function or in a listener, like the @on methods of CounterScreen, which call this.counterId() when the event arrives and so read the current route.

Where to put what: preparation or render?

The question to ask: should this exist only once for the instance, or is it recomputed from the current values?

@title = () => …declarationThe title is set once; the function itself is recomputed after every render.
@contract counter;declarationResolving a store is wiring, done once. During a render, it throws an error.

In short: preparation carries the verbs declare, subscribe, listen, prepare; render carries the verbs read, decide, display. render must be callable ten times in a row with no consequence.

The classic mistake: reading a value in a field

A field is initialised when the instance is created: props are readable, but the store is not resolved yet, and a value read at that point would not follow changes.

A component for a side effect

In the Widget example: timer-shortcuts.super. A keyboard shortcut on window, cleaned up through signal.

Some components exist mainly for what they do on mount, not for what they display. Everything they set up with this.signal, or through an @on listener, is cleaned up on unmount.

Typical cases: sending a command on mount, listening to an event to trigger an action elsewhere (analytics, sound, focus), setting a listener on window. A component that displays nothing keeps an empty render: render() {} (see Rendering nothing).

A field or a prop cannot have the name of a native HTMLElement property (slot, title, hidden, id…): the component is a DOM element, and that name is already taken. page is likewise reserved, for this.page. mounted and unmounted

In the Widget example: timer-widget.super. An interval started on mount, stopped on unmount.

The shell reads nothing from the counter store: it never re-renders for it. It only uses it to load the counters once, on mount.

Use mounted when you need the already rendered DOM (measuring, giving focus) or to start an action on mount. What must stop on unmount stops in unmounted:

Lifecycle

  1. Creation: the parent's tag (or create) sets the props, then constructs the instance (declarations and fields, in order, then the constructor if there is one), which already reads them.
  2. Mount: the element enters the DOM. Super resolves the declared contracts, wires the @on listeners, performs the first render, sets its title if it declares one, then calls mounted.
  3. Renders: on every change of props, local state or a value read from a store. Several changes in the same task give only one render.
  4. Move: an element moved in the DOM (for example by a for loop with key) is not restarted: it keeps its state.
  5. Unmount: a real removal from the DOM aborts signal, unsubscribes the component from its stores (reads and @on listeners), removes its title, then calls unmounted. If it is reinserted later, the same instance mounts again: its contracts are resolved again, its @on listeners rewired, its title set again, and mounted called again. Its local state is kept.

The page title

The tab title (document.title) belongs to the mounted components: a component sets it through @title, and removes it when it unmounts. Nobody writes document.title by hand.

A fixed or tracked title

A string gives a fixed title, set on mount and removed on unmount: @title = 'Widget';. A function gives a tracked title: it is recomputed after every render, with the same reads as render. The shop's title therefore changes with the cart:

The computation is free (a condition, formatting), unlike the function of a @selector. In a counter's screen, @title = () => this.label.value ?? 'Counter not found'; follows the counter's name: renaming it also changes the tab title.

this.page.title

@title is a shortcut: this.page.title = … does the same thing imperatively, with a string or a function. What changes is when you write it.

The title stack

Several mounted components can set a title at the same time. The last one mounted wins; those below keep following their data without being displayed; when it unmounts, the previous title comes back. Any component can set a title, not just a screen: in the demo, KitPage, the shared layout of the kit, gives all the kit pages their title with @title = () => this.heading;.

What is forbidden

  • Setting the title during render: this.page.title throws an error ("cannot be set during render").
  • Reading the title: this.page.title is set, not read; reading it throws an error.
  • A prop named title: it is a property of HTML elements (the demo calls it heading). page is reserved.

Creating an element outside a template

In a .super file, <CounterControls count={count} … /> mounts the child at this position (see Parents and children); the tooling translates it into CounterControls.create(props, { on }). Outside a template, for the initial mount or a test, you call this create(props?, { on }?) directly: it returns the element.

A component is not written by its tag: <counter-screen> typed in a template or in index.html is not supported. It always goes through its class, as a tag (<CounterControls count={count} … />) or through create.
