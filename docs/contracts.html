Contrats

Un contrat décrit un store vu de l'extérieur : ce qu'on peut lire, ce qu'on peut lui demander, ce qu'il annonce. C'est la seule chose qu'un composant connaît d'un store.

Déclarer un contrat

Un contrat tient en trois morceaux :

  1. Un type (CounterTypes) qui décrit son état, ses commandes et ses événements, pour le compilateur.
  2. Une classe qui étend SuperContract<CounterTypes> et se nomme dans son constructeur : super({ name: 'counter' }). Ce nom est la clé du contrat dans toute l'app : un composant déclare @contract counter;, un store déclare super({ contract: 'counter', … }).
  3. Des méthodes, facultatives : chacune est un sélecteur, une lecture autorisée de l'état (voir Sélecteurs).

Un contrat vit dans src/@core/<nom>/contract.ts, un dossier par contrat, à côté de son store. Le plugin Vite lit ces fichiers et génère src/@core/contracts.d.ts, le dictionnaire nom → classe qui type @contract counter;, @on('counter', …) et StoreOfContract<'counter'>. Ce fichier se committe, mais ne s'écrit jamais à la main.

Les trois clés : state, commands, events

Ce contrat minimal est valide :

state : l'interface de l'état

state est le type de ce que le store garde en mémoire. Il fixe la forme de l'initialState passé au constructeur du store, ce que le store lit avec this.get() et modifie avec this.set(), et le premier paramètre des sélecteurs. Les composants ne voient jamais cette interface : ils lisent à travers les sélecteurs.

commands : les demandes

Une commande est une demande adressée au store. Elle prend au plus un paramètre, le body (un objet, plus lisible et extensible que plusieurs arguments), et rien ne revient à celui qui l'envoie. En pratique, une commande modifie souvent l'état, mais pas forcément. La règle qui compte est dans l'autre sens : seul le store modifie son état.

Une commande déclare l'un ou l'autre :

  • void : elle n'a pas d'issue particulière à publier (en dehors d'un échec inattendu).
  • Outcome<Résultat, Raisons> : ce que produit son succès (publié dans increment:done), et la liste fermée de ses raisons d'échec (publiées dans increment:failed). Voir Déclarer l'issue.
Rien ne revient à l'appelant

Une réponse directe, ou plusieurs paramètres, ne compilent pas :

C'est un choix de conception : le composant envoie et laisse filer, et Super publie l'issue à tous ceux qui l'écoutent. void suffit même si la méthode du store est async.

events : les annonces

Dans l'exemple Boutique : cart/contract.ts.

Chaque commande a déjà ses événements, publiés par Super : increment:done et increment:failed. La clé events sert aux autres faits que le store annonce, ceux qui ne sont pas l'issue d'une seule commande. Un événement associe un nom à son payload. Seul le store émet (avec this.emit) ; tout le monde peut écouter : composants, autres stores, tests.

Un événement avec payload s'écrit synced: { at: number } et s'émet par this.emit('synced', { at: Date.now() }).

Ce qu'un contrat n'est pas

  • Pas une implémentation. Il ne dit pas comment les commandes sont traitées : c'est le rôle du store.
  • Pas une instance. Un contrat ne porte aucun état. Il peut exister plusieurs stores pour le même contrat (un par test, par exemple).
  • Pas les dépendances du store. Le CounterRepository n'apparaît pas dans le contrat : c'est un détail d'implémentation, déclaré par le constructeur du store.

À l'exécution, Super ne lit d'un contrat que son nom et ses méthodes (les sélecteurs). Les types state, commands et events n'existent que pour le compilateur.

Pièges

Une clé mal orthographiée est refusée command au lieu de commands (ou event au lieu de events) ne compile pas : l'erreur apparaît sur super({ name }), avec la clé en cause et les clés attendues (« clé inconnue dans les types du contrat : command (attendu : state, commands, events) »).
Le nom s'écrit en toutes lettres Le plugin lit super({ name: 'counter' }) dans le source : le nom doit être une chaîne littérale. Deux contrats du même nom sont refusés, et 'router' est réservé au router de l'app.
L'état des sélecteurs s'annote à la main TypeScript n'infère pas les paramètres d'une méthode : écris count(s: CounterState, id: string). Ce premier paramètre est vérifié à la déclaration du store (SuperStore<CounterContract>) : un type qui n'accepte pas l'état du contrat ne compile pas.
