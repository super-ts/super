Templates: .super files

A component is written in a .super file: TypeScript whose methods contain HTML elements written as statements. Control flow is TypeScript's (if, for, switch), and the whole template is checked by the compiler: props, events, attributes, references.

A .super file

  • The component is declared in its class: @tag for its tag, @prop for its props (read through this.label), @emit for its events, without generics. See Components: declarations.
  • What it prepares once is declared too: @contract for a store, @selector for a reading (read through this.count.value), and likewise @state, @form, @ref and the @on('contract', 'event') listeners. See Components: setup declarations.
  • Everything else is TypeScript: imports, types, fields, methods. Only the elements and these declarations are new.
  • You import it without an extension, like a .ts: import { ConfirmDialog } from '../shared/confirm-dialog', or @components/shop for shop/index.super.
  • A module without a template stays a .ts: contracts, stores, domain, routes, tests.

The Vite plugin compiles the file, npm run typecheck checks it and the editor understands it: see Tooling for .super files.

Elements written as statements

An element is written where TypeScript expects a statement, in a method of the class, and it is emitted at that point. render() returns nothing: it emits. Several elements in a row are allowed, without a common root.

  • No element inside an expression: const x = <p /> or () => <p /> are refused. To reuse a piece, write a method (see Fragments).
  • return; stops the render while keeping what is already emitted. return x; is refused in a method that emits elements: it returns what it emits.
  • An element without children is closed with /> (<div />), except HTML void elements (<br>, <input>, <img>…).

Text

Text is written as is between the tags. A child is read as a statement only if it starts with a reserved form:

Start of the childRead as
if (, for (, switch (A control statement
const or let, a name or a destructuring, then =A declaration
Everything else (Total:, if you need help, let me know)Text

Text that starts with a reserved form without being one is an error, never a guess. The editor offers the fix: wrapping it in braces.

<, { and } are not written in text: {'<'}, {'{'}, {'}'}. Between tags, // is text: a comment is written {/* … */}.

Whitespace

It follows HTML rules, like an HTML template written by hand:

  • Each run of whitespace counts as one space, line breaks included: containing then <code>offline</code> on the next line displays "containing offline".
  • Whitespace at the start and end of an element or block renders nothing: <button>, a line break, −, a line break, </button> gives a "−" button.
  • Two elements of the method separated only by whitespace are separated by a space; if there is code between them, they are not.

Interpolations

{expression} displays a string, a number or a boolean. null and undefined display nothing. An object is refused by the compiler, which avoids [object Object].

Everything is escaped {'<b>Ada</b>'} displays the text "<b>Ada</b>", without creating a tag. Data entered by a user cannot inject HTML.

  • A tag without a hyphen must exist in HTML or SVG: <dvi> is an error. A tag with a hyphen is a custom element.
  • lit syntax is refused, with the form to use: @click → on:click, ?disabled → disabled, .value → prop:value.

Events

on:event={handler} adds a listener. On an HTML tag, the name must be an event of that tag (on:clik is an error) and the handler receives the typed event, with currentTarget typed as the element.

On a child component, on: subscribes to its events, declared with @emit (see Child components). An error thrown in a handler is reported to onError (see Handling errors).

Showing or not: if

An if in the template is TypeScript's if, with its type narrowing: after if (user), user is no longer null.

else if and else are written as in TypeScript. The body of a block follows the same rules as an element's children.

Lists: for

Only for…of is accepted. key, after a ; inside the parentheses, identifies each item: when the order changes, elements are moved rather than recreated, and child components keep their local state.

Without key, rendering is positional: that is enough for a list whose order never changes. A loop over a single key recreates an area when the key changes: for (const _round of [round]; key _round) { … } in the errors screen.

Choosing: switch

Each case stops at the next case or default: no fall-through, and break is not needed. On a union, a default that calls a function expecting never makes the choice exhaustive: TypeScript flags a forgotten case.

Declarations in the template

A const or let declaration can be written among the children, ended with ;. It is visible to the children that follow it, in the same element or the same block.

Child components

A tag that starts with a capital letter is a component, a SuperElement class in scope:

  • The attributes are its props, checked against its @prop declarations: a missing, extra or wrongly typed prop is an error.
  • on:x subscribes to its @emit, with the type of the emitted data.
  • No directive on a component: {…} in the tag goes on an HTML element.

See Parents and children.

Named slots

A named slot (the modal's footer) is another prop of type Children, declared like the others (@prop footer?: Children;) and read through this.footer. It can be filled in two ways, as you prefer.

With a <:name> slot, written between the component's tags, where it is used:

With a method that emits elements: such a method returns Children (see Fragments).

The method is mostly useful for a list of slots, such as tabs whose panels are a panels: Children[] prop: <Tabs labels={['Profile', 'Security']} panels={[this.#profile(), this.#security()]} />.

  • Everything is checked against the component's @prop declarations: children for a component that declares none, required children or slots that are missing, an unknown slot.
  • The children stay the parent's: their listeners, their store readings and their state are the parent's, and they follow its render. The component receiving them keeps them when it re-renders on its own.
  • A <:name> slot goes directly inside a component, without attributes, once per name. <:content> does not exist: the direct children already fill content.
  • In the editor, <: inside a component suggests its slots.
  • A complete example: the Composition screen of the examples app.

References

ref={…} links an element to a reference declared with @ref name: T;. The element's type is checked: an HTMLInputElement reference put on a <div> is an error.

Reusable fragments

Not everything needs to be a component. A method that emits elements is reused in render through an interpolation of its call. It returns what it emits, of type Children: return x; is refused there, and its call can also fill a component's named slot.

Create a component when you need local state, a store, events or an independent re-render (like a list row).

Rendering nothing

A method that emits no element renders nothing: render() {} is an empty component, and an if without else renders nothing when its condition is false.

DOM and styles

  • The DOM is patched, not replaced: focus and ongoing input survive a re-render.
  • Light DOM: no shadow DOM. Your global styles apply to components, and you can target their tag in CSS (counter-list-item { display: contents; }).
  • A root element is not needed: render can emit several top-level elements.

Component styles

Super has no styling system: a component is a DOM element like any other. The examples app follows a simple convention you can reuse: one stylesheet per component, placed next to it (index.css for a screen, counter-controls.css for a child component), imported by the component, with its rules nested under its tag.

  • The tag acts as a scope: nesting under app-shell keeps an .app-header class from affecting the rest of the page, without shadow DOM.
  • The component loads what it needs: Vite includes the stylesheet as soon as the component is imported, and drops it once it no longer is.
  • Global styles first: main.ts imports styles.css (variables, typography, base elements) before any component, so that the component stylesheets come after.

What about html, nothing, repeat?

@super-ts/dom still exports html, nothing and repeat, the lit-html building blocks the compiler relies on. A component written in .ts whose render returns an html`…` still works, but its template is not checked by the compiler. Write your components in .super.
