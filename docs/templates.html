Templates : les fichiers .super

Un composant s'écrit dans un fichier .super : du TypeScript dont les méthodes contiennent des éléments HTML écrits comme des instructions. Le contrôle de flux est celui de TypeScript (if, for, switch), et tout le template est vérifié par le compilateur : props, événements, attributs, références.

Un fichier .super

  • Le composant se déclare dans sa classe : @tag pour son tag, @prop pour ses props (lues par this.label), @emit pour ses événements, sans générique. Voir Composants : les déclarations.
  • Ce qu'il prépare une fois se déclare aussi : @contract pour un store, @selector pour une lecture (lue par this.count.value), et de même @state, @form, @ref et les écouteurs @on('contrat', 'événement'). Voir Composants : les déclarations de préparation.
  • Tout le reste est du TypeScript : imports, types, champs, méthodes. Seuls les éléments et ces déclarations sont nouveaux.
  • On l'importe sans extension, comme un .ts : import { ConfirmDialog } from '../shared/confirm-dialog', ou @components/shop pour shop/index.super.
  • Un module sans template reste un .ts : contrats, stores, domaine, routes, tests.

Le plugin Vite compile le fichier, npm run typecheck le vérifie et l'éditeur le comprend : voir Outillage des .super.

Des éléments écrits comme des instructions

Un élément s'écrit là où TypeScript attend une instruction, dans une méthode de la classe, et il est émis à cet endroit. render() ne renvoie rien : il émet. Plusieurs éléments à la suite sont permis, sans racine commune.

  • Pas d'élément dans une expression : const x = <p /> ou () => <p /> sont refusés. Pour réutiliser un morceau, écris une méthode (voir Fragments).
  • return; arrête le rendu en gardant ce qui est déjà émis. return x; est refusé dans une méthode qui émet des éléments : elle renvoie ce qu'elle émet.
  • Un élément sans enfant se ferme par /> (<div />), sauf les éléments vides du HTML (<br>, <input>, <img>…).

Le texte

Le texte s'écrit tel quel entre les balises. Un enfant est lu comme une instruction seulement s'il commence par une forme réservée :

Début de l'enfantLu comme
if (, for (, switch (Une instruction de contrôle
const ou let, un nom ou une déstructuration, puis =Une déclaration
Tout le reste (Total :, if you need help, let me know)Du texte

Un texte qui commence par une forme réservée sans en être une est une erreur, jamais une devinette. L'éditeur propose la correction : l'entourer d'accolades.

<, { et } ne s'écrivent pas dans le texte : {'<'}, {'{'}, {'}'}. Entre les balises, // est du texte : un commentaire s'écrit {/* … */}.

Les espaces

Ils suivent les règles du HTML, comme un template HTML écrit à la main :

  • Chaque suite de blancs compte pour une espace, retours à la ligne compris : contenant puis <code>offline</code> à la ligne suivante s'affiche « contenant offline ».
  • Les blancs au début et à la fin d'un élément ou d'un bloc ne rendent rien : <button>, un retour à la ligne, −, un retour à la ligne, </button> donne un bouton « − ».
  • Deux éléments de la méthode séparés seulement par des blancs sont séparés par une espace ; s'il y a du code entre eux, non.

Interpolations

{expression} affiche une chaîne, un nombre ou un booléen. null et undefined n'affichent rien. Un objet est refusé par le compilateur, ce qui évite les [object Object].

Tout est échappé {'<b>Ada</b>'} affiche le texte « <b>Ada</b> », sans créer de balise. Une donnée saisie par un utilisateur ne peut pas injecter de HTML.

  • Une valeur d'attribut est une chaîne, un nombre, un booléen, null ou undefined.
  • Une balise sans tiret doit exister en HTML ou en SVG : <dvi> est une erreur. Une balise avec tiret est un élément personnalisé.
  • La syntaxe de lit est refusée, avec la forme à utiliser : @click → on:click, ?disabled → disabled, .value → prop:value.

Événements

on:événement={gestionnaire} pose un écouteur. Sur une balise HTML, le nom doit être un événement de cette balise (on:clik est une erreur) et le gestionnaire reçoit l'événement typé, avec currentTarget du type de l'élément.

Sur un composant enfant, on: s'abonne à ses événements, déclarés par @emit (voir Composants enfants). Une erreur levée dans un gestionnaire est signalée à onError (voir Gérer les erreurs).

Afficher ou non : if

Un if dans le template est le if de TypeScript, avec son rétrécissement de types : après if (user), user n'est plus null.

else if et else s'écrivent comme en TypeScript. Le corps d'un bloc suit les mêmes règles que les enfants d'un élément.

Listes : for

Seul for…of est accepté. key, après un ; dans les parenthèses, identifie chaque élément : quand l'ordre change, les éléments sont déplacés plutôt que recréés, et les composants enfants gardent leur état local.

Sans key, le rendu est positionnel : il suffit pour une liste qui ne change jamais d'ordre. Une boucle à une seule clé recrée une zone quand la clé change : for (const _round of [round]; key _round) { … } dans l'écran des erreurs.

Choisir : switch

Chaque case s'arrête au case ou au default suivant : pas de cascade, et break est inutile. Sur une union, un default qui appelle une fonction attendant never rend le choix exhaustif : TypeScript signale un cas oublié.

Déclarations dans le template

Une déclaration const ou let peut s'écrire au milieu des enfants, terminée par ;. Elle est visible des enfants qui la suivent, dans le même élément ou le même bloc.

Composants enfants

Une balise qui commence par une majuscule est un composant, une classe SuperElement en portée :

  • Les attributs sont ses props, vérifiés contre ses @prop : une prop manquante, en trop ou mal typée est une erreur.
  • on:x s'abonne à ses @emit, avec le type de la donnée émise.
  • Pas de directive sur un composant : {…} dans la balise se place sur un élément HTML.

Un emplacement nommé (le pied de la modale) est une autre prop de type Children, déclarée comme les autres (@prop footer?: Children;) et lue par this.footer. Elle se remplit de deux façons, au choix.

Par un emplacement <:nom>, écrit entre les balises du composant, là où il est utilisé :

Par une méthode qui émet des éléments : une telle méthode renvoie Children (voir Fragments).

La méthode sert surtout pour une liste d'emplacements, comme des onglets dont les panneaux sont une prop panels: Children[] : <Tabs labels={['Profil', 'Sécurité']} panels={[this.#profile(), this.#security()]} />.

  • Tout est vérifié contre les @prop du composant : des enfants pour un composant qui n'en déclare pas, des enfants ou un emplacement obligatoires qui manquent, un emplacement inconnu.
  • Les enfants restent ceux du parent : leurs écouteurs, leurs lectures de store et leur état sont ceux du parent, et ils suivent son rendu. Le composant qui les reçoit les garde quand il se re-rend seul.
  • Un emplacement <:nom> se place directement dans un composant, sans attribut, une seule fois par nom. <:content> n'existe pas : les enfants directs remplissent déjà content.
  • Dans l'éditeur, <: dans un composant propose ses emplacements.

Références

ref={…} relie un élément à une référence déclarée par @ref nom: T;. Le type de l'élément est vérifié : une référence HTMLInputElement posée sur un <div> est une erreur.

Fragments réutilisables

Tout n'a pas besoin d'être un composant. Une méthode qui émet des éléments se réutilise dans render par une interpolation de son appel. Elle renvoie ce qu'elle émet, de type Children : return x; y est refusé, et son appel peut aussi remplir un emplacement nommé d'un composant.

Crée un composant quand il te faut un état local, un store, des événements ou un re-rendu indépendant (comme une ligne de liste).

Ne rien rendre

Une méthode qui n'émet aucun élément ne rend rien : render() {} est un composant vide, et un if sans else ne rend rien quand sa condition est fausse.

DOM et styles

  • Le DOM est patché, pas remplacé : le focus et la saisie en cours survivent à un re-rendu.
  • Light DOM : pas de shadow DOM. Tes styles globaux s'appliquent aux composants, et tu peux cibler leur tag en CSS (counter-list-item { display: contents; }).
  • Un élément racine n'est pas nécessaire : render peut émettre plusieurs éléments de premier niveau.

Styles d'un composant

Super n'a pas de système de styles : un composant est un élément du DOM comme un autre. L'app d'exemples suit une convention simple, que tu peux reprendre : une feuille par composant, posée à côté de lui (index.css pour un écran, counter-controls.css pour un sous-composant), importée par le composant, et dont les règles sont imbriquées sous son tag.

  • Le tag sert de portée : imbriquer sous app-shell évite qu'une classe .app-header touche le reste de la page, sans shadow DOM.
  • Le composant charge ce dont il a besoin : Vite inclut la feuille dès que le composant est importé, et la retire s'il ne l'est plus.
  • Les styles globaux d'abord : main.ts importe styles.css (variables, typographie, éléments de base) avant tout composant, pour que les feuilles des composants passent après.

Et html, nothing, repeat ?

@super-ts/dom exporte toujours html, nothing et repeat, les briques de lit-html sur lesquelles le compilateur s'appuie. Un composant écrit en .ts dont render renvoie un html`…` fonctionne encore, mais son template n'est pas vérifié par le compilateur. Écris tes composants en .super.
