Architecture

Super imposes two folders and four rules. Everything else in your src is user-land: Super does not look at it.

The structure

In @core/, the convention is one folder per contract: contract.ts, store.ts and its test. In @components/, one folder per screen, in kebab-case and without a suffix (shop/index.super exports ShopScreen), with its sub-components as flat files (counter/counter-controls.super); reusable components go in shared/. A component is a .super file (see Templates); its tests stay .ts. The plugin's rules only look at the first level: a file is under @core/, under @components/, or elsewhere.

src/@core/contracts.d.ts is generated by the Vite plugin: it is the name → contract class dictionary (plus the router, under 'router') that lets you write @contract counter; with full types, and the link between each screen and its route (ScreenRoutes). You commit it, you never write it.

The @ prefix

The prefix reads at a glance: a prefixed folder belongs to Super, a folder without a prefix belongs to your project. A core/ or components/ folder without @ is nothing special: it is a user-land folder like any other, which therefore cannot contain a store or a component.

Why @ and not $? In a shell, $core is read as a variable: cd src/$core silently lands in src/. @ works fine in the shell, in relative imports and in the dev server's URLs.
Not to be confused @super-ts/core is the framework package. @core/counter/contract is a file in your app, in src/@core/. One comes from node_modules, the other from your src.

Importing from @core and @components

Both Super folders are imported through aliases, from any file, whatever its depth:

No more '../../@core/…' to recount when a file moves folder. Relative imports ('../@core/counter/store') remain possible, and the architecture rules apply to both forms.

On the Vite and Vitest side, nothing to do: the superPlugin plugin declares these aliases itself, from the src folder you give it. An import without an extension also finds a .super: '@components/app-shell' leads to app-shell/index.super.

On the TypeScript side, for the IDE and the type check, declare the aliases in your app's tsconfig.json (no plugin can inject them into TypeScript). Each alias has two targets: your src, and the declarations of the .super files, which the tooling writes to .super/types/ (a folder ignored by git). rootDirs merges the trees (your src, the declarations, then the virtual TypeScript in .super/virtual/ from which they draw their types): a .ts that imports a .super component, like routes.ts, sees its types, and "go to definition" opens the .super.

Who writes this virtual TypeScript, and when: see Tooling.

Import order

Super also sets the order of imports, checked by the linter:

  1. Super packages: @super-ts/…;
  2. Super folders: @components/… and @core/…;
  3. everything else: Node modules (node:…), npm packages, then relative paths.

Within each group, the order is alphabetical.

You can see at a glance what comes from the framework, what comes from the app's Super building blocks, and the rest. Imports without a name (import './styles.css') are never moved: they act as separators, which preserves the loading order of stylesheets.

Linting

The rule is enforced by Biome. Super provides its configuration, which your project extends in its biome.json:

In this repository, Super's configuration is in packages/lint/config.json. Super's configuration only touches the import order: formatting and the other lint rules are left to the project. The repository itself enables Biome's formatter (two spaces, single quotes, 140 columns) and formats .super files with the same rules (see Tooling).

Other folders have no alias Only the Super folders have one. ports/, adapters/ or routes.ts are imported with relative paths ('../routes'), or with your own aliases if you declare some.

The four rules

RuleWhat is rejected
Contracts and stores are defined under src/@core/. A module outside @core/ that imports SuperContract or SuperStore from @super-ts/core.
Components are defined under src/@components/. A module outside @components/ (.super or .ts) that imports SuperElement from @super-ts/dom.
A component imports only types from @core/. A component that imports a value from @core/: a store, a contract class, a constant, a function, or an import * as.
Contracts and stores do not depend on the DOM. A module in @core/ that imports anything from @super-ts/dom (html, SuperElement, createApp…), except types.

The fourth rule keeps the core of the app independent of the display: a store is tested without the DOM, and could serve another interface. The third rule is the most important: it guarantees that a component sees a store only through its contract, which it asks for by name (@contract counter;). It reads through the selectors, sends commands, listens to events, and nothing else. This is what lets you test it with a fake store, and keeps domain logic from slipping into the view.

The Vite plugin

The @super-ts/vite plugin compiles .super files and enforces these rules. It is declared in vite.config.ts, and also serves Vitest:

The same plugin:

  • compiles each .super to TypeScript (lit-html templates), then strips the types; a compilation error stops the module from loading, with its position in the .super;
  • provides a source map from the final JS to the .super: stack traces and the debugger point to the line and column of the source (see Source maps);
  • applies the architecture rules to the compiled code: a .super is checked as a .ts would be;
  • in dev, rewrites the virtual TypeScript of a .super on every transform, so that the .ts files that import it see up-to-date types;
  • declares the @core/ and @components/ aliases, and adds .super to the resolved extensions (see above);
  • reads the contracts in src/@core/ (the contract.ts or *.contract.ts files, which declare export class X extends SuperContract and are named through super({ name })), rejects two contracts with the same name, and registers them so that each store finds its own by name;
  • finds the app's router (export const Router = defineRouter(…)) and adds it under 'router'; reads its .screens(…) to link each screen's tag to its route ('counter-screen': 'counter'), which types this.router.current in the screen;
  • writes it all to src/@core/contracts.d.ts, at startup and then on every file save in dev;
  • in dev, makes components hot-replaceable (see below).

Hot replacement of components

In dev, editing a component does not reload the page: the new version replaces the old one, and the displayed elements keep their state (local state, input, store state) and re-render with the new code. Components created afterwards use the new version, including from a parent that was not modified.

This replacement is only safe if the component's fields have not changed: the displayed elements were built with the old ones. Super therefore reloads the whole page when the change:

  • adds, removes or renames a field or a setup declaration (@state extra = …;);
  • modifies a handler written as an arrow field (onAnswered = () => …);
  • touches a component that has #private members, fields or methods such as a #row() that emits elements (those of the old class are not those of the new one).

Editing render, renderError, mounted or another method is done hot. For a .super, its compiled code replaces the old one. A file in @core/ (contract, store) always reloads the page. None of this exists in a build: the code added by the plugin is only active under vite in dev.

A module that breaks a rule is not loaded: Vite refuses to transform it and displays the error (overlay in dev, build or test failure).

What the plugin does not check

  • Tests (*.test.ts, *.test-d.ts): the app does not load them, so they can import a real store or define test doubles wherever they like.
  • Type imports (import type { CounterState } from '@core/counter/contract'): they disappear at compile time, so they are allowed everywhere.
  • User-land: domain/, ports/, adapters/, routes.ts, main.ts import whatever they like.

The plugin reads the code as text (for a .super, the compiled code): it recognises named imports (including those renamed with as), a contract by its declaration export class X extends SuperContract and the router by export const Router = defineRouter(…). See Limitations.

User-land

Outside @core/ and @components/, you organise things as you like. In the examples app:

  • domain/: the domain types and rules (Product, CartLine, the counter catalogue, the page of products requested from an API), without Super or the DOM. Contracts use them; a component can import their types.
  • ports/: the interfaces the stores need (here CounterRepository, ProfileClient, OrderClient, ProductCatalog). This is a choice inspired by hexagonal architecture; another project could put these interfaces next to the store, in @core/.
  • adapters/: the concrete implementations of these ports (localStorage, in-memory, a simulated server, the dummyjson.com HTTP API…).
  • routes.ts: the routes and screens, declared in a single export, Router. A component accesses it through this.router, which also builds links (this.router.href(…)); Router.href is for code outside components.
  • main.ts: the composition root, the only place that chooses the adapters and assembles everything.
