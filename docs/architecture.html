Architecture

Super impose deux dossiers et quatre règles. Tout le reste de ton src est du user-land : Super ne le regarde pas.

La structure

Dans @core/, la convention est un dossier par contrat : contract.ts, store.ts et son test. Dans @components/, un dossier par écran, en kebab-case et sans suffixe (shop/index.super exporte ShopScreen), avec ses sous-composants en fichiers à plat (counter/counter-controls.super) ; les composants réutilisables vont dans shared/. Un composant est un fichier .super (voir Templates) ; ses tests, eux, restent des .ts. Les règles du plugin, elles, ne regardent que le premier niveau : un fichier est sous @core/ ou sous @components/, ou ailleurs.

src/@core/contracts.d.ts est généré par le plugin Vite : c'est le dictionnaire nom → classe de contrat (plus le router, sous 'router') qui permet d'écrire @contract counter; avec tous les types, et le lien entre chaque écran et sa route (ScreenRoutes). On le committe, on ne l'écrit jamais.

Le préfixe @

Le préfixe se lit d'un coup d'œil : un dossier préfixé appartient à Super, un dossier sans préfixe appartient à ton projet. Un dossier core/ ou components/ sans @ n'a rien de spécial : c'est un dossier user-land comme un autre, qui ne peut donc contenir ni store ni composant.

Pourquoi @ et pas $ ? Dans un shell, $core est lu comme une variable : cd src/$core arrive silencieusement dans src/. @ passe sans souci dans le shell, dans les imports relatifs et dans les URLs du serveur de dev.
À ne pas confondre @super-ts/core est le paquet du framework. @core/counter/contract est un fichier de ton app, dans src/@core/. L'un vient de node_modules, l'autre de ton src.

Importer depuis @core et @components

Les deux dossiers Super s'importent par alias, depuis n'importe quel fichier, quelle que soit sa profondeur :

Plus de '../../@core/…' à recompter quand un fichier change de dossier. Les imports relatifs ('../@core/counter/store') restent possibles, et les règles d'architecture s'appliquent aux deux écritures.

Côté Vite et Vitest, rien à faire : le plugin superPlugin déclare ces alias lui-même, à partir du dossier src que tu lui donnes. Un import sans extension trouve aussi un .super : '@components/app-shell' mène à app-shell/index.super.

Côté TypeScript, pour l'IDE et le typecheck, déclare les alias dans le tsconfig.json de ton app (aucun plugin ne peut les injecter dans TypeScript). Chaque alias a deux cibles : ton src, et les déclarations des .super, que l'outillage écrit dans .super/types/ (un dossier ignoré par git). rootDirs fusionne les arborescences (ton src, les déclarations, puis le TS virtuel de .super/virtual/ d'où elles tirent leurs types) : un .ts qui importe un composant .super, comme routes.ts, en voit les types, et « aller à la définition » ouvre le .super.

Qui écrit ce TS virtuel, et quand : voir Outillage.

L'ordre des imports

Super fixe aussi l'ordre des imports, vérifié au lint :

  1. les paquets Super : @super-ts/… ;
  2. les dossiers Super : @components/… et @core/… ;
  3. tout le reste : modules Node (node:…), paquets npm, puis chemins relatifs.

À l'intérieur de chaque groupe, l'ordre est alphabétique.

On lit d'un coup d'œil ce qui vient du framework, ce qui vient des briques Super de l'app, et le reste. Les imports sans nom (import './styles.css') ne sont jamais déplacés : ils servent de séparateurs, ce qui préserve l'ordre de chargement des feuilles de style.

Le lint

La règle est portée par Biome. Super fournit sa configuration, que ton projet étend dans son biome.json :

Dans ce dépôt, la configuration de Super est dans packages/lint/config.json. La configuration de Super ne touche qu'à l'ordre des imports : le formatage et les autres règles de lint restent au choix du projet. Le dépôt, lui, active le formateur de Biome (deux espaces, guillemets simples, 140 colonnes) et formate les .super avec les mêmes règles (voir Outillage).

Les autres dossiers n'ont pas d'alias Seuls les dossiers Super en ont. ports/, adapters/ ou routes.ts s'importent en relatif ('../routes'), ou avec tes propres alias si tu en déclares.

Les quatre règles

RègleCe qui est refusé
Les contrats et les stores se définissent sous src/@core/. Un module hors de @core/ qui importe SuperContract ou SuperStore depuis @super-ts/core.
Les composants se définissent sous src/@components/. Un module hors de @components/ (.super ou .ts) qui importe SuperElement depuis @super-ts/dom.
Un composant n'importe de @core/ que des types. Un composant qui importe une valeur de @core/ : un store, une classe de contrat, une constante, une fonction, ou un import * as.
Les contrats et les stores ne dépendent pas du DOM. Un module de @core/ qui importe quoi que ce soit de @super-ts/dom (html, SuperElement, createApp…), sauf des types.

La quatrième règle garde le cœur de l'app indépendant de l'affichage : un store se teste sans DOM, et pourrait servir à une autre interface. La troisième règle est la plus importante : elle garantit qu'un composant ne voit un store qu'à travers son contrat, qu'il demande par son nom (@contract counter;). Il lit par les sélecteurs, envoie des commandes, écoute des événements, et rien d'autre. C'est ce qui permet de le tester avec un faux store, et d'empêcher qu'une logique métier se glisse dans la vue.

Le plugin Vite

Le plugin @super-ts/vite compile les .super et fait respecter ces règles. Il se déclare dans vite.config.ts, et sert aussi à Vitest :

Le même plugin :

  • compile chaque .super en TypeScript (des gabarits lit-html), puis en retire les types ; une erreur de compilation arrête le chargement du module, avec sa position dans le .super ;
  • fournit une source map du JS final vers le .super : traces d'erreur et débogueur pointent la ligne et la colonne de la source (voir Source maps) ;
  • applique les règles d'architecture au code compilé : un .super est vérifié comme le serait un .ts ;
  • en dev, réécrit le TS virtuel d'un .super à chaque transformation, pour que les .ts qui l'importent en voient les types à jour ;
  • déclare les alias @core/ et @components/, et ajoute .super aux extensions résolues (voir plus haut) ;
  • lit les contrats de src/@core/ (les fichiers contract.ts, ou *.contract.ts, qui déclarent export class X extends SuperContract et se nomment par super({ name })), refuse deux contrats du même nom, et les inscrit pour que chaque store retrouve le sien par son nom ;
  • repère le router de l'app (export const Router = defineRouter(…)) et l'ajoute sous 'router' ; lit ses .screens(…) pour relier le tag de chaque écran à sa route ('counter-screen': 'counter'), qui type this.router.current dans l'écran ;
  • écrit le tout dans src/@core/contracts.d.ts, au lancement puis à chaque fichier enregistré en dev ;
  • en dev, rend les composants remplaçables à chaud (voir ci-dessous).

Remplacement à chaud des composants

En dev, modifier un composant ne recharge pas la page : la nouvelle version remplace l'ancienne, et les éléments affichés gardent leur état (état local, saisie, état des stores) et se re-rendent avec le nouveau code. Les composants créés ensuite utilisent la nouvelle version, y compris par un parent qui n'a pas été modifié.

Ce remplacement n'est sûr que si les champs du composant n'ont pas changé : les éléments affichés ont été construits avec les anciens. Super recharge donc la page entière quand la modification :

  • ajoute, retire ou renomme un champ ou une déclaration de préparation (@state extra = …;) ;
  • modifie un handler en champ fléché (onAnswered = () => …) ;
  • touche un composant qui a des membres #privés, champs ou méthodes comme un #row() qui émet des éléments (ceux de l'ancienne classe ne sont pas ceux de la nouvelle).

Modifier render, renderError, mounted ou une autre méthode se fait à chaud. Pour un .super, c'est son code compilé qui remplace l'ancien. Un fichier de @core/ (contrat, store) recharge toujours la page. Rien de tout ça n'existe en build : le code ajouté par le plugin n'est actif que sous vite en dev.

Un module qui enfreint une règle n'est pas chargé : Vite refuse de le transformer et affiche l'erreur (overlay en dev, échec du build ou du test).

Ce que le plugin ne vérifie pas

  • Les tests (*.test.ts, *.test-d.ts) : l'app ne les charge pas, ils peuvent importer un vrai store ou définir des doublures où ils veulent.
  • Les imports de type (import type { CounterState } from '@core/counter/contract') : ils disparaissent à la compilation, ils sont libres partout.
  • Le user-land : domain/, ports/, adapters/, routes.ts, main.ts importent ce qu'ils veulent.

Le plugin lit le code comme du texte (pour un .super, le code compilé) : il reconnaît les imports nommés (y compris renommés avec as), un contrat à sa déclaration export class X extends SuperContract et le router à export const Router = defineRouter(…). Voir Limites.

Le user-land

Hors de @core/ et @components/, tu organises comme tu veux. Dans l'app d'exemples :

  • domain/ : les types et les règles métier (Product, CartLine, le catalogue des compteurs, la page de produits demandée à une API), sans Super ni DOM. Les contrats s'en servent ; un composant peut en importer les types.
  • ports/ : les interfaces dont les stores ont besoin (ici CounterRepository, ProfileClient, OrderClient, ProductCatalog). C'est un choix inspiré de l'architecture hexagonale ; un autre projet pourrait mettre ces interfaces à côté du store, dans @core/.
  • adapters/ : les implémentations concrètes de ces ports (localStorage, mémoire, un serveur simulé, l'API HTTP de dummyjson.com…).
  • routes.ts : les routes et les écrans, déclarés dans un seul export, Router. Un composant y accède par this.router, qui construit aussi les liens (this.router.href(…)) ; Router.href sert au code hors composants.
  • main.ts : la racine de composition, le seul endroit qui choisit les adapters et assemble le tout.
